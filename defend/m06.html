AI code review and the software supply chain

What an AI code reviewer can and cannot see, why a published accuracy score can mislead, how to turn a warning into proof, and where AI assistants add new trust to your supply chain.

The idea in one minute

An AI reviewer reads a code change and comments on possible security problems. It is good at spotting patterns that nobody wrote a rule for, and at explaining them in plain language. But it sees only what it is given, and it never runs the code.

So "No security issues found" means "nothing in the text I was shown looked like a known problem". It does not mean "this change is safe".

Think of it like this

An AI reviewer is like a smart friend who reads one page of your contract. They can spot odd wording on that page. They cannot see the other pages, your company rules, or what happens when the contract is used.

Learn it from zero

Step 1. Four ways to check code

  • Rule scanner (SAST). Matches a fixed list of known-bad patterns in seconds. Finds nothing outside its list.
  • AI reviewer. Reads the change and points out anything that resembles a known problem. Sees only what it is given and never runs the code.
  • Data-flow tool. Traces where user input travels through the whole codebase. Needs everything and is slow.
  • Dynamic testing (DAST). Runs the live app and tries attacks. Finds only what its tests try.

Step 2. Scores that mislead

A model scored F1 68 percent on the BigVul benchmark. On a cleaned version, PrimeVul, the same model scored about 3 percent. BigVul had wrong labels, duplicates between training and test, and test code from the same years as training. The 68 percent measured how well the model repeated labels on code it had seen, not how well it finds new flaws.

Step 3. Specific labels matter

CWE is a catalog of weakness types. A broad label such as CWE-20, improper input validation, fits almost anything, so a model picks it often. A specific label such as CWE-502, deserialization of untrusted data, tells the developer the fix. MITRE discourages CWE-20 for mapping real vulnerabilities.

Step 4. From flagged to confirmed

A warning is a guess until a test proves it. Use three verdicts. Confirmed means someone carried out the attack in a test and it worked. Disproved means how the feature works shows it is impossible. Could not confirm means a test failed but nothing shows it is impossible. Keep that record open.

Step 5. Trust points in the supply chain

You trust the package registry, package authors, build tools, vendors, and now the AI coding assistant, which may recommend packages that do not exist. Attackers register those names. A lock file records what you installed, but it does not tell you a new package was safe.

Words you need

Pull request
A proposed code change that teammates review before it is accepted.
SAST
Static application security testing. Scans source code without running it.
DAST
Dynamic application security testing. Attacks the running app.
CWE
Common Weakness Enumeration. A catalog of software weakness types.
F1
One number from 0 to 100 percent that balances precision and recall.
IDOR
Insecure direct object reference. The app returns an object without checking that it belongs to the caller.
Lock file
A file that records each package's exact version and a fingerprint of its contents.
Shift left
Moving checks earlier in development, where fixes are cheaper.
