Excessive agency, how agents go wrong

Agents turn words into actions. Learn the agent loop, the confused deputy problem, and how to give an agent only the power its task needs.

The idea in one minute

A chatbot can only say things. An agent can do things. It calls tools such as email, a database, a browser or a payment API, in a loop, until a task is done.

OWASP names three ways an agent gets too much power.

  • Excessive functionality. It has tools it does not need, such as a delete tool for a read task.
  • Excessive permissions. Its tools reach more data than needed, such as a whole mailbox for one folder.
  • Excessive autonomy. It acts on high-impact steps with no person to check.

When an injection or a plain mistake happens, these extra powers turn it into real damage.

Think of it like this

You give a house sitter a key to water the plants. If the key also opens the safe and the car, a trick phone call to the sitter can empty your house.

Words you need

Agent
An LLM that runs in a loop, chooses tools, reads their results and decides the next step.
Tool
A function the app lets the model call, such as send_email or run_sql.
ReAct
A common agent pattern. The model writes a Thought, then an Action, then reads an Observation, and repeats.
Confused deputy
A program with power that is tricked into using it for someone else. The agent acts with the user's rights for the attacker's goal.
OAuth scope
A named permission given to an app, such as 'read mail'. Scopes are coarse.
Policy engine
A separate program that checks each action against rules before it runs.
LLMjacking
Stealing access to someone's AI service and using it at their cost.

How it works, step by step

The agent loop

  1. The user gives a task.
  2. The model writes a Thought and picks a tool with arguments.
  3. The app runs the tool. The model never runs anything itself.
  4. The result goes back into the context as an Observation.
  5. The model decides the next step, until it says it is done.

Step 3 is where you put controls. Step 4 is where attacks get in, because tool results are untrusted text.

The confused deputy

The agent acts with the user's real permissions. An attacker who cannot read the user's mail sends the user one email with hidden instructions. The agent reads it while doing a normal task, and then uses the user's rights to forward private mail. The attacker borrowed the user's power through the agent.

Why OAuth scopes are too broad

A scope says what an app may touch, such as all mail. It cannot say why or which items, such as only travel receipts. So the agent's real power is much bigger than its task.

The attack, as a workflow

  1. List the agent's tools and what each one can reach.
  2. Find a way to put text in front of the agent, such as an email, a web page, a file or a tool result.
  3. Write an instruction that uses a powerful tool the task does not need.
  4. Make the action look routine, so a person who must approve it says yes.
  5. Use the agent's access to read, send, change or delete data.

Real cases

Chevrolet dealer bot, 2023

The bot could make promises for the dealer with no limit, so a user got it to 'agree' to a one-dollar car. This is excessive autonomy.

Operation Bizarre Bazaar

Pillar Security reported a campaign that found exposed AI endpoints, took them over and sold access on a marketplace. Owners paid for the attackers' use.

How to defend

  • Fewer tools. Give only the tools the task needs. Prefer narrow tools, such as get_order_status, over open ones, such as run_any_sql or run_shell.
  • Fewer permissions. Run tools with the current user's identity and the smallest scope. Use short-lived tokens.
  • Check each call. Put a policy engine between the model and the tools. It checks the content of each call, not only who calls.
  • Human approval for high impact. Money, deletion, sending outside and permission changes need a person. Show the person exactly what will happen.
  • Limits. Cap amounts, counts and steps per task. Log every tool call.

Case study. ARTEX, an autonomous pentest agent

ARTEX is an open source, self-hosted platform where LLM agents run penetration tests. A planner splits a goal into small tasks called intents. Workers run real tools for each intent and write results back into two linked graphs, one for the target's assets and one for the test's progress.

Its README lists the controls it uses to keep an autonomous agent inside its job. They map closely to the defenses above.

  • Scope and deny rules. The agent may touch only listed targets. This is least privilege for the network.
  • Command prefix rules. Only allowed command shapes can run. This is a narrow tool set.
  • Human approval gates. A person approves chosen actions. This limits autonomy.
  • Token and turn budgets, and a noise governor. Caps on cost, steps and traffic. This also guards against unbounded consumption (lesson 14).
  • Prompt injection framing on tool output. Tool results are marked as data, because a target can answer with text that tries to steer the agent.
  • Evidence for every finding. Each finding links to the exact request and response that proves it, which helps humans check the agent's claims.
Careful

Tools like this are for authorized testing only. Running them against systems without written permission is illegal in most countries. In MITRE ATLAS, attackers who use agents like this map to AML.T0116 Autonomous Reconnaissance and AML.T0124 Autonomous Attack Orchestration.
