Prompt injection, advanced defenses

Why "do not reveal the password" in a prompt is not a defense, and how real defenses treat the model as an untrusted part.

The idea in one minute

A rule in the system prompt is a request. The attacker can write a stronger request. So defenders build around the model.

Some defenses look at the text, such as filters and detectors. Some defenses change how the model is asked, such as SmoothLLM, which asks many times. The strongest defenses limit what a fooled model can reach.

Think of it like this

You cannot make a guard dog that never gets tricked by a treat. You can put the money in a safe that the dog cannot open.

Words you need

Guardrail
Any check placed before or after the model to block bad input or output.
Sandwich defense
Put the untrusted text between two copies of the rules, so the last thing the model reads is the rule.
Spotlighting
Mark untrusted text clearly, for example with tags or a changed encoding, so the model can tell it apart.
SmoothLLM
Make several slightly changed copies of the prompt, run each one, and take the majority answer.
Erase-and-check
Delete tokens from the prompt in a planned way and run a safety check on each shorter version.
Canary token
A secret string placed in the prompt. If it shows up in the output, the prompt has leaked.
Latency
The time a user waits for an answer.

How it works, step by step

Layer 1. Prompt design

Write clear rules. Put untrusted text inside tags, and say that text inside the tags is data. Repeat the key rule after the data (the sandwich). This lowers the success rate. It does not stop a determined attacker.

Layer 2. Input and output checks

A detector looks for known attack patterns before the model runs. An output check looks for leaked secrets, canary tokens or banned content after it runs. Tools include classifiers and open source detectors such as Rebuff. They catch known patterns well and new wording badly.

Layer 3. Smoothing defenses

SmoothLLM (Robey et al., 2023) works because many automatic jailbreaks, such as GCG suffixes, are fragile. A few random character changes break them. SmoothLLM makes N copies of the prompt, changes a few characters in each, runs all N, and takes a majority vote. The cost is N model calls per message.

Erase-and-check (Kumar et al., 2023) deletes tokens from the prompt and runs a safety filter on each shorter version. If any version is harmful, it rejects the prompt. Its full mode gives a proven guarantee for attacks up to a set length, but it is slow. Section 7 of the paper describes faster versions, such as RandEC, which checks only a random sample of the erased versions.

Layer 4. Architecture

Give the model only the tools and data that the task needs. Check every tool call in code. Ask a person before risky actions. Research designs such as the dual LLM pattern and CaMeL keep untrusted text away from the part that decides what to do next.

Real cases

Guardrail benchmarks

Module 11 shows a vendor claim of 94 percent blocked that fell to about 37 percent on new attacks. Detectors trained on public jailbreak sets often miss the same new prompts, so stacking two of them adds little.

How to defend

  1. Write the system prompt with tags around untrusted text and the key rule repeated at the end.
  2. Add a cheap detector on input. Log what it flags.
  3. Add an output check that looks for secrets, canary tokens and outside links.
  4. Remove tools the bot does not need. Put limits on the ones it keeps.
  5. For high-risk actions, ask a person to approve.
  6. Test with new attacks every month and update the layers.

Readings, explained

  • SmoothLLM. Defending LLMs against jailbreaking attacks must read paper
    Shows that adding random character noise to many copies of a prompt and taking a vote cuts the success of GCG attacks to below one percent in their tests. Read the method and the cost section.
  • Erase-and-check. Certifying LLM safety against adversarial prompting paper
    Gives a proven guarantee against adversarial text up to a set length. Read Section 7 for the faster versions used in practice.
  • Security Innovation. Securing LLMs against prompt injection article
    A practical primer on prompt design, least privilege and output monitoring for security teams.
