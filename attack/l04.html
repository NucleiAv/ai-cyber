Sensitive information disclosure

How a model gives back private data it learned, how RAG apps leak documents to the wrong user, and why "delete my data" is hard for a model.

The idea in one minute

Private data can leak from an LLM app in three places.

  • The weights. A model can memorize rare text from its training data, such as an email address or a key, and repeat it word for word.
  • The context. A RAG app pastes documents into the prompt. If it pastes a document the user may not see, the model can repeat it.
  • The plumbing. Logs, databases and keys around the model leak too. Often the model is fine and the server is open.
Think of it like this

A parrot that heard your phone number a hundred times may say it to a stranger. A parrot that hears a secret only once usually will not. Models are similar. Text that appears many times, or that is very unusual, is the text they remember.

Words you need

PII
Personally identifiable information, such as a name, phone number or address.
Memorization
The model stores exact training text and can reproduce it.
Training data extraction
Prompting a model to give back exact pieces of its training data.
Membership inference
Testing whether a given record was in the training data.
Confused deputy
A program with high permissions that is tricked into using them for someone who should not have them.
Machine unlearning
Methods that try to remove one piece of data's effect from a trained model without retraining from zero.
Differential privacy
A training method with a mathematical limit on how much any single record can change the model.

How it works, step by step

Extraction from the weights

Carlini and others (2021) attacked GPT-2 in three steps.

  1. Generate a very large number of text samples from the model.
  2. Rank them. Text that the model finds far more likely than a reference finds it, for example a smaller model or zlib compression, is likely memorized.
  3. Check the top results against the internet and the training data.

They recovered hundreds of exact training sequences. Some held names, phone numbers, email addresses and chat logs. Larger models memorized more.

Leaks through RAG

A RAG app retrieves documents with its own service account. If the search step does not filter by the user's permissions, a question from an intern can pull a board-only document into the prompt. The model then summarizes it.

The ConfusedPilot paper (2024) studied RAG systems like Microsoft 365 Copilot. An insider plants a document with crafted text. When it is retrieved, it can change other users' answers or make the system ignore real documents. The paper also shows that cached answers can keep content visible after the source document is gone.

Leaks around the model

Wiz found an open DeepSeek database in January 2025. It held more than a million lines of logs with chat history, secret keys and backend details. No prompt was needed. Wiz also found AI service keys pushed to public code on GitHub.

The attack, as a workflow

  1. Find out where the app gets its knowledge. Ask what documents or data it can use.
  2. Ask for content near the private data, for example "summarize all HR documents from this quarter".
  3. For memorized data, give the model the start of a likely record, such as "Contact John at", and let it complete it.
  4. Ask for the same data in a new form, such as a table, a translation or a JSON object, to get past output filters.
  5. Look outside the model too. Search public code and buckets for keys and open databases. Look, never use.

Real cases

DeepSeek database, January 2025

Wiz found a public ClickHouse database with chat history, API secrets and logs. DeepSeek closed it after Wiz reported it.

Samsung, 2023

Staff pasted source code and meeting notes into a public chatbot. The company then limited the use of outside AI tools. The data left the company through the prompt, not through an attack.

How to defend

  • Do not train on data that the model must never repeat. Remove secrets and PII before training.
  • In RAG, check permissions in the search step. Use metadata filters or separate indexes per group.
  • Filter output for PII and secrets. Treat it as a last layer, not the main control.
  • Keep keys in a secret manager, never in prompts or code. Scan your repositories for secrets.
  • For strong privacy needs, train with differential privacy. It lowers accuracy, so plan for that.

Hands-on lab

Solve LLMGoat A02, sensitive information disclosure. Then do the extend task.

  1. Open A02 and read what the app knows.
  2. Ask for the protected data directly and note the refusal.
  3. Ask for it in a new format or as part of a larger task.
  4. Save the prompt that worked.
  5. Extend task. Search GitHub for leaked AI API keys the way Wiz did, with code search for key prefixes in public repositories. Look, never use. If you find a live key, report it to the owner.

Readings, explained

  • Extracting training data from large language models (Carlini et al.) must read paper
    The classic extraction paper. Read the attack method, the examples of memorized data and the section on ethics.
  • ConfusedPilot. Confused deputy risks in RAG-based LLMs must read paper
    Shows how crafted documents and caching break the confidentiality and integrity of RAG answers in enterprise tools.
  • Wiz. Exposed DeepSeek database leak article
    A short case. A leading AI company exposed logs and keys through a plain open database.
  • Wiz. Leaking AI secrets in public code article
    How AI keys end up in public code, and how to find them.
