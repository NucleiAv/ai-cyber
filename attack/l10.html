Excessive agency, governance and policy as code

How to control agents with rules that a computer enforces. Anthropic's RSP, the EU AI Act, and Open Policy Agent with Rego.

The idea in one minute

Lesson 9 said "put a check between the agent and its tools". This lesson builds that check.

There are two kinds of rules.

  • Organization rules, such as a company's safety policy or a law. People read them.
  • Code rules, such as "deny DELETE requests". A computer enforces them on every call. This is policy as code.

Good governance turns the first kind into the second kind wherever it can.

Think of it like this

A sign that says "staff only" is a people rule. A door that opens only for a staff badge is a code rule. The door works even when nobody reads the sign.

Words you need

RSP
Anthropic's Responsible Scaling Policy. It ties stronger safety and security measures to stronger model capabilities.
ASL
AI Safety Level. A set of required safeguards in Anthropic's RSP, such as ASL-3.
OPA
Open Policy Agent. An open source engine that decides allow or deny from a policy and an input.
Rego
The policy language of OPA.
Default deny
If no rule allows an action, it is blocked.
LLM-as-a-judge
Using a model to score or classify another model's output.

How it works, step by step

Self-regulation and law

Anthropic's RSP sets capability thresholds. When a model reaches one, the company must apply a matching AI Safety Level of protection before it trains further or deploys. In May 2025 Anthropic turned on ASL-3 protections for Claude Opus 4. The policy is voluntary. Anthropic can change it.

The EU AI Act is law. It sorts AI systems by risk. High-risk systems carry duties such as risk management, logging and human oversight, with fines for breaches.

How OPA decides

  1. The app sends OPA a JSON input that describes the action, such as the method, the path and the user's role.
  2. OPA evaluates the Rego policy against the input.
  3. OPA returns a decision, such as allow true or false.
  4. The app enforces the decision. The model never sees the policy and cannot argue with it.

The limit

Rego is exact. It can check amount > 5000. It cannot check "this answer is biased", because that needs judgment about meaning. For that, teams add an LLM judge or a classifier in the loop. A judge is probabilistic, so its decision needs logging, testing and often a person.

How to defend

  • Write agent permissions as code with default deny.
  • Keep exact rules in code (methods, paths, roles, amounts). Send meaning-based rules to a judge plus a person.
  • Version, review and test policies like code.
  • Log every decision for audit.

Case study. ARTEX, an autonomous pentest agent

ARTEX, the autonomous pentest platform from lesson 9, shows policy as code in an offensive tool. Its README describes argv-prefix rules, which allow only commands that start with an approved prefix, plus scope and deny gates and approval gates. A Rego policy in your own agent does the same job. It decides, outside the model, which actions are allowed.

Hands-on lab

Write a Rego policy in the OPA Playground that limits an AI agent's API calls. Try your own policy first. Then open the solution and compare.

  1. Rule 1. Allow GET requests to /products.
  2. Rule 2. Deny DELETE requests to any endpoint.
  3. Rule 3. Allow POST to /orders only if user_role is admin.
  4. Test 1. {"method": "POST", "path": ["orders"], "user_role": "admin"} must be allowed.
  5. Test 2. {"method": "GET", "path": ["products"], "user_role": "guest"} must be allowed.
  6. Test 3. {"method": "DELETE", "path": ["products"], "user_role": "admin"} must be denied.
  7. Extend task. Write a Rego rule that would have blocked your week 9 LLMGoat attack.
Show one solution. Try your own first
package agent.authz

default allow := false

deny if input.method == "DELETE"

allow if {
    not deny
    input.method == "GET"
    input.path == ["products"]
}

allow if {
    not deny
    input.method == "POST"
    input.path == ["orders"]
    input.user_role == "admin"
}
Hints, open only if stuck for 30 minutes
  • The Playground uses OPA 1.x syntax, so rule bodies use the keyword if.
  • With default allow false, any request that no rule allows is already denied. Rule 2 makes the deny explicit, so a later allow rule cannot open DELETE by mistake.
