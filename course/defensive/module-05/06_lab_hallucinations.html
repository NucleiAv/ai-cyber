The Hallucination Audit Lab

A model will hand you fluent, confident threat intelligence. Some of it is true, some is true but out of date, and some is invented. Your job is not to trust the tone, it is to run the audit. In this lab you will hunt fabrications in raw model output, route every claim to the source that adjudicates it, stamp a verdict, and walk away with a verification checklist that is yours to keep.

~30 min lab, self-paced 4 stages 2 knowledge checks

What this lab builds

By the end of this lab, you will be able to:

  • Spot the fabrications that look exactly like the real thing: invented identifiers, wrong version boundaries, dead reference links
  • Route every atomic claim to the one source that adjudicates its type, and stamp a calibrated verdict
  • Separate a hallucination from a stale truth, and an unsupported claim from a contradicted one
  • Assemble a personal verification checklist you can carry into any CTI engagement or professional practice

How this lab works

Everything runs right here, no model setup required. You will work on illustrative reconstructions of model output, written to behave exactly like the real failure modes we covered in the summarization material. Every case is a real, well-documented vulnerability chosen because its facts are long settled (Log4Shell, Heartbleed, and the Apache Struts flaw behind the Equifax breach), so the practice transfers and nothing here goes stale. Each stage gives you instant, explained feedback. There is nothing to submit: the point is the reasoning and the checklist you leave with.

    This is a risk decision, not a fact to route. The right patch window depends on exposure, change windows, and risk acceptance. The model can propose 24 hours; only the organization can decide it.     The artifact you would actually ship keeps claims 1–3 with their sources and a verification date, replaces claim 4 with the current vendor guidance, strips or explicitly flags claim 5 as unsubstantiated, and converts claim 6 into a recommendation for the risk owner. Next: Heartbleed, a bug so famous the model will describe it with total confidence, and watch what that confidence does to the facts.

    Heartbleed is one of the most famous bugs in security history, which is exactly why a model will speak about it with total confidence. Asked without grounding, here is what it produced. Watch what that confidence does to the technical details.

    model: local · ungrounded  ·  claims tagged (1)–(5)
    // reconstructed model output (no grounding) "CVE-2014-0160, Heartbleed, is a vulnerability in the OpenSSL cryptographic library. (1) It is a critical remote code execution flaw that lets an attacker run arbitrary code on the server. (2) Its CVSS v3.1 base score is 10.0 Critical. (3) Every version of OpenSSL is affected, and there is no available fix. (4) It is listed in CISA's Known Exploited Vulnerabilities catalog. (5)"
    Source dossier · the ground truth you route to
    CVE record / NVD
    CVE-2014-0160 (Heartbleed): a buffer over-read in OpenSSL's TLS/DTLS heartbeat extension lets a remote attacker read process memory (private keys, credentials, session data). Information disclosure; no code execution. CVSS 3.1 base 7.5 HIGH (AV:N/AC:L/PR:N/UI:N/S:U/C:H/I:N/A:N). CVSS v2 base 5.0.
    OpenSSL security advisory
    Affected: OpenSSL 1.0.1 through 1.0.1f (and 1.0.2-beta). Fixed in 1.0.1g. 1.0.0 and earlier are not affected. After upgrading, reissue and revoke certificates and reset secrets that may have been exposed.
    CISA KEV
    CVE-2014-0160 is listed in the Known Exploited Vulnerabilities catalog.
    1

    “CVE-2014-0160, Heartbleed, is a vulnerability in the OpenSSL cryptographic library.”

    Route · which source adjudicates this?
    Verdict · stamp it
    VerifiedRoute → CVE record / NVD

    Existence and identity check out against the CVE record. As always, the headline of a famous CVE is the part the model is most likely to get right. Hold your trust there and nowhere else yet.

    2

    “It is a critical remote code execution flaw that lets an attacker run arbitrary code on the server.”

    Route · which source adjudicates this?
    Verdict · stamp it
    ContradictedRoute → CVE record / NVD

    The single most common Heartbleed misconception, and the model repeats it with a straight face. NVD describes an information-disclosure buffer over-read: the attacker reads memory, they do not run code. The vector says so plainly (C:H, but I:N and A:N). Mischaracterizing the flaw type changes the whole response, the containment, the urgency, and the story you tell the CISO.

    3

    “Its CVSS v3.1 base score is 10.0 Critical.”

    Route · which source adjudicates this?
    Verdict · stamp it
    ContradictedRoute → NVD enrichment

    NVD scores Heartbleed 7.5 High on CVSS 3.1 (and 5.0 on the older v2), not 10.0. The inflated score follows naturally from the previous error: once you wrongly believe it runs code, a 10.0 feels right. Routing the score to NVD instead of to the model’s sense of drama catches it.

    4

    “Every version of OpenSSL is affected, and there is no available fix.”

    Route · which source adjudicates this?
    Verdict · stamp it
    ContradictedRoute → Vendor advisory

    Both halves are wrong, and the vendor advisory owns both. Only OpenSSL 1.0.1 through 1.0.1f are affected; 1.0.0 and earlier never were, and the fix shipped in 1.0.1g. “No fix available” is the most dangerous shape of wrong: it tells a defender to despair instead of upgrade.

    5

    “It is listed in CISA’s Known Exploited Vulnerabilities catalog.”

    Route · which source adjudicates this?
    Verdict · stamp it
    VerifiedRoute → CISA KEV

    True, and KEV is the source that confirms it. Notice the pattern across this case: the model was right about what is easy to recall (the name, the existence, the KEV listing) and wrong about the engineering specifics that decide your response. Fame is not accuracy.

    0 / 5 audited

    Case B audited

    Three of five claims overstated a real, world-famous bug: Heartbleed is an information-disclosure over-read, not remote code execution; its score is 7.5, not 10.0; and a fix has existed since 1.0.1g. The sharper the model’s confidence, the more carefully you route. Next: Apache Struts, where the headline is right and the details quietly drift.

    This is the Apache Struts flaw behind the 2017 Equifax breach. Asked without grounding, the model nails the headline, then drifts on exactly the specifics that decide a remediation. This is the realistic profile you will meet most often: right where it is easy, wrong where it matters.

    Route · which source adjudicates this?
    Verdict · stamp it
    VerifiedRoute → CVE record / NVD

    Correct: RCE in the Jakarta Multipart parser, triggered through a crafted Content-Type header. The nature of the flaw matches NVD. So far the model is reliable, which is precisely the trust the next three claims will try to spend.

    2

    “It carries a CVSS base score of 10.0.”

    Route · which source adjudicates this?
    Verdict · stamp it
    VerifiedRoute → NVD enrichment

    NVD confirms 10.0 Critical (the scope change to other components pushes it to the maximum). Unlike Heartbleed, here the severity claim is genuinely right. Verifying is still a lookup, not a guess: you confirmed it, you did not assume it.

    3

    “Affected versions are 2.3.5 through 2.5.31; upgrade to 2.5.33 to remediate.”

    Route · which source adjudicates this?
    Verdict · stamp it
    ContradictedRoute → Vendor advisory

    The Apache bulletin owns these numbers: affected ranges are 2.3.5–2.3.31 and 2.5–2.5.10, fixed in 2.3.32 and 2.5.10.1. The briefing’s “2.5.31” and “2.5.33” are confident inventions that read just like real version strings. This is the version-boundary failure that survives every casual reread and only the vendor advisory catches.

    4

    “A full analysis is published at struts.apache.org/announce/2017/cve-2017-5638-analysis.html.”

    Route · which source adjudicates this?
    Verdict · stamp it
    FabricatedRoute → Click the reference

    The domain is real; this specific path is not, and it resolves to nothing. The model assembled a plausible URL the way it assembles any string, with nothing forcing it to point at a real page. One click settles it. A citation no one clicked is a citation no one verified.

    5

    “Public reporting attributes the exploitation to a single named ransomware crew.”

    Route · which source adjudicates this?
    Verdict · stamp it
    Unverifiable hereRoute → Primary reporting

    Your dossier carries no attribution, so on this evidence the claim cannot be verified, and it routes to primary reporting, where it should be read with the deepest skepticism. The “single named crew” framing is exactly the over-specific, tidy story tends to invite, and real exploitation of this flaw was broad. Mark it unverified rather than passing the model’s certainty along as your own.

    0 / 5 audited

    Case C audited

    Right headline, right severity, then a fabricated version boundary, an invented citation, and over-specified attribution. This is the failure profile you will actually face: not obvious nonsense, but confident drift on the few specifics that decide a remediation. The fix is not a sharper eye, it is the routine you just ran. Build it into a checklist next.
