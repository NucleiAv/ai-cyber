Driving Question

How do we turn the prose of a threat report into machine consumable intelligence, how well do language models do that conversion, and how would we know?

1

Why Structure Matters

A SOC's defensive systems ( rules, , EDR watchlists) consume : typed, normalized, machine readable artifacts. A forty page APT report is unstructured intelligence: rich for the human analyst, invisible to the firewall. Module 3 introduced this gap between human-readable and machine-consumable output; IoC extraction is how bridges it. The conversion between them, historically a tedious manual task, is precisely the kind of text transformation language models are suited to, which makes it both a real productivity win and a place where silent errors flow directly into enforcement systems.

The raw material comes first. We defined the earlier; here is the full working taxonomy. Each type has different operational use, different lifespan, and different false positive consequences when blocked.

File hashes

MD5, SHA-1, SHA-256. Identify specific files with high precision while they last; trivially changed by the adversary. Blocking cost: near zero .

IPs and domains

Identify adversary infrastructure. Domains cost more to rotate than IPs. Blocking cost: real, since shared hosting and abused legitimate services mean collateral damage is possible.

Host artifacts

File paths, registry keys, mutexes, and URLs. Identify particular malware behavior on hosts. Weaker individually, valuable in combination for hunting.

Published reports usually their indicators: rendering them inert so a document cannot be accidentally clicked or auto linked. Convention: hxxp for http, bracketed dots like 203.0.113[.]47 or evil[.]example. Extraction must recognize defanged forms and refang them correctly for machine use. And a careless pipeline that refangs into a live clickable link inside a shared document recreates the hazard defanging exists to prevent.

Why this matters

Extraction sits on the path between reading and enforcement. Whatever lands in the structured output is what the SIEM matches and the firewall blocks; an error here is not a wrong sentence in a document but a wrong rule in production. block legitimate services, including, in the classic blunder, the victim organization's own domain lifted from the report's narrative. are silent coverage gaps. And interoperability is an organizational reality: sharing communities, government feeds, and commercial platforms speak STIX, so an analyst who cannot read an indicator object cannot evaluate what their own feeds are telling their systems to do.

The Extraction Pipeline, Scored Like a Detector

The LLM extraction workflow applies our Module 3 structured output skills, end to end:

  1. 1

    Schema first

    Decide fields before prompting: type, value, defanged original, context sentence, confidence. The Module 3 lesson: models conform to schemas far better than they infer them.

    {"type": "...", "value": "...", "defanged_original": "...", "context": "..."}
  2. 2

    Prompt with few-shot examples

    Include a defanged example so the model learns the convention is in scope. Instruct: extract only indicators the text presents as attacker controlled or malicious.

    Example in: "hxxps://bad[.]example/x" → {"type": "url", "value": "https://bad.example/x", ...}
  3. 3

    Generate and parse

    Validate the JSON syntactically first. A malformed field is also an extraction failure.

    json.loads(output) before anything else
  4. 4

    Score against the key

    Manual extraction by a human is the ground truth. Apply the precision and recall framework from Module 1: the formulas and intuitions carry over unchanged. Inspect every error: misses and false positives have causes, and the causes tell us how to improve the prompt or whether the task needs a human pass.

  5. 5

    Structure for sharing

    Render accepted indicators into the target format (a STIX indicator template in this course), preserving the link back to the source report. An indicator divorced from its context is data again, not intelligence.

    indicator object + relationship back to the report

The evaluation step deserves emphasis. We evaluate an extractor exactly the way we evaluated a detector in Module 4: the and vocabulary transfers unchanged; only the artifact differs. What is new here is where the errors go: into an enforcement system that acts on them silently.

Why the answer key matters: extraction failures are silent

The failure taxonomy in CTI extraction: missed defanged forms (recall failure), false positives from context (the report mentions the victim's own domain, or a legitimate service the actor abused, and the extractor sweeps it into the blocklist), type confusion (a SHA-1 labeled as MD5, an internal IP extracted as infrastructure), and silent normalization errors (refanging mistakes, truncated hashes). Module 4's error-analysis lesson applies directly here: a blocklist from an extractor with 100 percent precision and 60 percent recall is dangerous not because it is wrong, but because it earns trust while 40 percent of the indicators silently never arrived. Coverage you believe you have but do not is worse than coverage you know you lack.

"The actor's phishing emails delivered an archive from

Your prediction task, before scrolling further: a manual analyst extracted seven items from this excerpt as the answer key. Predict which two indicators a language model is most likely to miss or mishandle, and state why in one sentence each. Write your predictions down. The reveal in the scenario box below discusses the 'chosen' answers, and a justified case for other choices earns credit in the lab version of this exercise.

Step 2 · The manual key and the model's first pass

The manual key (ground truth): the defanged URL, the SHA-256, the IP 203.0.113.47, the registry key, the domain update-portal.example-cdn.net, the domain filestore.example-cdn.net, and the file name pkg.zip as a weak host artifact. Seven items. Explicitly excluded: megacorp.example, which is the victim, not infrastructure.

The model's first pass extraction (illustrative reconstruction, labeled as such) returned six items. It correctly extracted the URL (and refanged it), the hash, the IP, the registry key, and both domains. It missed pkg.zip. And it included megacorp.example as a malicious domain. 

// Score it like a detector (Module 4 vocabulary)
Extracted items:        7   (6 correct + 1 false positive)
Key items:              7   (6 found + 1 missed)

Precision = 6 / 7 = 0.86   
Recall    = 6 / 7 = 0.86

Scenario: compare your predictions

You predicted which two indicators the model would mishandle. Open the discussion and compare against what happened, and against why the aggregate numbers above are misleading.

The 'chosen' answers:

  • The victim domain (context judgment). The model swept megacorp.example into the malicious list. Extraction requires reading comprehension of the indicator's role in the narrative, not regex shaped pattern spotting. An automated pipeline would have blocked the victim's own domain.
  • The weak host artifact (pkg.zip). The lowest value indicator was the miss. Generic file names sit at the boundary of "indicator the text presents as malicious," and models handle boundary judgments inconsistently.

Defensible alternative predictions: the defanged URL (convention handling is a classic miss, though this run caught it) and the line broken hash (token level fragmentation, Module 2, makes split strings genuinely risky). If you predicted either, your reasoning was sound; bring it to the lab and test it against your own model's live output.

The metrics lesson: 0.86 precision and 0.86 recall look strong, and the error analysis is what matters: the single false positive is the one that blocks the victim's domain, and the single miss is the least valuable item. Same arithmetic as Module 4, same conclusion: aggregate scores hide exactly the errors that hurt.

Reading STIX and TAXII

The sharing layer. (Structured Threat Information Expression), an OASIS standard, is the field's common JSON format for representing intelligence. (STIX Domain Objects) represent things: indicator, malware, , vulnerability, report, and others. (STIX Relationship Objects) connect them: this indicator indicates that malware. Indicators carry a pattern in STIX's pattern language. is the companion transport protocol: an HTTPS API for publishing and subscribing to STIX collections. The one sentence version: STIX is the envelope format, TAXII is the courier.

You'll read, critique, and complete STIX indicator templates, not build full bundles from scratch. The point is to see what "machine-readable and shareable" actually looks like, so interoperability means something concrete. Below is one of the accepted indicators from the extraction example, rendered as a STIX 2.1 indicator object. Hover or focus each annotated line:

1 { "type": "indicator", ⓘ
2 "spec_version": "2.1",
3 "id": "indicator--c4f1e2a8-0000-4000-8000-000000000001", ⓘ
4 "created": "2026-06-10T00:00:00.000Z", ⓘ
5 "modified": "2026-06-10T00:00:00.000Z",
6 "name": "Loader SHA-256",
7 "pattern": "[file:hashes.'SHA-256' = '9f86d081884c7d659a2feaa0c55ad015a3bf4f1b2b0b822cd15d6c15b0f00a08']", ⓘ
8 "pattern_type": "stix",
9 "valid_from": "2026-06-10T00:00:00.000Z" } ⓘ
Hover or tap an annotated line to unpack it.

A relationship object would then link this indicator to a malware SDO with relationship type "indicates." Read the anatomy: a typed object, a globally unique ID, timestamps, and a pattern a machine can match against file telemetry. That is what interoperability means: any STIX consuming system can ingest and act on this object without a human reading the report.

Watch out: four common misconceptions

"Extraction is mechanical, so the model can't really get it wrong." The victim domain trap shows otherwise: extraction requires comprehension of the indicator's role in the narrative.

"High precision means the pipeline is safe." Precision says nothing about misses. The blocklist question is always asked of both numbers.

"STIX is just JSON bureaucracy." The typed object and pattern are what let intelligence cross organizational boundaries without a phone call. The bureaucracy is the interoperability.

"Defanging is cosmetic." It is a safety control, and it is also the single most common cause of extraction misses. Treat it as a first class part of the task.

LLM extraction competes with and dedicated extraction tools. For rigidly formatted indicators (hashes, IPs), regex is faster, cheaper, deterministic, and auditable. The model earns its cost on context judgment (malicious vs victim vs merely mentioned) and on messy formats. Many production pipelines sensibly use both: regex proposes candidates, judgment filters them. Know what each layer contributes before trusting either. Extraction quality claims for any specific model are time bound; the evaluation method is what transfers. STIX coverage here is deliberately awareness level: real bundles involve identity objects, markings (including , which we cover in the verification methodology), versioning, and sighting flows that belong to a dedicated CTI course.
