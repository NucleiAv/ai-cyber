Driving Question

When a security tool (a rule-based parser, a machine learning classifier, or a language model) produces a parsed result or a triage recommendation, how do we know whether to trust its output?

1

The SOC and the Alert Volume Problem

Security teams face a challenge they cannot solve by working longer hours: their own detection tools generate more alerts than there is time to investigate. This module examines how analysts handle that volume, what tools help, and how we decide whether any tool's output deserves trust.

A aggregates feeds from every detection tool (firewalls, , endpoint protection, cloud services) into one operational view. How fast analysts can assess those alerts is the central bottleneck, and three practitioner numbers define it:

  • 1,000sof alerts per day at a mid-size organization
  • 40–50% rates reported in practitioner surveys (varies by tooling and tuning)
  • 15–30 minper genuine alert: read logs, check context, assess severity, decide whether to escalate

That gap drives the investment in triage tooling: SIEM correlation rules, automated playbooks, ML classifiers, and now language models. This module's question is not which tool is best in the abstract, but how to evaluate any tool's reliability in a specific operational context.

2

How Analysts Triage Alerts

is the analyst's first task when an alert appears, and it is more than a yes-or-no call: what happened, which asset, how severe, what response? It generally follows five stages:

  1. 1

    Collection

    Security tools detect events and forward alerts to a centralized system, typically a .

  2. 2

    Categorization

    Alerts are sorted by type (malware, unauthorized access, policy violation), source, and affected system.

  3. 3

    Prioritization

    Alerts are ranked by potential impact and urgency. Severity classification happens here.

  4. 4

    Investigation

    Analysts gather and analyze evidence to determine whether the alert is a genuine threat.

  5. 5

    Response

    Confirmed threats trigger action: containment, escalation, remediation, or documentation.

Tools Assist; Humans Decide

At every stage, automated scores and classifications (from a SIEM rule, an ML classifier, or a language model) are inputs to analyst judgment, not replacements for it. This principle anchors the whole module.

Security Log Formats

Security logs are the raw material of SOC work: every device and service produces them, describing what happened, when, and involving which addresses or accounts. The catch is that different sources use different formats, and format determines parsing difficulty for every tool. We will examine the three formats that appear most often.

Syslog (RFC 5424)

is one of the oldest and most widely adopted logging standards. Defined in RFC 5424, it specifies a message structure with a header and a free-form message body:

1<34>1?
22026-05-15T08:12:33.003Z?
3fw01.corp.example sshd 2048?
4- -?
5Failed password for admin from 10.0.14.55 port 44312 ssh2?
Hover or tap a segment to decode it. On the wire, this is one line.

CEF (Common Event Format)

was designed to solve the interoperability problem between security products and SIEMs. Unlike syslog's free-form message body, CEF provides a structured format with a fixed pipe-delimited header followed by key-value extension pairs with defined field names:

1CEF:0|?
2SecurityVendor|IDS|1.0|?
3100|Intrusion Detected|7|?
4src=10.0.0.1 dst=192.168.1.5 dpt=443?
5act=blocked msg=SQL injection attempt detected?
Hover or tap a segment to decode it. On the wire, this is one line.

CEF's advantage is that its field names are defined by the format specification, not by individual vendors. A parser looking for src= will find the source IP in any CEF entry, regardless of which product produced it. This consistency benefits every parsing tool, from simple scripts to SIEM normalization rules.

JSON (JavaScript Object Notation)

is an open data-interchange format, not a log standard. It uses named key-value pairs and nested objects, and is widely adopted by modern applications and cloud services for logging because its syntax is readable by both humans and machines: 

{
  "timestamp": "2026-05-15T08:15:44Z",
  "source_ip": "10.0.14.55",
  "dest_ip": "192.168.1.10",
  "event_type": "brute_force_attempt",
  "severity": "high",
  "details": "15 failed login attempts in 60 seconds",
  "service": "web_portal"
}

JSON's syntax makes the structure clear: every value is paired with a named key, and nested objects can represent complex events. However, the key names are chosen by whoever produces the log. JSON itself does not define what a source IP field should be called. One vendor might write "source_ip", another "src_ip", another "srcAddr". Without a (a separate specification defining which fields must appear and what they mean), different JSON logs can name the same concept differently.

This is an important distinction from CEF. CEF defines its field names as part of the format specification (e.g., src always means source IP). JSON defines only the syntax for expressing key-value pairs. The semantics (what the fields mean and what they are called) depend on the log producer or on an external schema.

Log Formats?

Syslog, CEF, and JSON are not the only formats in production; Windows Event Logs (EVTX), LEEF, W3C Extended Log Format, and many vendor-proprietary formats also appear. We focus on these three because they span the spectrum above. Carry that relationship between structure and parsing reliability into the next subsection.

4

How Logs Are Parsed in Practice

When a log message arrives at a SIEM or analysis platform, it must be parsed: the raw text is broken into individual fields (source IP, destination IP, port, severity, timestamp) so that analysts and automated rules can search, filter, and correlate across events.

Conventional Parsing Approaches

How a log gets parsed follows directly from where its format sits on the structure spectrum. Most major SIEM platforms ship built-in parsers for the common formats; teams write custom rules for organization-specific sources.

Format How it is parsed Reliability
CEF Split the header on pipes; read spec-defined key-value pairs from the extension Deterministic: identical results every time for the same input
JSON (known schema) Read the key-value structure directly, using the expected field names Reliable once configured for the producer's schema
Syslog body Vendor-specific , , or maintained by the SIEM administrator Breaks when a device or software version changes its message format; rules need ongoing upkeep

Two Tool Families, Compared

1

Conventional parsers

regex, grok, SIEM normalization rules

Strengths
Fast, deterministic, consistent. Handles defined delimiters and field names reliably at high volume.
Struggles with
Vendor variation in free-form bodies, formats that change between software versions, natural-language descriptions without field markers.
How it fails
Loudly and visibly: an unmatched pattern yields an unparsed field, not an invented one.
2

Language models

one additional approach, not a replacement

Strengths
Reads natural language, so it can sometimes extract fields from free-text bodies where regex would need per-vendor customization.
Struggles with
Speed and cost per entry; consistency, since repeated runs of the same input can produce different results.
How it fails
Fluently and invisibly: it may fabricate values not in the input or misclassify severity. This is why evaluation against ground truth (next subsection) is essential.

The question is not which parsing approach is universally best. It is which approach fits the specific format, volume, latency requirement, and risk tolerance of the operation, and how we verify that the output is correct.

5

Ground Truth: How We Evaluate Any Tool's Output

Whether we are evaluating a SIEM normalization rule, a regex parser, a machine learning classifier, a language model, or a human analyst's manual review, we need something to compare the output against. That something is : known-correct answers used as the reference standard for evaluation.

It is easy to skip this step. When any tool, not just a language model, produces a neatly formatted result, the output looks reasonable. The fields are labeled. The values seem plausible. But "the output looks reasonable" is not measurement. Without a known-correct reference, we cannot distinguish between a tool that extracts fields accurately and one that produces confident-looking but incorrect results.

Ground Truth Is Not Absolute Truth

Ground truth is the best available reference, not absolute truth. Even benchmark datasets contain labeling errors. We will see a specific example in Section 3 (CIC-IDS2017). Treat ground truth as the standard we measure against while remaining aware that the standard itself may have limitations.

In this module we build ground truth manually: read each entry, identify every field's correct value, record it, then compare tool outputs against it field by field. Slow, but it builds the judgment that automated metrics depend on. Precision, recall, and F1 arrive in later sections; they are only meaningful when the ground truth under them is sound.

Parsing a CEF Entry and Comparing Outputs

To make the evaluation process concrete, we will work through a single CEF log entry. Read it carefully and identify every field before looking at the parsed outputs below.

The CEF Entry

CEF:0|AcmeFW|Firewall|2.1|401|Denied Connection|8|src=172.16.5.22 dst=10.10.1.50 dpt=22 proto=TCP spt=51442 act=deny cs1Label=Reason cs1=Policy violation

What a Conventional CEF Parser Extracts

A conventional CEF parser handles this entry deterministically. It splits the header on pipe delimiters, reads the seven header fields, and extracts key-value pairs from the extension. Every correctly implemented parser will produce the same result:

Field Extracted Value Source
Severity8 (High)Header field 7; CEF scale 7-8 = High
Source IP172.16.5.22Extension: src=
Destination IP10.10.1.50Extension: dst=
Destination Port22Extension: dpt=
ProtocolTCPExtension: proto=
Source Port51442Extension: spt=
ActiondenyExtension: act=
ReasonPolicy violationExtension: cs1= (custom string 1)
Timestampnot presentNo timestamp field in this entry

Note the last row. The parser reports that no timestamp is present because the entry does not contain one. This is correct behavior: a deterministic parser extracts what exists and reports what is absent.

What a Language Model Produced

The same CEF entry above was given to a language model. The prompt asked the model to parse the entry and return the extracted fields as JSON (the JSON here is the model's response format, not a conversion of the log itself). The model returned: 

{
  "format": "CEF",
  "timestamp": "2026-05-15T10:30:00Z",
  "source_ip": "172.16.5.22",
  "destination_ip": "10.10.1.50",
  "destination_port": 22,
  "protocol": "TCP",
  "source_port": 51442,
  "action": "deny",
  "severity": "medium",
  "reason": "Policy violation",
  "summary": "Firewall denied a TCP connection from 172.16.5.22:51442 to 10.10.1.50:22 due to policy violation."
}

Analysis: Two Distinct Failure Types

Two errors appear in the language model's output. Understanding them as distinct failure types is important for evaluating any tool that uses a language model.

Failure Type 1: The Fabricated Timestamp (Hallucination)

The model generated a plausible-looking value for a field that does not exist in the input: a . This connects to the autoregressive generation process from Module 2: a plausible timestamp is statistically more likely than an explicit "not present" statement unless the prompt instructs otherwise. A conventional parser avoids this error entirely. In a SOC, a fabricated timestamp could misdirect an investigation by suggesting a false timeline.

Failure Type 2: The Severity Mapping Error

CEF severity 8 maps to High (7–8 = High on the 0–10 scale), but the model output "medium." Not a hallucination, but an incorrect mapping, perhaps from applying the wrong scale or defaulting to a conservative estimate. Operationally it matters: a "medium" rating might leave an alert sitting in queue while a "high" rating would trigger immediate investigation.

These two errors illustrate why comparing tool output against ground truth is essential. Both errors are invisible without a known-correct reference: the timestamp looks plausible, and "medium" is a valid severity label. Only the ground truth comparison reveals that one value was fabricated and the other was miscalibrated.
