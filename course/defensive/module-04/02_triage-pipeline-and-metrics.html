1

From Parsing to Triage: What Comes After Field Extraction

Section 1 parsed log entries into structured fields. Parsing serves a larger goal: decisions. Is this event malicious? How severe? What do we do? Within the five-stage process from Section 1, severity classification is the decision that determines what happens next: which alerts get immediate attention, which can wait, and which can be closed automatically.

Severity Classification as a SOC Concept

Every SOC maps alert content to an urgency level: a small set of categories with defined criteria that route alerts to the right response. The five-level scale below is our instructional model, adapted from common SOC conventions; real organizations tune the criteria to their own risk profile and regulatory environment.

Severity Criteria (Instructional Model)
Critical Active exploitation detected; data exfiltration in progress; critical system compromise
High Successful attack detected but impact not yet confirmed; privileged account compromise; malware execution
Medium Suspicious activity requiring investigation; policy violation; unusual but not confirmed malicious behavior
Low Minor policy violation; informational alert with low confidence; known false positive pattern
Informational System status messages; routine scanning; expected network behavior

Triage Severity vs. Log Severity

These triage severity levels are different from the severity values encoded in log formats. Syslog encodes severity 0 (Emergency) through 7 (Debug) as part of its priority value. CEF uses a 0-10 numeric scale. Triage severity is an operational judgment made about the alert after reviewing its content, not a value extracted from the log itself. We will see this distinction concretely in the worked example below.

How SOCs Automate Triage Today

Before we build an LLM-based pipeline, we need to understand what triage automation already looks like. SOCs do not process thousands of alerts manually. They use layered automation to handle volume, reserving human judgment for decisions that automated tools cannot make reliably.

Conventional Triage Automation

Approach How It Works Strengths Limitations
Boolean logic evaluated against incoming log fields. Example: IF source_ip IN watchlist AND dest_port = 443 AND byte_count > 10MB THEN severity = High Fast, deterministic, auditable; the same input always produces the same result Must be written and maintained for each pattern; cannot handle novel attack patterns not covered by existing rules
Multi-step workflows that chain automated actions: receive alert, query threat intelligence API, check asset inventory, assign to analyst queue. Example: "On Critical IDS alert, enrich with VirusTotal lookup, isolate host via EDR (endpoint detection and response) API, page on-call analyst" Consistent execution of complex procedures; reduces manual handoff errors between steps Only as good as the rules that trigger them; cannot adapt to scenarios not anticipated by the playbook author
Threshold-based routing Alerts above a severity threshold go to senior analysts; below the threshold go to automated closure or junior review Simple to implement; reduces analyst workload for low-severity alerts Depends entirely on the accuracy of the severity classification that feeds it
Analyst runbooks Documented step-by-step procedures for specific alert categories, followed by human analysts Captures organizational knowledge; handles edge cases through human judgment Slow; inconsistent across analysts; does not scale to high alert volumes

Each of these approaches is deterministic or human-guided: the same input produces the same routing decision (for rules and playbooks) or a documented decision process (for runbooks). They are the baseline against which any new approach, including LLM-based triage, should be evaluated.

Why the Baseline Matters

When we test an LLM-based pipeline later in this section, the question is not "does it work?" in isolation. It is: "how does it compare to what a SIEM rule, a SOAR playbook, or an experienced analyst would produce for the same alerts?" Without a baseline, we cannot answer that.

3

An LLM-Based Triage Pipeline

With the baseline established, here is one instructional model of LLM-based triage (not the only design, and not automatically better than the automation above). Its core principle is task decomposition: instead of one prompt that parses, classifies, enriches, and summarizes all at once, four focused steps, each with a defined input and output, so each can be validated and debugged independently.

A

Parse

Convert the raw alert from its native format (syslog, CEF, or JSON) into a standardized JSON structure. This step extracts only the fields present in the source entry. It should not generate summaries, interpretations, or values that are not in the original log. Conventional parsers handle this step deterministically; using an LLM here introduces the risk of fabricated fields.

B

Classify Severity

Given the parsed alert, classify it into one of the five severity levels from our instructional model. The classification criteria must be included explicitly in the prompt. Unlike a SIEM rule (which encodes criteria as conditions) or a trained ML classifier (which learns patterns from labeled data), an LLM must receive classification criteria as text instructions. It cannot infer an organization's severity definitions from context.

C

Enrich (Critical and High Only)

For alerts classified as Critical or High, generate an enrichment summary: what asset is affected, what attack technique does this alert resemble (using terminology where possible), and what should the analyst investigate next. This step produces generated text, not extracted data, and must be validated against authoritative sources before anyone acts on it.

D

Generate Shift Handoff

After processing all alerts in a batch, produce a summary document grouping alerts by severity, highlighting top priorities, and noting patterns. This is generated text intended as a starting point for a team lead reviewing the shift, not a finished operational report.

Each step takes the previous step's output as input. If severity classifications are wrong, we know the problem is in Step B's prompt or criteria, not buried in a combined prompt that handles everything at once.

A Key Difference from Conventional Pipelines

Conventional triage pipelines (SIEM rules, SOAR playbooks) execute deterministic steps: rule evaluation, API calls, database lookups. The same input always produces the same output. An LLM pipeline introduces stochastic (probabilistic) generation at each step. This means a subtly wrong classification in Step B may not be obviously wrong, but it will affect every downstream step. It also means running the same alert through the pipeline twice may produce slightly different results unless the model's is set to zero.

Prompt Structure and Classification Consistency

Some models support a dedicated that separates behavioral instructions ("classify severity using these criteria") from the log entry itself, helping criteria stay stable across many entries. Models without it may need instructions repeated in each prompt. Either way, test whether your classification prompts produce consistent results across varied inputs with the specific model you use.

Tracing One Alert Through the Pipeline

To see how the pipeline handles a real alert, we will trace a single IDS alert through all four steps, then examine what worked and what requires validation.

The Raw Alert (Syslog Format)

<38>1 2026-05-15T03:22:17Z idsensor01 suricata 5501 - - [1:2024897:3] ET MALWARE Win32/Agent.UNK CnC Beacon [Classification: A Network Trojan was detected] [Priority: 1] {TCP} 192.168.4.100:49152 -> 45.33.22.11:443

Decoding the Syslog Header

Before feeding this alert to any tool, we can decode the syslog header using the formula from Section 1. The priority value <38> encodes two pieces of information: facility and severity, combined as facility x 8 + severity. Here, 38 = 4 x 8 + 6, giving us facility 4 (security/authorization) and severity 6 (Informational).

This is worth pausing on. The syslog severity is Informational (level 6), because that is the level chose when generating the message. But the alert content describes C&C beaconing from an internal host, one of the most serious findings a SOC can encounter, and Step B will classify it as Critical. The two values answer different questions: syslog severity reflects the application's logging level at generation time; triage severity reflects operational impact assessed during investigation.

Step A Output: Parsed Fields

{
  "timestamp": "2026-05-15T03:22:17Z",
  "hostname": "idsensor01",
  "application": "suricata",
  "pid": 5501,
  "source_ip": "192.168.4.100",
  "source_port": 49152,
  "dest_ip": "45.33.22.11",
  "dest_port": 443,
  "protocol": "TCP",
  "suricata_sid": "1:2024897:3",
  "suricata_msg": "ET MALWARE Win32/Agent.UNK CnC Beacon",
  "suricata_classification": "A Network Trojan was detected",
  "suricata_priority": 1,
  "syslog_facility": 4,
  "syslog_severity": 6,
  "raw_format": "syslog"
}

Notice that Step A extracts only fields present in the source entry: the timestamp, hostnames, ports, and Suricata rule metadata all appear verbatim in the raw syslog message. The only non-verbatim field is raw_format, which is pipeline metadata indicating the source format. There is no natural-language summary or interpretation. Parsing and generation are separate tasks: Step A is extraction; Steps C and D are generation.

Step B Output: Severity Classification

Severity: Critical. Rationale: IDS rule match for known C&C beaconing behavior; internal host communicating with external C&C server; indicates active compromise. This matches the Critical criteria from our severity table: "active exploitation detected" and "critical system compromise."

Step C Output: Enrichment (Generated Text)

  • Affected asset: 192.168.4.100 (internal host; verify hostname and user assignment in asset inventory).
  • Attack technique: Command and Control (MITRE ATT&CK , Application Layer Protocol).
  • Recommended investigation steps: Isolate 192.168.4.100 from the network; check for from this host; preserve memory and disk for forensic analysis; block 45.33.22.11 at the perimeter firewall.

What Worked and What Requires Validation

Step Verdict The honest comparison
A · Parse Correct Suricata's syslog output is well structured; a regex, grok pattern, or SIEM rule would produce the same result deterministically.
B · Classify Correct C&C beaconing matches our Critical criteria. A SIEM correlation rule could reach the same verdict by matching the signature ID; the LLM got there by text interpretation instead.
C · Enrich Useful, but unverified Output a rule-based system typically cannot produce. But the LLM does not know whether 192.168.4.100 is a workstation, a domain controller, or a printer, or what our IR procedures are. A starting point, not a response plan.

Validating the ATT&CK Mapping

The LLM cited T1071 (Application Layer Protocol). We can verify this: search T1071 in the ATT&CK Navigator and check whether C&C beaconing over TCP port 443 matches the documented sub-technique T1071.001 (Web Protocols). If it does, the mapping adds real context for the analyst. If it does not, the LLM has generated a plausible but incorrect technique reference, a framework citation that could misdirect an investigation. This is what validation means in practice: verify every claim against an authoritative source before acting on it.

Evaluating Any Classifier: Confusion Matrices and Metrics

Any system that produces categorical labels is a . A SIEM rule that labels alerts as "Critical" or "Low" is a classifier. A trained ML model that predicts "malicious" or "benign" is a classifier. An LLM that assigns severity levels is a classifier. A human analyst making triage decisions is also a classifier, albeit a slow and expensive one.

Module 1 introduced , precision, recall, and F1; we reuse those tools here rather than re-teach them. They apply regardless of what produced the classifications: the metrics measure whether the output is correct, not how it was generated. What this module adds is the triage-specific reading of those numbers.

To apply this framework, we need two things: the system's classifications (from whatever tool we are evaluating) and (from expert review or a verified answer key). With these, we can build a confusion matrix.

Binary Simplification

For practical purposes in this section, we simplify the five severity levels to a binary classification:

  • Actionable = Critical + High (requires immediate analyst attention)
  • Non-actionable = Medium + Low + Informational (can be deferred or closed)

This reduces a 5x5 multi-class confusion matrix to a 2x2 binary matrix, which is easier to calculate and interpret while preserving the core question: did the system correctly identify which alerts need immediate attention?

The 2x2 Matrix, Applied to Triage

This is the same matrix from Module 1, with new labels: the classes are triage decisions, and each cell is a use (or waste) of one of the day's investigation slots.

Actually Actionable Actually Non-actionable
Triaged Actionable True Positive (TP)Flagged for investigation, was a genuine threat. An investigation slot well spent. False Positive (FP)Flagged for investigation, was benign: a that burns a slot an analyst could have spent on a real threat.
Triaged Non-actionable False Negative (FN)Deprioritized, was a genuine threat: a that may never be investigated. The worst case. True Negative (TN)Deprioritized, was benign. Correct silence; no analyst time spent.

Formula Recap from Module 1 (No New Math)

Precision = TP / (TP + FP): of what we flagged, how much was real? Recall = TP / (TP + FN): of what was real, how much did we catch? F1 = the harmonic mean of the two. Module 1, Section 5 derives all three with a worked example; revisit it if the formulas feel rusty.

What is new in this module is not the formulas; it is what they mean when the classifier is a triage gate and the unit of cost is an analyst's investigation slot. F1 in particular hides exactly the information a SOC manager needs: precision and recall must be read separately to make staffing and workflow decisions.

Interpreting Metrics in SOC Context

Suppose a triage system produces precision = 0.40 and recall = 0.90. What does this mean operationally?

Recall of 0.90 means only 10% of real attacks slip through. That sounds good. But precision of 0.40 means that of every 10 alerts marked actionable, only 4 are real threats; analysts must investigate and dismiss the other 6.

Is this acceptable? It depends on the SOC. A 20-analyst team might tolerate the false-alarm load to keep recall high. A 3-analyst team cannot waste 60% of its investigation time and would trade some recall for higher precision. The tradeoff applies identically whether the system is a SIEM rule, an ML classifier, or an LLM.

This Is an Organizational Decision

The precision-recall tradeoff is not a technical question with a single correct answer. It is an organizational decision about risk tolerance, staffing, and the cost of missed detections versus wasted investigation time. When presenting metrics to a SOC manager, present precision and recall separately (not just F1) so the manager can make an informed staffing and workflow decision. We will explore this tradeoff further in Section 4 when we examine ROC curves.

Evaluating Deterministic vs. Stochastic Classifiers

A deterministic classifier (a SIEM rule, a trained ML model at inference time) produces the same output every time for the same input, so a single evaluation pass is definitive. An LLM may produce different classifications on repeated runs due to sampling variability. Evaluation of LLM classifiers should either use = 0 for reproducibility or include multiple runs to characterize variance. This is a practical consideration when designing evaluation procedures.

Where LLM-Based Triage Fails

Every approach fails somewhere: rules miss novel attacks, ML classifiers degrade as traffic evolves (), and humans suffer . Knowing how a tool fails is a prerequisite for deploying it safely. The five cards below are the failure modes specific to LLM-based triage, where a wrong answer means missed attacks, wasted investigation time, or disrupted services rather than just a bad summary.

Failure Mode 1: Hallucinated Indicators of Compromise

The LLM generates an IP address, domain name, file hash, or identifier that does not exist in the source log entry. We saw this in the Section 1 worked example: the model invented a timestamp for a CEF entry that had none. In a triage context, an analyst who acts on a might block a legitimate IP address, investigate a non-existent domain, or search for a file hash that was never on the network, wasting time and potentially disrupting operations.

Failure Mode 2: Severity Inflation

The LLM classifies a routine event as high-severity because the log text contains words that superficially resemble attack indicators. Keyword-triggered false positives are a well-known problem across many tools: a SIEM rule matching "port scan" without context will also fire on legitimate vulnerability scanners. The LLM-specific variant is that there is no explicit rule to inspect or tune. When a SIEM rule produces false positives, an analyst can read the rule logic and adjust the threshold or add an exception. When an LLM inflates severity, the reasoning is opaque, making the trigger harder to diagnose and correct.

Failure Mode 3: Severity Deflation

The LLM classifies a genuine threat as low-severity because the malicious activity does not match the patterns it has seen in training data. This can be the most consequential failure mode in contexts where the LLM serves as the primary triage gate, because it causes real attacks to be deprioritized or ignored entirely. Unlike severity inflation (which wastes time but still surfaces the alert for review), severity deflation means the alert may never be investigated. In SOCs with secondary review processes or bypass rules, the risk is reduced, but not eliminated.

Failure Mode 4: Context Fabrication

The LLM generates a plausible-sounding attack narrative around a benign event. For example, given a log entry showing a DNS query to a legitimate content delivery network, the LLM might construct a story about "potential to exfiltrate data," complete with a detailed explanation of how DNS tunneling works. The explanation may be technically accurate about DNS tunneling in general, but the specific log entry shows no evidence of it. An analyst who reads this confident narrative without checking the raw data might initiate an unnecessary investigation.

Failure Mode 5: Knowledge-Cutoff Blind Spots

The LLM cannot recognize attack patterns, malware families, or CVEs that emerged after its training data cutoff. If a new command-and-control framework becomes prevalent six months after the model was trained, the LLM may classify its traffic patterns as benign because it has never seen them described as malicious. This failure mode is inherent to all LLMs and cannot be resolved by better prompting; it requires model updates or augmentation with external, up-to-date threat intelligence feeds.

About This Failure Taxonomy

These five categories are an instructional taxonomy organized for this course, drawing on published research into LLM hallucinations in cybersecurity contexts (see references page). They are not a formal industry standard. Published research on LLM failure modes in security is still evolving.

When Triage Fails: A DNS Beaconing Scenario

This scenario shows how severity deflation and context fabrication combine to produce a dangerous triage failure.

An LLM-based triage system processes overnight alerts. Among them is a set of DNS query logs from an internal workstation to a newly registered domain, enriched with domain registration metadata showing the domain was created 48 hours earlier. The queries occur every 5 to 7 minutes with small, consistent data payloads, a pattern consistent with .

LLM Classification: "Low: routine DNS traffic. The queried domain appears to be a recently registered content delivery endpoint. No malicious indicators detected."

The LLM's explanation is confident and specific. It notes the domain's recent registration (correctly, from the enrichment data) but interprets it as benign (a new CDN endpoint) rather than suspicious (a newly registered C2 domain). It does not flag the timing of the queries. The model reads one query every 5 to 7 minutes as a low, ordinary rate and does not register that the interval stays within that narrow range for hours.

Twelve hours later, the incident response team discovers that the workstation was compromised. The DNS queries were C2 beaconing, and the attacker used the same channel to exfiltrate a set of stored credentials.

Why did the LLM fail? What should have prevented this outcome?

Why did the LLM fail? Three factors converged:

  • Knowledge-cutoff blind spot. The C2 framework was newer than the model's training data. The LLM had no examples of this specific beaconing pattern labeled as malicious.
  • Severity deflation. The LLM treated the query rate as the relevant signal. One query every 5 to 7 minutes is a modest rate, and the model's training examples of C2 beaconing may have featured higher-frequency traffic, so it classified the activity as routine. Rate is weak evidence in either direction: C2 operators routinely lengthen the sleep interval between beacons and add random variation to it (jitter) to stay below frequency thresholds. Beacon detection looks at regularity instead. In this scenario the interval stayed within a two-minute window for hours and the payloads were small and consistent, which is the pattern that should have been flagged.
  • Context fabrication. The model generated a plausible alternative explanation (CDN endpoint) and presented it with high confidence. It constructed a benign narrative rather than flagging uncertainty.

What should have prevented this? An architectural control: a deterministic rule that flags any communication with domains registered within the last 72 hours for mandatory analyst review, regardless of the LLM's classification. The lesson is architectural: the pipeline must include bypass rules that route high-signal alerts (newly registered domains, unusual DNS patterns, known C2 indicators) around the LLM entirely. An LLM is useful for bulk triage of ambiguous alerts, but it should not override signals that rule-based or statistical checks catch more reliably.

When Query Volume Does Matter

Query rate is weak evidence for C2 beaconing, but it is a useful signal for DNS tunneling used to move large amounts of data. Each DNS query can carry only a small payload, at most a few hundred bytes encoded in the queried name. In this scenario, roughly ten queries per hour over twelve hours carries at most tens of kilobytes, which is enough for credentials or encryption keys but not for a database or a document archive. Exfiltrating larger amounts of data through DNS requires a much faster query rate, often hundreds or thousands of queries per minute, and traffic at that volume is itself a detectable anomaly.

Documenting How Tools Fail

We have now examined five failure categories. A professional skill that applies across all security tooling (not just LLMs) is systematically documenting how a tool fails in your specific environment. For any tool you evaluate, record:

  • Input: the exact data provided to the tool.
  • Output: what the tool produced.
  • Error: why the output is wrong, with evidence from authoritative sources.
  • Category: which failure mode it belongs to.
  • Impact: what would happen if an analyst acted on this output.
  • Prevention: how the failure could be caught or prevented architecturally.

This is not a gotcha exercise; it is how security teams deploy tools safely.
