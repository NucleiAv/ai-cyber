1

One Flow, End to End: Classifying a Brute-Force SSH Burst

We now trace one detection from raw input to validated conclusion, using the same six-step pattern we will reuse for every example in this module: input, task, expected output, interpretation, failure mode, validation. The connection is the SSH flow from Section 3, part 3, except now it appears 87 times in one minute.

1

Original input: one flow record

The input format is a flow record conforming to the UNSW-NB15 feature schema: one row of named numeric fields per connection. No payload, no packets, no log text. Shown here in key-value form:

proto=tcp  dur=0.08  spkts=6  dpkts=5
sbytes=1240  dbytes=980  sttl=62  dttl=64
sinpkt=2.1  sjit=0.4
ct_srv_src=87  ct_dst_sport_ltm=3  ct_srv_dst=87
2

Task

Binary classification: label this flow attack or benign. The is a Random Forest trained on labeled flows from this schema. Same task shape as Section 2's severity labeling, different input and different machinery.

3

Expected output: a label and a score

The output representation is a categorical label plus a confidence score. Here it is serialized as JSON because that is what this pipeline's downstream tooling consumes; the same result could be a CSV row or a syslog message. The format is a pipeline choice, not a property of the model:

{"flow_id": "f-83120", "label": "attack", "score": 0.93}
4

Correct interpretation: why these numbers say brute-force

Four features carry the signal. ct_srv_src=87: the same source has hit the same service 87 times in the recent window; this is the defining brute-force fingerprint. dur=0.08: each connection is brief, consistent with a login attempt that is rejected immediately. sinpkt=2.1: packets arrive milliseconds apart, machine speed, not typing speed. dpkts=5: the server sends the same small rejection every time. Each value matches the analyst knowledge encoded in the schema table in Section 3, part 3.

5

Possible failure: the uptime monitor

Now the same flow statistics arrive from a different source IP. Short connections to port 22, rapid intervals, dozens per window, small identical responses. The classifier outputs attack, 0.91. The source is the operations team's uptime monitor, probing the server every few seconds to confirm it is alive. Flow features describe shape, and the shapes are nearly identical. The model is not malfunctioning; it is answering the only question the features let it answer.

6

Validation: a second, independent evidence source

The classifier's verdict is a claim, and claims get checked against . Ground truth here is not an ML concept or an LLM concept; it is the general principle from Section 1 that any tool's output is evaluated against independently verified evidence. For an SSH brute-force claim, the independent source is the server's own authentication log. The real attacker's window shows thousands of Failed password entries for changing usernames. The uptime monitor's window shows no authentication attempts at all: it connects, reads the banner, and leaves. Same flow shape, opposite verdicts, and only the second evidence source can tell them apart.

Pattern Practice: Exfiltration and Floods Through the Feature Lens

Now you apply the same six-step pattern yourself, on two harder cases. For each scenario: identify the 3 or 4 schema features that carry the signal, name what the flow view cannot see, and propose a validation source before revealing the guided analysis. Work from the feature table in Section 3, part 3.

Scenario A: Low-and-Slow Data Exfiltration. An insider slowly copies 500 MB of data to an external server over 6 hours using encrypted HTTPS connections.

Which features carry the signal? Which feature in the table looks relevant but is actually useless here, and why? How would you validate?

Signal-carrying features:

  • sbytes high with dbytes low: the defining mark of exfiltration is asymmetry. Data leaves; little comes back. Either number alone is ambiguous, the ratio is the signal.
  • dur: hours-long or persistently repeated connections to one external host sit far outside normal browsing behavior.
  • sjit low: a scripted copy pushes data at machine-steady intervals; human-driven traffic is burstier.

The trap: ct_flw_http_mthd looks tailor-made for catching upload-heavy POST traffic, but the scenario says HTTPS. HTTP methods live inside the encrypted channel, so the extractor cannot see them and the feature stays at zero. A feature can be well designed and still be blind in context. Knowing which features go dark under encryption is part of reading any feature schema.

What the flow view cannot see: file names, file contents, and whether the data was sensitive. A nightly cloud backup produces nearly the same flow shape. This is among the hardest detection problems in network security precisely because the shape is legitimate-looking.

Validation: pivot to independent sources. Proxy or egress firewall logs identify the destination and certificate; endpoint logs show which process read which files in that window; data-loss-prevention tools, where deployed, log what left. The flow record raises the question. It cannot answer it.

Scenario B: Volumetric Flood. A botnet directs a attack at a web server: 10 Gbps of traffic from thousands of sources.

Which features light up? What does the windowed connection count actually measure here, and what does it not measure? How would you validate?

Signal-carrying features:

  • spkts and sbytes: extreme packet and byte volume is the defining characteristic of a volumetric flood. These two features alone separate it from almost everything else.
  • sinpkt near zero: flood sources emit packets as fast as the link allows. Near-zero source inter-packet time at sustained volume is machine-generated traffic by definition.
  • ct_srv_dst spiking: every flood flow targets the same service on the same host, so the count of recent connections sharing that service and destination climbs sharply.

Read the windowed count carefully: ct_srv_dst counts connections converging on one service at one destination. It does not count how many distinct sources they came from. The convergence pattern is the same whether one host or ten thousand hosts produce it, so this feature alone cannot distinguish a distributed flood from a single broken client retrying in a loop. Source-diversity questions need source-counting evidence.

What the flow view cannot see: whether the source addresses are real. UDP floods routinely spoof source IPs, and the flow record stores the spoofed value at face value. Blocking the listed sources may block nobody at all.

Validation: server-side connection state and service health confirm real impact; upstream flow data from the ISP or border router shows whether the traffic pattern exists beyond our edge and from how many true paths. Spoofing means our own records cannot settle the question alone; the independent vantage point can.

One pattern to carry forward from both scenarios and the worked example: in every case, the flow features raised a question, a limit of the feature view obscured the answer, and an independent evidence source resolved it. The summary grid below makes the division of labor visible.

Why Detectors Go Stale: Concept Drift and the Retraining Bill

Everything so far described a detector at a single moment. Networks do not hold still. New applications appear, users change habits, infrastructure gets rebuilt, and attackers adapt on purpose. An ML model, trained on history, degrades as the present drifts away from that history. This is , and in network security it is not an edge case; it is the operating condition.

The UNSW-NB15 traffic we have been using makes the point by its age alone. It was generated in 2015, before TLS 1.3 became the default, before cloud-native services made API-to-API traffic dominant, and before IoT devices added entirely new traffic profiles. A model trained on it meets a modern network as a stranger. The same aging happens, more slowly, to every model trained on any network's past.

The decay curve has a price tag. Each recovery step requires collecting current traffic, labeling it, validating the new model, and redeploying. Labeling is the expensive part: it needs experienced analysts, the same people already handling the alert queue and managing . Organizations that budget for the model but not for this recurring loop end up with the left side of the curve in their procurement deck and the right side in production.

Reading Benchmark Claims: UNSW-NB15 and CIC-IDS2017

Detection research, and detection marketing, runs on benchmark numbers. The two datasets behind most of those numbers are UNSW-NB15 and CIC-IDS2017, and knowing how each was built is what lets us read a claimed score critically instead of taking it at face value. The full citations and dataset statistics live on the References page; here we compare what matters for interpretation.

1

UNSW-NB15

UNSW Sydney, 2015

How it was built
Testbed traffic generated with the IXIA PerfectStorm tool: normal activity mixed with synthetic attacks, captured in two sessions of 16 and 15 hours.
Size and structure
About 2.54 million flow records, 49 features, 9 attack categories, plus raw PCAP files.
Known limits
Traffic predates TLS 1.3, cloud-native patterns, and IoT. Attacks are tool-generated, not captured from real adversaries. Some records carry ambiguous labels.
Question to ask of any score
Which attack categories, which train/test split, and how would this transfer beyond 2015 traffic?
2

CIC-IDS2017

Canadian Institute for Cybersecurity, 2017

How it was built
Five days of testbed traffic with realistic user profiles and 7 attack scenarios, designed to improve on older benchmarks.
Size and structure
Millions of flow records; roughly 80% benign, 20% attack across the full dataset, a strong .
Known limits
A 2021 analysis by Engelen and colleagues found that the feature extraction tool miscalculated many features and that improper TCP session handling produced contradictorily labeled flows. The errors carry into the successor dataset CSE-CIC-IDS2018.
Question to ask of any score
Original or corrected feature set? And is accuracy doing the talking where precision and recall should be?

The class imbalance deserves a picture, because it is the single most common way benchmark numbers mislead.

So when a paper or product sheet reports a high accuracy figure on CIC-IDS2017, we have a checklist rather than an impression. Did the authors report precision and recall per class, or accuracy alone against an 80% head start? Did they use the corrected feature set, or the original extraction with known errors? Was the test set held out from tuning? The deeper lesson generalizes: benchmarks are complex artifacts that can carry undetected errors for years, and results built on them inherit those errors. The critical stance we practiced on LLM output in Module 3 applies to the research literature too.

Choosing a Detector the Clinic Can Run

We close with the decision this section has been preparing for. A small healthcare organization, a clinic network with patient records, has a two-person security team, no budget for ongoing model retraining, and a regulatory obligation to detect and report intrusions, with as the threat that keeps its leadership up at night. Which approach from Section 3, part 4 should be its primary IDS?

Reason through the constraints before revealing our analysis. The grid from part 4 is your map; the constraints below are the territory.

Constraint Rule-based Supervised ML Unsupervised anomaly
Two analysts' worth of alert capacity Favorable: low, tunable false positive volume Workable, if the model stays current Unfavorable: highest false alarm budget
No retraining budget Favorable: rule updates come with the subscription Unfavorable: staleness is structural (part 7) Partially unfavorable: baselines still need upkeep
Regulatory detection floor Favorable: interpretable, auditable alerts Conditional: explainability varies Unfavorable: "anomalous" is hard to audit

Decision task. Choose a primary approach, name the tradeoff you are accepting, and answer one more question: what evidence, six months from now, would tell you that you chose wrong?

A defensible choice: rule-based detection (Suricata or Snort with a maintained ruleset) as the primary IDS. Every constraint row favors it: the false positive volume fits two analysts, the maintenance burden is outsourced to the ruleset publisher, and each alert is auditable because the rule is the explanation.

The accepted tradeoff: blindness to novel attacks. The clinic is betting that the threats it faces, commodity ransomware and known exploit kits, are exactly the well-signatured kind, and that bet is reasonable for its profile. It is still a bet.

The six-month test: the choice may need re-evaluation if evidence shows attacks arriving that rules cannot see: an incident discovered through some other channel (a user report, an audit) that the IDS never flagged, or threat intelligence showing the clinic's sector targeted by novel techniques. The choice is also failing if the team cannot keep up with even the rule-based alert volume. Tool choices are claims about the future; like every claim in this section, they get validated against evidence, on a schedule, not assumed true because they were reasonable once.

There is no single correct answer. A different organization, with a data science team and a tolerance for false positives, defensibly chooses differently. The method is the lesson: constraints first, grid second, named tradeoff, scheduled validation.

Where the LLM Sits on This Bench

Notice what never came up as an option: using an LLM as the detector. The latency budget from Section 3, part 1 rules it out at stage 2. Where LLM assistance plausibly earns a place is downstream, in Sections 1 and 2 territory: drafting explanations of alerts already raised, helping with , summarizing an investigation for the regulator's report. Each of those uses inherits every validation obligation we established there. Section 4 takes up that comparison directly.

The Grounded Takeaway

Detection tools differ in what they learn from, what they can see, and what they cost to keep honest. Rules see what humans wrote down. Supervised models see what the labels taught. Anomaly detectors see deviation, not malice. LLMs read text downstream of all of them. None is automatically better; each is a different bet about where the evidence will be. Our job, here is to know which bet we are making, name the tradeoff out loud, and check the bet against independent evidence on a schedule.
