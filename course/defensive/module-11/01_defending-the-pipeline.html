The Practitioner's Problem

We spent two modules cataloging attacks. Prompt injection exploits the missing boundary between instructions and data in the context window. Poisoning corrupts training data; evasion fools classifiers at inference time. Supply chain attacks compromise the components a system depends on, and excessive agency lets systems act beyond their intended scope.

Every one of those attacks traces back to the same root vulnerability: the collapsed instruction/data boundary. An LLM cannot structurally tell "follow this instruction" apart from "here is some text to process." There is no hardware boundary, no type system, no memory protection ring between the two. That separation vanished the moment we started processing arbitrary user input alongside system instructions in the same context window.

Nobody knows how to restore it. This is not a bug waiting for a patch. It is an architectural property of how large language models work. Researchers have tried delimiter tokens, fine-tuned instruction hierarchy models, and formal verification methods. Some reduce attack success rates; none create a real boundary.

The practitioner's question, then, is not "how do we solve this?" but "given that the root cause persists, how do we reduce risk enough to justify deployment?" The approach is the same one network security arrived at decades ago: defense-in-depth.

Defense-in-Depth for LLM Applications

: stack multiple independent controls so that no single bypass compromises the system. We applied the same principle to code review earlier in the course, layering five defenses so a vulnerability missed by one tool might be caught by another. For LLM applications, the stack has six layers: , , privilege separation, , monitoring, and human-in-the-loop review. Each layer is imperfect on its own. The strategy works because the layers fail independently.

"Fail independently" is the key phrase in that definition. If two layers share the same blind spot, one attack bypasses both. Two keyword filters are not defense-in-depth; they are the same defense repeated. A keyword filter plus a model-based classifier plus a rate limiter is defense-in-depth, because the three fail for different reasons: the keyword filter misses encoded inputs, the classifier misses novel patterns, and the rate limiter misses slow, patient attackers. An attack would need to evade all three at once.

This maps directly to the network security concepts we already know. A perimeter firewall, an intrusion detection system on internal segments, endpoint monitoring on each host, and an incident response process for when everything else fails: four layers, each catching threats the others miss. The LLM defense stack follows the same logic on a different threat surface.

Deterministic versus probabilistic controls

Not all controls fail the same way, and how a control fails tells us what role it should play in the stack.

Deterministic

A blocking any user who exceeds 100 requests per minute produces the same outcome every time. Request 101 is rejected whether it is benign, malicious, or written in Klingon. The decision rests on a countable, unambiguous property (request count) rather than on interpreting meaning.

Probabilistic

A classifier-based guardrail that detects jailbreak attempts produces a variable outcome. It may or may not flag a given input depending on how similar that input is to its training data. Change the wording, encode the payload differently, or switch languages, and the result changes. The decision boundary can be probed and gamed.

This distinction gives us a vocabulary for the rest of the module. It is not about quality; both types are useful. It is about what kind of guarantee each one provides.
Behavior Same result every time Results vary with input distribution
Examples Rate limiters, sandbox execution, privilege enforcement, allow-lists, structured output validation Classifier-based guardrails, LLM-as-judge review, safety training, content-based filtering
Network analogy Firewall: block or allow by rule : classify traffic patterns, may miss novel attacks
Guarantee Hard floor that no prompting can bypass Reduces frequency of successful attacks

Nobody builds a network with only a firewall or only an ; effective defense uses both. A guardrail classifier catches automated abuse and casual jailbreak attempts, and that has real value. But when consequential actions are at stake, at least one deterministic control should stand between the model's output and the real world. No amount of clever prompting can bypass a permission that was never granted.

Misconception: "Probabilistic" Does Not Mean "Unreliable"

Probabilistic controls reduce attack success rates against non-adaptive adversaries, which covers most real-world abuse. The problem is relying on them alone for consequential decisions. Two keyword filters are not defense-in-depth; a keyword filter plus a model-based classifier plus a rate limiter is. The layers must be independent and heterogeneous.

Input Validation and Output Filtering

Input validation: the pre-model defense layer

Input validation controls what reaches the model. It is the first layer an attacker's prompt encounters, and the simplest version, a keyword filter blocking known jailbreak phrases, is also the least effective.

A keyword filter that blocks "ignore your instructions" operates on exact string matching. An attacker who knows the filter exists (and we should always assume they do) can encode the same phrase in Base64: aWdub3JlIHlvdXIgaW5zdHJ1Y3Rpb25z. Or substitute Unicode lookalike characters: "ign0re y0ur instruct1ons." Or rephrase entirely: "disregard the above directives." Or split the phrase across multiple messages. String matching operates in one representation space; language meaning lives in another. The attacker can always find an input that means the same thing to the model but looks different to the filter.

Effective input validation works in layers, each operating on a different representation:

  1. 1

    Encoding-aware fuzzy matching

    Catches character substitutions, Unicode tricks, and common encoding schemes by normalizing the input before comparison rather than matching raw strings.

  2. 2

    ML-powered classifiers

    Small, specialized classifiers detect injection patterns in embedding space rather than string space. Many are compact enough to run on a CPU alongside the main application, catching semantic variations that string matching misses. The trade-off: they are probabilistic and may miss novel patterns absent from their training data.

  3. 3

    Token budgeting

    Caps the number of tokens a single request can consume, preventing resource abuse and limiting the space available for complex injection payloads.

  4. 4

    Prompt delineation markers

    Structured tags separate user input from system instructions, making it easier for the model to tell data from directives. This is a soft defense, not a structural boundary, but it raises the difficulty of injection.

Each technique catches threats the others miss, which is why input validation is a layer, not a single tool.

Output filtering: the post-model defense layer

Input validation tries to stop bad prompts from reaching the model. Output filtering addresses the opposite side: the model has already produced a response, and we need to decide whether that response is safe to deliver to the user or a downstream system.

The operating principle: treat all LLM output as untrusted. This is the OWASP LLM05 principle. The model is a source of content, not an authority. Its output can contain harmful material the model was tricked into generating, leaked data from the training set or retrieval corpus, or injection payloads targeting downstream systems. A model that outputs JavaScript into a web page, or SQL into a database query, is a concrete example of each.

This connects directly to traditional web security. If an LLM's output is rendered in a browser without sanitization, a successful prompt injection can produce a cross-site scripting (XSS) payload. Interpolated into a SQL query, it can produce SQL injection. The LLM becomes a vector for attacks that predate it by decades. Output encoding and structured format validation are the same defenses web applications have needed since the early 2000s.

Output filtering modeHow it worksDeterministic?
Classifier-based content filtering Scans responses for policy violations, harmful content, or leaked sensitive information No. Catches known categories but probabilistic.
LLM-as-judge review A second model evaluates the first model's output for policy compliance No. More nuanced than a classifier but slower, and the judge model can be wrong.
Structured format validation Enforces that output conforms to a defined schema (JSON fields, allowed values, expected types) Yes. If the output does not match the schema, it is rejected regardless of content.
Output encoding Sanitizes the model's response before it reaches downstream systems like databases, APIs, or web pages Yes. Analogous to encoding user input before inserting it into HTML.

Least privilege for AI systems

Privilege separation is a deterministic control. OWASP identifies three sub-dimensions of that we studied in the attacks module: excessive functionality (the system has tools it does not need), excessive permissions (the system has broader access than its task requires), and excessive autonomy (the system acts without human approval on consequential actions).

Applying least privilege means three concrete steps: remove tools the application does not use, restrict each tool's permissions to the minimum scope, and require human approval for high-impact actions. These are architectural decisions made before deployment, not runtime classifiers. No prompt injection can grant the model access to a tool that was never connected.

Consider a customer support chatbot that needs to look up order status and product information. It does not need to modify orders, access employee records, or query the billing system. If the application connects the chatbot to a database with full read-write access "for convenience," a successful prompt injection could instruct it to modify records or extract payment information. Connect it with read-only access to the orders and products tables only, and the same injection attempt fails at the database layer regardless of what the model tries to do. The database will not execute a write query from a read-only connection, no matter how persuasive the prompt.

Choosing which tools to connect, what permissions each tool gets, and which actions require a human in the loop are decisions made before deployment. They are not problems solved with better classifiers. Removing a tool from an agent's toolkit eliminates that attack surface entirely.

Guardrail Architectures

A guardrail is a constraint on LLM input or output behavior. The term gets used loosely in the industry to mean almost any safety mechanism, which makes it hard to evaluate what someone actually means when they say "we added guardrails." The useful question is not "which product should we deploy?" but "what are we guarding: conversation flow, output format, or content safety?" The answer determines which architecture fits, because each architecture has different failure modes.

  1. 1

    Rule-Based

    Regex patterns, keyword lists, and allow/deny lists. Fast, predictable, deterministic: a regex either matches or it does not. But brittle: an attacker who knows the rules can craft inputs that satisfy every rule while still achieving the attack goal.

  2. 2

    Model-Based

    A classifier model evaluates inputs or outputs against a configurable safety taxonomy, flagging prompts that violate defined categories. Catches semantic variations that rule-based systems miss, but probabilistic: accuracy depends on training data and taxonomy coverage. Production latency targets are typically 100-200ms per check.

  3. 3

    Hybrid

    Rules handle what can be decided deterministically (format compliance, rate limits, banned-string detection); models handle what requires judgment (semantic classification, intent detection). This is the architecture most production systems use.

Guardrail tools change rapidly. Specific products and versions will be different by the time you read this. What matters is learning to evaluate any guardrail tool against a stable set of criteria:

Evaluation criterionWhat to askWhy it matters
Architecture type Rule-based, model-based, or hybrid? Determines the tool's failure mode: brittle rules vs. probabilistic classification vs. a mix of both
Scope Does it cover input, output, or both? Conversational flow, content safety, or structured output? A tool that only validates output format does not defend against prompt injection at the input layer
Latency budget What latency does each check add? Can it run synchronously without degrading user experience? A guardrail that adds 500ms per check may be impractical for real-time chat but fine for batch processing
Customizability Can you define your own policy categories? Adjust sensitivity thresholds? A healthcare chatbot needs different guardrails than an internal code assistant
Evaluated accuracy Has the tool been independently tested on unseen attack patterns, not just its own training data? Vendor-reported accuracy on known patterns overestimates real-world effectiveness (the 85% to 34% drop)

When evaluating tools, apply the same skepticism this section teaches: vendor benchmarks reflect known-pattern accuracy; real-world performance against adaptive adversaries is always lower.

When a guardrail tool disappears: LLM Guard and open-source supply chain risk

One of the guardrail tools referenced in this module's supplementary materials is LLM Guard, built by Protect AI. It offered 15 input scanners and 20 output scanners under an MIT license and was designed to run on CPU without GPU dependencies. On July 9, 2026, Protect AI archived the repository, setting it to read-only. No new patches, no security updates, no maintained releases.

Open-source maintainers do not always publish an explicit post-mortem when they archive a project, but repositories are typically set to read-only for a few specific operational and business reasons. In this case, the archiving appears to be part of a strategic shift by Protect AI toward its commercial product line. When a company maintains both an open-source tool and a paid product that overlaps with it, the open-source project can create internal competition, divert engineering resources, and complicate the commercial narrative. Sometimes companies believe archiving helps resolve that tension.

This pattern extends beyond any single company. As the AI security landscape matures, standalone open-source scanners are being absorbed into broader platforms: native security features embedded inside API gateways like and , or enterprise AI firewall products that bundle input validation, output filtering, and monitoring into a single managed service. The standalone scanner category is consolidating.

The practical consequence is immediate. Every organization that deployed LLM Guard in production now has a dependency on unmaintained code. No new vulnerability patches. No compatibility updates when upstream libraries change. No adaptation to new attack patterns. This is abandonware, and it is a recurring problem in software supply chains. When evaluating any open-source security tool, ask: what is the project's governance model, who funds the maintainers, and what is your migration plan if the project is archived tomorrow?

What the evidence says about guardrail effectiveness

The evidence on guardrail effectiveness is less reassuring than deployment experience might suggest, and the gap between the two directly shapes how we should design defense architectures.

A systematic evaluation of 10 guardrail models found the best achieved 85.3% accuracy on known attack patterns. The same study tested those guardrails on unseen attack patterns, prompts not in the guardrail's training data, and accuracy dropped to 33.8%: from catching roughly 5 out of 6 known attacks to catching roughly 1 in 3 novel attacks. The guardrail learned to recognize the attacks it was trained on, not the underlying concept of "injection attempt." This is the same overfitting problem we studied in machine learning fundamentals: high performance on the training distribution, poor generalization to new distributions.

A second study adds context. Researchers at three major AI labs evaluated 12 distinct prompt injection defenses, covering every major defense strategy available at the time. Under adaptive conditions, where the attacker could study the defense and iterate, all 12 were bypassed at greater than 90% success rates.

Together, these findings set the terms for the rest of this module. A guardrail catches most casual abuse (the 85% number). It degrades sharply against novel attacks (the 34% number). It fails almost completely against a determined, adaptive adversary (the 90%+ bypass number). That is not a reason to skip guardrails; it is a reason to never rely on them alone.

The Most Frequent Error

Treating a deployed guardrail as though it eliminates prompt injection risk. The accuracy degradation (85% → 34% on unseen patterns) and the adaptive bypass rate (>90% success) directly contradict that assumption. Guardrails are a layer, not a solution.

Guardrails still reduce attack success against non-adaptive adversaries, and that covers most real-world abuse: automated scripts, casual attempts, users who try a known jailbreak phrase once and give up. The problem is sole reliance. A guardrail that catches 85% of attacks is a useful layer. The same guardrail treated as the complete solution leaves the remaining 15% (or more, against adaptive attackers) unaddressed.

Researchers have begun applying differential privacy to the prompt layer itself. The idea: before a prompt reaches the model, a sanitization step uses differential privacy guarantees and format-preserving encryption to strip or obscure sensitive tokens while preserving the prompt's structure. Early work in this space, Pr∈∈mpt, was published at NDSS 2026. The approach is still experimental and has not seen production deployment, but it is interesting because it borrows a well understood privacy mechanism and applies it to a new surface.

Why Guardrails Fail Under Adaptive Attacks

Guardrails fail for specific, analyzable reasons. Work through these three questions; understanding the mechanisms matters more than memorizing the statistics.

Part 2: Training on Known Patterns

A guardrail is trained on 50,000 known jailbreak patterns and catches 95% of them in testing. Why does this not solve next month's attacks?

The 95% catch rate applies to known patterns, which are the distribution the guardrail was trained on. An adaptive attacker does not reuse known patterns; they craft novel ones. The evaluation on unseen patterns shows accuracy dropping from 85% to 34%. Training on yesterday's attacks does not stop tomorrow's.

Part 3: Defend Guardrails Honestly

Write one sentence that defends guardrails while honestly acknowledging their limitations. The sentence should explain why guardrails are worth deploying even though adaptive attackers can bypass them.

One approach: "Guardrails substantially reduce attack success against non-adaptive adversaries, which covers most real-world abuse, making them a valuable layer within a defense-in-depth architecture even though they cannot stop an attacker who specifically targets them." The key is the qualifier: "a layer within," not "the solution." Any sentence that calls guardrails sufficient on their own contradicts the evidence.
