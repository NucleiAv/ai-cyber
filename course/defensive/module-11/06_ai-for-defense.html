Four Areas Where AI Is Being Used

Everything in this module so far has treated AI as a system to defend. AI is also a tool for defense: LLMs and machine learning models are being applied to cybersecurity problems that historically required either manual expert analysis or rigid rule-based automation.

We apply the same evaluation method here. Every capability claim gets paired with its documented limitation. We did this with guardrails (85% accuracy on known patterns, 34% on novel ones). We did it with RAG architectures (retrieval provides grounding, but retrieval cannot tell trustworthy content from adversarial content). The failure mode is the same: overconfidence in AI-generated output leads to missed vulnerabilities, misclassified threats, and false assurance.

The four areas below are where AI-assisted security operations are seeing the most use. In each case, the capability and the limitation are both real. The practitioner's job is to design workflows that capture the capability while managing the limitation.

IAM Policy Analysis

IAM policies define who can do what in a cloud environment. In AWS alone, a mid-size organization might have hundreds of policies with thousands of permission statements, and the security implication of each statement depends on its interactions with every other statement. Manual review at that scale is slow and error-prone. Static analysis tools (like AWS Access Analyzer) catch syntactic issues and known misconfiguration patterns, but they struggle with logic-level risks: permissions that are individually reasonable but create dangerous combinations.

LLMs bring a different capability. They can reason about logical relationships between policy statements and identify risks that emerge from combinations rather than individual rules. A study tested LLM-based IAM policy synthesis against 47 ground-truth policies using SMT (Satisfiability Modulo Theories) solvers for formal verification. The LLMs generated syntactically correct, logically consistent policies, and they caught logic-level issues that static tools typically miss, like implicit permission escalation paths where a combination of innocuous permissions lets a user grant themselves broader access.

Limitation: The same study found that LLMs inconsistently evaluated risk severity. They caught obvious risks like S3 wildcard access but sometimes underestimated subtler permissions. The PassRole example is instructive: iam:PassRole lets a user assign a role to a service, effectively inheriting that role's permissions. If the target role has administrative access, PassRole is one of the most common privilege escalation vectors in AWS. An LLM might dismiss it as "low-risk" and "standard" because PassRole appears frequently in legitimate configurations, without evaluating what the target role actually grants. The LLM recognized the pattern (PassRole is common) but missed the implication (PassRole to an admin role is dangerous).

Infrastructure as Code Misconfiguration Detection

LLMs are being applied to detect misconfigurations in Infrastructure as Code (IaC) templates, particularly Terraform. Studies show they outperform traditional static analysis at detecting logic-level "code smells": security groups with overly broad CIDR ranges, IAM policies with unnecessary wildcards, storage resources without encryption. The LLMs caught issues that required understanding the intent of the configuration, not just its syntax.

Limitation: A separate study tested LLM-generated IaC repairs and found that 20.4% of repairs that passed linter validation were nonetheless incorrect. The failures broke down into schema validation failures (the repair used parameters or resource types that do not exist in the provider) and wrong-issue targeting (the repair fixed a different issue than the one flagged, or introduced a new misconfiguration while fixing the original).

A practical note: LLMs perform measurably better on YAML and JSON configuration formats than on HCL (HashiCorp Configuration Language). If you are using AI-assisted IaC review, format matters.

Malware Behavioral Classification

Signature-based malware detection matches known malware against a database of signatures. It is fast and produces near-zero false positives on known threats. It fails against polymorphic malware (which changes its signature on each execution) and zero-day threats (which have no known signature).

AI-based behavioral classification works differently: instead of matching signatures, it analyzes what the malware does. Behavioral patterns (file system modifications, network communications, registry changes, process injection) are more stable than code signatures because attackers can change their code far more easily than they can change the fundamental actions their malware must perform.

Gradient-boosted decision tree models, combined with dimensionality reduction and feature scaling, have achieved over 97% accuracy on malware behavioral classification. They catch polymorphic and zero-day threats that signature-based detection misses because they classify behavior rather than code.

Consensus: Hybrid detection is the field standard. Signature-based as the fast first layer (high speed, near-zero false positives on known threats), behavioral classification as the second layer (catches novel threats, higher computational cost, some false positives). Neither alone is sufficient.

YARA Rule Generation

are pattern-matching rules used by malware analysts to identify and classify malware samples. Writing them well requires expertise: the analyst must identify byte patterns, strings, and structural features specific enough to match the target malware family without producing excessive false positives.

Research into automated YARA rule generation has shown substantial time savings, with studies reporting 44-86% reductions in analyst time compared to manual writing. Generated rules matched the detection quality of manually written rules across test datasets. More recent work uses LLMs for nuanced rule generation, including the ability to analyze malware behavior reports and generate rules based on behavioral descriptions rather than byte patterns alone.

Failure mode: LLMs sometimes confuse YARA (the open-source pattern matching language) with YARA-L (Google Chronicle's proprietary detection language). The two have different syntax and different capabilities. Rules generated in the wrong language will not execute in the intended environment. Human review is required for all LLM-generated YARA rules, both for correctness and for language verification.

Evaluating an LLM's IAM Analysis

An LLM analyzed a three-statement AWS IAM policy and produced the assessment below. Evaluate its work: which finding is correct, which underestimates risk, and which is misleading?

Statement 1: S3 Wildcard Permissions

Allows s3:* on all resources in the production bucket.
LLM Assessment: "HIGH RISK. Wildcard S3 permissions grant read, write, delete, and administrative access to the entire production bucket. Recommend restricting to specific actions (s3:GetObject, s3:PutObject) and specific prefixes."

Correctly assessed. S3 wildcard access to a production bucket is a clear high-risk finding, and the recommendation to restrict to specific actions and prefixes is appropriate.

Statement 2: EC2 Instance Permissions

Allows ec2:RunInstances and ec2:TerminateInstances on all instances.
LLM Assessment: "MEDIUM RISK. These permissions allow creating and destroying compute resources. Consider restricting to specific instance types and requiring tags for resource tracking."

Underestimates risk. The ability to run and terminate arbitrary EC2 instances is not "medium risk." An attacker with these permissions can launch instances for cryptocurrency mining (financial impact), terminate production instances (availability impact), or spin up instances in unmonitored regions (evasion). The LLM's recommendation about instance types and tags is reasonable but does not capture the full scope of the risk.

Statement 3: IAM PassRole

Allows iam:PassRole for a specific service role.
LLM Assessment: "LOW RISK. PassRole is a standard permission needed for service integrations. The scope is limited to a single named role."

Misleading. iam:PassRole is one of the most common privilege escalation vectors in AWS because it lets a user assign a role to a service, effectively inheriting that role's permissions. If the named role has administrative access, PassRole enables escalation to admin. Calling this "LOW RISK" and "standard" is incorrect. The assessment should flag PassRole as requiring explicit review of the target role's permissions to determine actual risk.

The Pattern

One correct assessment, one partial, one dangerously wrong. That is "trust but verify" in practice. Automated IAM analysis is valuable as a first pass; human review is required for all findings, especially for permissions like PassRole where the risk depends on context the LLM may not fully evaluate.

Module Wrap-Up and Integration Check

The closing principle: trust but verify

Every AI-for-defense tool we surveyed follows the same pattern. The capability is real: LLMs catch IAM logic issues that static tools miss, detect IaC misconfigurations at the intent level, classify malware by behavior rather than signature, and accelerate YARA rule writing. The limitation is also real: IAM risk assessments are inconsistently calibrated, roughly one in five LLM-generated IaC repairs is incorrect despite passing linter validation, behavioral classifiers produce false positives that signature-based detection avoids, and YARA rules may target the wrong language entirely.

"Trust but verify" means: use AI tools for their speed and pattern recognition, but verify their output before acting on it. Build workflows with human review at decision points. This applies to the defense tools in this section exactly as it applies to the controls we studied in Sections 1 through 4.
