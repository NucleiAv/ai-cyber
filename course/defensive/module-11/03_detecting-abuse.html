From Hardening to Monitoring

Why Monitoring Is Not Optional

Every control we studied in Section 1 has a bypass rate. degrade from 85% to 34% accuracy on unseen prompts. Adaptive attackers bypass all 12 tested defenses above 90%. Controls will sometimes fail. Monitoring is the feedback loop that catches what they miss. Without it, a compromised system can keep producing harmful output, and the team may not know.

Monitoring AI systems fills the same role that and log analysis play in traditional security operations. The telemetry is different: instead of firewall logs and network flows, we analyze prompts, responses, token counts, guardrail verdicts, and behavioral patterns. But the analytical discipline is the same: look for anomalies, correlate signals, investigate when multiple indicators point in the same direction.

What prompt injection looks like in logs

leaves two kinds of signatures in application logs: input-side and output-side.

Input-side signatures. are among the most reliable because legitimate users rarely encode their questions. -encoded strings in a customer support chat, Unicode substitution characters (zero-width joiners, homoglyphs from Cyrillic or Greek alphabets), and mixed-encoding patterns within a single message are all unusual in normal usage. A customer asking about a refund does not encode the question in Base64. An attacker trying to bypass keyword filters does.

patterns are another signal. Phrases like "ignore previous instructions," "you are now DAN," "system:" or "[INST]" appear frequently in injection attempts because they try to override the system prompt. System prompt keywords in user input ("your instructions," "original prompt," "system message") suggest extraction attempts: the user is fishing for how the system was configured.

No single signature confirms an attack. A developer might legitimately paste Base64 into a technical support chat. A curious user might ask "what are your instructions?" out of genuine curiosity. Each signature raises the probability; it is not a verdict.

Output-side signatures. can indicate successful extraction: if the system averages 380 tokens and a particular response runs to 2,100, the model may have returned more than intended, possibly the full text of a retrieved document, a system prompt, or a data dump. Structured data appearing in freeform responses (JSON objects, configuration blocks, database connection strings, internal identifiers) may indicate exposed internal state that should not typically reach a user. System prompt fragments in output are a strong indicator of successful extraction.

The relationship between input and output signatures is where detection becomes useful. An input that triggers guardrail flags but produces a normal-length, normal-format response was likely blocked: the system worked. An input that triggers zero guardrail flags but produces an anomalous response is the scenario worth investigating: it suggests the attacker may have evaded input-side controls, making monitoring a critical fallback.

Data exfiltration signatures

through an LLM system produces its own patterns. in responses (email addresses, phone numbers, identification numbers) that were not part of the user's query suggests the model retrieved and disclosed personal information. Document-level metadata in output (file paths, author names, revision dates) indicates exposed retrieval infrastructure. Unusually complete responses, where the model returns what looks like an entire document rather than a summary, suggest it retrieved full documents rather than relevant passages.

Log Signatures and Detection Layers

Detection works at three levels, each catching different attack patterns:

1

Content-Based Detection

Matches known attack signatures and patterns in request and response content. Includes keyword patterns, , and structural indicators (, instruction override attempts). Fast and specific but brittle: catches known patterns and misses novel ones.

2

Rate-Based Detection

Identifies anomalies in request volume, frequency, and timing. A single user sending 14 queries in 3 minutes, or 847 queries in a day, deviates from normal patterns. Session-level patterns also matter: rapid-fire queries with incrementally modified prompts suggest an automated probing tool. Catches volume-based attacks but misses slow, patient attackers.

3

Behavioral Detection

Identifies shifts in output characteristics that may indicate compromise. Output drift (responses clustering differently than historical patterns), perplexity anomalies, and can indicate sustained exploitation. For example, if a customer support chatbot's responses suddenly cluster around internal-procedure topics rather than product questions, that distribution shift may indicate a successful injection steering the model's behavior. Catches gradual degradation that content and rate-based detection miss, but requires a baseline period of normal operation to calibrate what "normal" looks like.

3

Compound Detection: Combining Signals

A single anomalous signal is ambiguous. A user sending 14 queries in 3 minutes might be impatient. A Base64-encoded string might be a legitimate technical question. A long response might be a thorough answer to a complex question, not the model dumping its system prompt. Individually, each signal generates too many to be actionable.

Correlated signals change the picture. When the same session shows high query volume AND AND AND , the probability that all four are benign drops sharply. reduces false positives by requiring multiple independent indicators before triggering an alert.

The tradeoff is real. Requiring three signals to fire before alerting means fewer false positives but also missed attacks that produce only two signals. Alerting on a single signal catches more attacks but drowns analysts in noise (the same problem that plagues traditional operations). Where to draw the line depends on context: a medical chatbot handling patient data may warrant more aggressive alerting than a product FAQ bot.

Why guardrails can miss an entire session: a constructed walkthrough

To understand how guardrails can produce zero flags on a malicious session, we need to open a guardrail stack and trace attacker queries through every rule. This walkthrough constructs a specific three-layer guardrail configuration, then evaluates five attacker queries against it, one rule at a time.

The guardrail stack

This customer support chatbot deploys three input-side guardrail checks. Every incoming query runs through all three before reaching the model. If any rule triggers, the query is blocked.

1 RULE 1 │ Keyword blocklist │ 38 injection phrases │ exact + fuzzy match │ → BLOCK if match ⓘ
2 RULE 2 │ Semantic classifier │ DistilBERT, 12k training samples │ threshold ≥ 0.75 │ → BLOCK if score ≥ 0.75 ⓘ
3 RULE 3 │ Encoding detector │ Base64 regex + homoglyph ranges + zero-width chars │ → BLOCK if detected ⓘ
Hover or tap a rule to see what it checks.

These three rules cover the standard guardrail categories from Section 1: string-level matching, semantic-level classification, and encoding-level detection. Each operates on a different representation of the input. Together, they achieve roughly 85% detection accuracy on known injection prompts from their training distribution, the same figure that degrades to 34% on unseen prompts.

Five queries. Fifteen rule checks. Not a single flag. The attacker avoided blocked keywords, kept the classifier below threshold, and used no encoding tricks. Each evasion exploited the same structural limitation: guardrails evaluate each query in isolation against patterns they were trained on. An attacker who studies those patterns can construct inputs that carry a completely different intent than the guardrail's training data prepared it for.
