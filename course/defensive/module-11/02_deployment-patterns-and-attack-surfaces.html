Three Patterns, Three Attack Surface Envelopes

Deploying an LLM into production connects it to real systems, real users, and real data, and how we deploy it determines what can go wrong. Each deployment architecture connects the model to different systems, exposes different interfaces, and draws different trust boundaries.

We analyze three common deployment patterns here as security design problems, not implementation tutorials. The question is not "how do I build a RAG pipeline?" but "what attack surfaces does a RAG pipeline create, and what controls address each one?" Every pattern inherits the general risks we studied in the attacks modules: , , , . The patterns differ in what they add on top of that baseline, and the additions are where most real-world incidents originate.

The Baseline Pattern

The simplest deployment: direct user interaction with an LLM, no external data retrieval, no tool access. Its attack surface is the baseline against which we compare everything else. Every prompt injection technique we studied applies: override attempts, encoding tricks, role impersonation, system prompt extraction.

All the defenses from Section 1 apply: input validation, output filtering, guardrails, privilege separation. Because the chatbot pattern does not retrieve external content or call external tools, it has no retrieval-specific or tool-specific attack surfaces. That clean baseline lets us see exactly what the next two patterns add.

Unique risks: None beyond the general LLM baseline. That is the point of defining it as the baseline.

An API-exposed LLM serves programmatic clients rather than human users. This adds risks that neither chatbots nor RAG systems face: unauthorized endpoint discovery, , , and lifecycle endpoint exploitation.

The RAG Pattern: Four Retrieval-Specific Attack Surfaces

We study this architecture at the security-analysis level only: what attack surfaces does retrieval introduce, and what controls address them? How to build a RAG pipeline, choose an embedding model, or configure a vector database is outside our scope. What matters here is understanding why each step in the RAG pipeline creates an opportunity for an attacker, and how to evaluate whether the controls in place actually address the right threat.

The core issue is that RAG adds a data channel that bypasses the model's training. In a plain chatbot, the model responds from its weights. In a RAG system, the model also responds from whatever documents the retrieval system hands it. That retrieval channel is a new attack surface because the model treats retrieved content like anything else in its : content to process and potentially follow. If an attacker can influence what gets retrieved, they can influence what the model says.

Each step in the RAG architecture introduces a distinct vulnerability:

1

Corpus Poisoning

An attacker injects adversarial documents into the knowledge base, crafted to surface for specific queries and steer the model's response. A peer-reviewed study showed that injecting just 5 adversarially crafted documents into a corpus of 400 million achieved 90-99% attack success rates at a cost of roughly $60 (domain purchase and web crawling). Embedding similarity cannot distinguish adversarial content from legitimate content; both are retrieved by the same mechanism.

2

Adversarial Embeddings

An attacker crafts content designed to maximize with target queries, so the adversarial content surfaces even when it is not semantically relevant. Embedding spaces compress meaning in ways that can be gamed: high similarity in vector space does not guarantee honest relevance.

3

Cross-Document Injection

Instructions hidden in retrieved content are processed by the model alongside legitimate documents. This is through the retrieval channel: the attacker places the payload in a document, and the retrieval system delivers it to the model.

4

Cross-Tenant Leakage

In multi-tenant deployments where customers share a , data from one tenant's namespace can leak into another's results. The root cause is usually architectural: access control enforced at the application level rather than at the database level, so a filtering bug exposes everything.

Deterministic versus probabilistic RAG controls

The deterministic/probabilistic distinction from Section 1 applies directly here. Database-level is : tenants physically cannot query each other's namespace regardless of what the application does. Application-level is : it depends on the application correctly tagging and enforcing access metadata for every single query.

Cross-Tenant Leakage: A Documented Incident

A shared vector store in a major platform allowed sales representatives from Company A to retrieve Company B's knowledge base data. The root cause: access control was enforced at the application layer via metadata tags, not at the database. When the filtering failed, every tenant's documents became accessible through similarity search. The fix is architectural: enforce isolation at the database level, where it is deterministic.

The API-Exposed Pattern: Programmatic Access Risks

An API-exposed LLM serves programmatic clients rather than human users, which changes the threat model. Programmatic access enables automation: an attacker can write a script that sends thousands of requests per minute, probes every endpoint, extracts model behavior systematically, and runs up compute bills at machine speed. The following risks are unique to API exposure:

  1. 1

    Unauthorized endpoint discovery

    Security researchers examining popular LLM deployment frameworks have found hundreds of API endpoints, many with minimal or default authentication. Default framework configurations prioritize ease of setup, not security, and the number of exposed endpoints grows as frameworks add features.

  2. 2

    Model extraction

    Repeated queries through an API can extract enough information to reconstruct a reasonable approximation of the model, especially for smaller or fine-tuned models.

  3. 3

    Denial-of-wallet

    Stolen API credentials generate massive compute bills. Documented incidents have run up costs in the tens of thousands of dollars per day from a single compromised key. (not just request-count limiting) is necessary because one long-context request can cost as much as dozens of small ones.

  4. 4

    Lifecycle endpoint exploitation

    Many frameworks expose model management endpoints (reload, configuration, fine-tuning triggers) alongside inference endpoints. Without proper authentication, these let an attacker modify the model itself, not just query it.

Going deeper: denial-of-wallet

Denial-of-wallet is easy to pass over, because nothing stops working while it happens. The two panels below add the OWASP framing and the controls that follow from it.

OWASP does not give denial-of-wallet an entry of its own. It sits inside . OWASP describes that entry as an application permitting excessive and uncontrolled inference, with denial of service, economic loss, model theft, and service degradation among the results. Denial-of-wallet is the economic branch: OWASP defines it as a high volume of operations aimed at the cost-per-use model of cloud AI services, large enough to create a financial burden the provider may not be able to absorb.

The placement matters, because a denial-of-wallet attack does not look like an outage. Latency can stay normal, error rates flat, and the service keeps answering correctly while the cost keeps rising. Several of the consumption patterns OWASP lists run up cost without any of the usual availability symptoms.

OWASP consumption pattern What the caller sends Why the bill moves
Variable-length input flood Many requests of differing sizes Each request looks unremarkable on its own, so it is the total that drains the budget
Continuous input overflow Input that runs past the model's context window Work is done on input that is then discarded, so the cost is paid and nothing is returned
Resource-intensive queries Prompts that force long reasoning chains or long output A few requests can account for a large share of the cost

The simulation below makes the same point with numbers: a request-count limit treats a 200-token request and a 200,000-token request as one unit each, so it can be working exactly as configured while the bill grows a thousandfold.

OWASP's mitigation list for LLM10 runs to fifteen items and covers the whole of unbounded consumption, model extraction included. For the financial branch, a smaller set does most of the work, and it maps onto controls we have already met:

  • Rate limiting counted in tokens. The unit of cost is the token, so a limit counted in requests measures the wrong thing. This is the control the comparison below is built around.
  • Resource allocation management, timeouts and throttling. A ceiling on how long one inference may run and how much of the pool one caller may hold, so a single client cannot occupy the service indefinitely.
  • Bounded queues alongside deliberate scaling. Autoscaling answers a load spike by buying more capacity, which is the wrong response when the spike is the attack. OWASP pairs its scaling guidance with a limit on queued actions for this reason.
  • Logging, monitoring, and anomaly detection. Spend per credential over time is the signal that separates a busy day from a compromised key. Section 4 returns to denial-of-wallet from that angle.
  • Access controls and graceful degradation. Narrow what a given key may call, and decide in advance what the service does when a limit is reached, so that degrading is something the system does on purpose rather than an outage.

The two incidents this module cites, roughly $46,000 in a day and $82,000 across 48 hours, both ran through valid credentials against services that stayed healthy throughout. The figures come from the reporting parties and have not been independently audited. What matters here is which control would have caught them, not the exact amounts.

The takeaway is that security controls must be pattern-specific. An organization that deploys a RAG-based chatbot and secures it using only the controls appropriate for a plain chatbot has left four attack surfaces entirely undefended. An organization that exposes an LLM API without is vulnerable to denial-of-wallet attacks where a single request can cost hundreds of dollars. The assessment skill is matching the deployment pattern to the correct threat model and verifying that controls actually address the pattern-specific risks, not just the baseline.

RAG Attack Surface Mapping

For each of the three scenarios below, identify (a) which RAG-specific attack surface it targets, (b) whether it would work against a plain chatbot with no RAG, and (c) what control would mitigate it.

Scenario 1: The Paralegal's Upload

A paralegal at a law firm uploads a document to the firm's legal research knowledge base. The document contains hidden instructions that redirect queries about contract termination clauses to return misleading information.

This is cross-document injection (indirect prompt injection via the retrieval channel). The paralegal's document carries hidden instructions that the model follows when the document is retrieved. It would not work against a plain chatbot because the chatbot has no retrieval mechanism to deliver the payload. Mitigation: scan ingested documents for hidden instructions, restrict who can add documents, and apply output filtering to detect responses that deviate from the retrieval source.

Scenario 2: Shared Vector Store

Company A's employees can retrieve Company B's internal product documentation from a shared vector store, even though both companies were told their data would be isolated.

This is cross-tenant leakage. It targets the vector store's access control architecture. It would not work against a plain chatbot because there is no shared data store. Mitigation: enforce namespace isolation at the database level (deterministic), not just application-level metadata filtering (probabilistic).

Scenario 3: System Prompt Extraction

A user types a prompt that makes the customer support chatbot reveal the first 200 characters of its system prompt. The chatbot uses RAG to search product documentation, but the attack does not involve any retrieved documents.

This is system prompt extraction, a general chatbot-level attack. It works against any chatbot, with or without RAG, because it targets the model's system prompt rather than the retrieval system. The RAG component is irrelevant to this attack. Mitigation: input validation to detect extraction patterns, output filtering to scan responses for system prompt content.

PoisonedRAG Case Analysis

A research team demonstrated that injecting 5 adversarially crafted documents into a RAG knowledge base of 400 million documents achieved 90-99% attack success across multiple question types. The adversarial documents were optimized to maximize embedding similarity with target queries, so the retrieval system actively delivered the attack: poisoned documents scored high on relevance precisely because they were designed to.

This study is worth analyzing because it reveals how retrieval-based systems break the trust assumptions that make them useful. Work through each question, then check your reasoning against the explanation.

The implicit trust assumption is that documents in the knowledge base are benign and accurate. RAG systems treat retrieved content as grounding context, but the retrieval mechanism has no way to judge whether content is trustworthy. Retrieval selects by similarity, not credibility.

Reviewing 5 documents in 400 million is like finding 5 specific needles in a haystack the size of a building. Content-level review of the entire corpus is infeasible at that scale. The attacker needs to poison a vanishingly small fraction; the defender needs to verify the entire corpus.

Embedding similarity measures how closely a document's vector representation matches a query's. Adversarial documents are crafted to maximize that similarity, so in embedding space they look indistinguishable from highly relevant legitimate documents. The retrieval system surfaces them precisely because they score high on the same metric used for legitimate retrieval.

Two controls that reduce risk: (a) anomaly detection on retrieval patterns, flagging when a small number of recently added documents are retrieved disproportionately often across many different queries; (b) multi-source verification, requiring the model to corroborate retrieved claims across multiple independent documents before presenting them as answers.

Even with these controls, the vulnerability persists because the LLM processes retrieved content and instructions in the same representation space. The instruction/data boundary is still collapsed. Any content injected into the model's context, whether through user input or retrieval, can potentially be interpreted as instructions. Controls reduce the likelihood; they do not create a structural separation.
