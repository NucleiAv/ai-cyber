What Is a Large Language Model?

A is a neural network trained on massive text data (trillions of tokens, billions of parameters) that generates text by predicting the most probable next word (or, more precisely, the next ).

The mental model you should carry: an LLM is an extraordinarily sophisticated autocomplete system. It generates what is statistically likely to follow, not what is true. This distinction is the single most important thing a security professional needs to understand about language models.

LLMs now write phishing emails, analyze security logs, summarize CVE reports, generate code, and classify threats. Their capabilities are real and growing, but every output is a statistical prediction, not a fact retrieval, and that gap has direct security consequences you will explore throughout this page.

2

How Text Generation Works

Next-token prediction: Given the text "The server was compromised via a..." the model assigns a probability to every possible next token in its vocabulary. It selects one (say, "misconfigured"), appends it, and repeats. The entire response is built one token at a time, each conditioned on everything that came before.

Context window: An LLM can only "see" a fixed amount of text at a time, specifically its . Everything outside that window is invisible. If you paste 10,000 log lines into a model with an 8,000 token window, the model literally cannot see the overflow and will not tell you it missed anything.

Temperature and sampling: A randomness parameter controls how the model selects from its probability distribution. Higher temperature means more variation; the same prompt produces different outputs each time. This is by design, not a defect, but it means you cannot rely on reproducible results from the same query.

Hallucination: A Structural Property

is the generation of plausible sounding but factually incorrect output, sometimes delivered with complete confidence. An LLM asked about a specific CVE may fabricate a CVE number that looks correct, cite a vulnerability that does not exist, or confidently describe mitigation steps that would not work.

This is not a bug. It is a structural property of next-token prediction. The model generates text that is statistically probable given its training data. It does not retrieve facts from a database, and it has no internal mechanism to check whether its output is true. Mathematical research demonstrates that hallucination is inherent to the architecture, not a problem that will be solved by the next model version (Xu et al., 2024).

The professional imperative: Every LLM output used in a security context must be validated against authoritative sources. Not sometimes. Every time.

Security-Critical Hallucination Examples

Fabricated CVE numbers: LLMs generate CVE identifiers that look syntactically correct but reference vulnerabilities that do not exist. An analyst acting on a fabricated CVE wastes investigation time, or worse, misses the real vulnerability.

Hallucinated package names: When generating code, LLMs recommend software packages that do not exist. Researchers found that 19.7% of LLM suggested package dependencies were hallucinated (Spracklen et al., 2025). This is not just an accuracy problem. It is an exploitable attack surface (see the slopsquatting case below).

Confident but wrong security recommendations: LLMs may recommend security configurations that are outdated, inapplicable, or actively harmful, delivered with the same confidence as correct advice.

Case Spotlight: Slopsquatting

Spracklen et al. (2025, USENIX) analyzed 576,000 code samples generated by 16 LLMs and found that 19.7% of recommended package dependencies were hallucinated, meaning they did not exist in any package registry. Critically, 43% of these hallucinated names were repeatable: the same LLM produced the same fake package name across multiple runs.

This repeatability transforms hallucination from an accuracy problem into a supply chain attack vector. An attacker who identifies predictably hallucinated package names can register those names in public registries, populate them with malicious code, and wait for developers using LLM generated code to install them. The attack requires no interaction with the victim because the LLM does the delivery.

Before you move on: Why does the 43% repeatability rate matter more than the 19.7% hallucination rate for an attacker planning this campaign? Think about what predictability gives an attacker that randomness does not. You will explore this fully in Activity 5 (Slopsquatting Case Study), a separate assignment.

Large Reasoning Models

A is an LLM augmented with chain-of-thought reasoning via reinforcement learning. Where a standard LLM generates an immediate response in a single pass, an LRM produces an internal reasoning chain, working through a problem step by step before committing to an answer.

Worked example, LLM vs. LRM on the same query:

Query: "Is CVE-2024-3094 exploitable if our XZ Utils version is 5.6.0 but we don't use systemd?"

LLM response pattern: Generates an immediate, confident answer, possibly correct, possibly hallucinated. Single pass: input produces output with no visible reasoning.

LRM response pattern: Generates an internal reasoning chain first: "Step 1: CVE-2024-3094 affects XZ Utils 5.6.0-5.6.1. Step 2: The backdoor triggers through systemd's use of liblzma during SSH authentication. Step 3: If systemd is not used, the exploitation path through SSH is not present. Step 4: However, other applications linking liblzma could theoretically be affected. Step 5: Therefore the answer is 'likely not exploitable via the documented path, but confirm no other liblzma consumers exist.'"

Security implications of LRMs:

  • Reasoning chains can be hijacked. An attacker can supply text that the model treats as its own prior deliberation, so that the chain proceeds from premises the attacker chose rather than from the ones the task actually presents. In H-CoT (Kuo et al., arXiv 2502.12893), the injected material imitates the model's internal safety-reasoning phase, and the model continues as though it had already completed and passed that check. The injected step does not need to survive into the visible answer. It only needs to alter the premises on which the remaining steps build, and a single altered premise early in the chain will cascade through everything that follows.
  • Reasoning is opaque. Whether the visible chain faithfully represents the model's actual computation is itself uncertain. The chain is generated text, a post hoc narrative, not a transparent execution log.
  • Reasoning length is itself an attack parameter. The intuitive expectation is that a model which deliberates longer about safety should be harder to subvert, and the evidence points the other way. Chain-of-Thought Hijacking (Zhao et al., arXiv 2510.26418) pads a harmful request with long sequences of entirely benign puzzle reasoning and reports attack success rates of 94% to 100% against Gemini 2.5 Pro, o4-mini, Grok 3 mini, and Claude 4 Sonnet. The mechanism the authors identify is refusal dilution: middle layers encode the strength of the safety check and later layers encode its outcome, and a long benign chain attenuates both by drawing attention away from the harmful tokens. Note carefully what this is not. Nothing adversarial is injected into the reasoning at all, so this is a distinct failure mode from the one above rather than a larger-scale version of it. Length is the weapon.
  • Cost and latency. The extended reasoning pass consumes significantly more tokens and time. In a SOC automation pipeline, this tradeoff (better accuracy vs. slower response) must be evaluated per use case.
  • Visible reasoning is persuasive to the analyst. The three implications above concern the model. This one concerns the person reading its output. A chain that presents itself as a numbered sequence of justified steps invites the reader to audit the form of the argument rather than its content, and a fabricated chain is no less orderly than a sound one. The practical consequence is that an LRM verdict is likely to receive less scrutiny than a bare LLM verdict of identical quality, which inverts the review posture the added reasoning was supposed to earn. Treat the chain as a claim requiring verification, not as evidence supporting the conclusion it precedes.
