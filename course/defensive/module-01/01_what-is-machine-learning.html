Driving Question

How should a security professional think about AI, and what must they know to evaluate it critically?

AI is operationally reshaping cybersecurity: 94% of surveyed leaders identify it as the #1 change driver (WEF 2026, large-enterprise skew). This module gives you the mental models to evaluate AI claims, tools, and threats with the rigor your role demands. The NIST Cybersecurity Framework Profile for AI (2025) organizes this challenge into three pillars you will encounter throughout this course: (1) secure AI systems, (2) use AI for defense, and (3) counter AI-enabled attacks.

1

The Limits of Rules

Consider a scenario you know well: a new malware variant uses code obfuscation to avoid signature matching. Your IDS has zero detections. The attacker changed the packaging, not the behavior, but because the system only recognizes what it has been explicitly told to look for, it sees nothing.

This is the fundamental limitation of : they catch what you have explicitly described and nothing else. Signature-based detection is excellent for known threats (it produces zero false positives for matched signatures) but it is structurally blind to novel attacks, polymorphic malware, and adversaries who deliberately evade known patterns.

This raises a practical question: what if the system could learn what "malicious" looks like from examples, rather than from a human writing rules?

2

Machine Learning: Learning from Data

is the alternative paradigm. Instead of a human encoding every detection rule, an ML system learns to recognize patterns from data. Given enough examples of malicious and benign network traffic, the system derives its own decision boundaries, catching threats the rule-writer never anticipated.

The key shift for a security professional: ML extends analyst pattern recognition to volumes no human can process. A supervised classifier can evaluate millions of network flows per hour against patterns derived from thousands of labeled incidents.

ML Is Not Magic

Machine learning fails when patterns change, training data is unrepresentative, or adversaries deliberately evade learned patterns. Most deployed security AI today uses classical ML, not large language models. And a well-tuned signature set still outperforms a poorly trained classifier for known threats.

The question is always: which tool fits this specific problem?

3

Three Paradigms of Machine Learning

Not all ML works the same way. The three paradigms differ in what data they need, what problems they solve, and what failure modes they produce. For a security professional, knowing which paradigm a tool uses tells you what questions to ask about its data, its limitations, and its failure behavior.

1

Supervised Learning

Labeled data

How it works
Learns from labeled input-output pairs. You provide examples of "attack" and "benign," and the model learns the boundary.
Security use case
Network IDS trained on labeled attack/benign traffic; malware classification from known samples.
Key requirement
Labeled data: expensive to produce, error-prone in security, and stale within months as threats evolve.
2

Unsupervised Learning

No labels

How it works
Finds structure in unlabeled data. The model builds a picture of "normal" and flags deviations without being told what an attack looks like.
Security use case
Anomaly detection in network traffic; insider-threat detection; clustering unknown malware into families.
Key requirement
A stable baseline of "normal." Sensitive to baseline drift; high false-positive rate because not every anomaly is an attack.
3

Reinforcement Learning

Trial & reward

How it works
Learns through trial-and-error with reward signals. An agent takes actions in an environment and learns which sequences produce the best outcomes.
Security use case
Adaptive network defense that adjusts firewall rules in response to ongoing attacks; automated penetration-testing agents.
Key requirement
An environment to interact with (simulated or real) and a clear reward signal. Rare as a deployed security product, and the mechanism behind the preference tuning in nearly every language model you will use. Part 4 below looks at both.

Reinforcement Learning Up Close

reaches security work from two directions. Very few security products on the market today are built on it, so you are unlikely to evaluate one as a purchase. Nearly every language model you will work with in this course was shaped by it in the final stage of training, so you are already working with its results. This part covers both: why the security shelf is thin, and why a model's behavior is not a readout of what it read.

The loop

Supervised learning is handed the right answer. Reinforcement learning has to find it. Instead of labeled pairs, an agent acts inside an environment and receives a number back telling it how well that went.

  1. 1

    Observe

    The agent reads the current state of its environment. For a network defense agent, that might be the set of open connections, current alert volume, and which hosts are reachable from which.

  2. 2

    Act

    The agent picks an action from what its allows: block a source, isolate a host, raise an alert, do nothing. Early in training the choices are close to random.

  3. 3

    Receive a reward

    The environment returns a : a number, not an explanation. Attack contained, positive. Legitimate service knocked offline, negative. Nothing tells the agent which action in the sequence earned the score.

  4. 4

    Update the policy

    Actions that preceded higher rewards become more likely; actions that preceded lower rewards become less likely. The policy shifts by a small amount, not a rewrite.

  5. 5

    Repeat, at volume

    The loop runs thousands to millions of times. Competence comes from the accumulated statistics of many failures, which is the detail that determines where this paradigm can be used at all.

Why the security shelf is thin

Step 5 sets two preconditions, and operational security struggles with both.

The first is an environment you can afford to fail in repeatedly. An agent learning to isolate hosts will, early on, isolate the payroll server during closing week. That is acceptable in a simulator and unacceptable in production, so most published work in this area runs in research simulators of enterprise networks. The distance between a simulator and your network is not a detail to be closed later; it is the substance of the problem, and it is the first question to ask any vendor whose product claims to have learned this way.

The second is a reward that encodes what you actually want. This is harder than it sounds. Reward the agent for blocked attacks and it learns to block everything, since a fully quarantined network has an excellent attack containment record. Reward it for uptime and it learns to permit everything. Writing a reward that balances the two is the same problem as writing a good detection policy, except that a system will optimize against your wording continuously and without judgment about what you meant.

The skill that transfers

You may never deploy an RL security product. You will regularly evaluate systems that were trained against a proxy for the outcome someone wanted. The question that works on all of them is the same: what number was this optimized against, and where does that number stop agreeing with the result I actually care about?

Where reinforcement learning actually reaches you: RLHF

A pretrained language model predicts plausible continuations of text. That is not the same as being useful: it will answer a security question with text shaped like an answer, without being organized around answering yours. The gap between plausible text and useful assistance is closed by , usually shortened to RLHF, and it runs the loop you just read with two substitutions.

1

Collect preferences

Humans, in advance

What happens
Raters see two model outputs for the same prompt and mark which is better, working from a written guideline.
What it produces
A dataset of comparisons. Not corrections, and not ground truth: judgments about which of two answers a person preferred.
2

Train a reward model

A stand-in for the rater

What happens
A second model learns, from those comparisons, to predict which output a rater would have chosen. This is ordinary supervised learning.
What it produces
A that can score any output automatically, which is what makes the next step affordable.
3

Optimize the policy

The RL loop

What happens
The language model generates, the reward model scores, and the language model's weights shift toward higher-scoring behavior. Repeat at volume.
What it produces
The assistant behavior you recognize: following instructions, keeping a consistent register, declining some requests.

Map that back to the five steps. The environment is the prompt, the action is the generated response, the reward is the reward model's score, and the policy is the model's own weights. The human contribution sits in stage 1, aggregated and frozen before you ever open a session. Module 2 returns to this as one stage in a model's lifecycle, alongside instruction tuning and safety training; is the umbrella term for RLHF and the related methods that reach the same result by a shorter route.

What preference tuning does not do

RLHF explains a great deal about model behavior, and it is routinely asked to explain more than it can.

Often assumed What is closer to accurate
It teaches the model facts, so a tuned model is more accurate. It changes which outputs are favored, not what is stored in the weights. A confident wrong answer that raters preferred to a hedged right one is reinforced as written.
A model tuned to refuse harmful requests is secure against them. It was tuned against the kinds of requests raters saw. Requests shaped to fall outside that distribution are the subject of Module 9, and they work often enough to be a professional concern.
"Aligned" is a property of the model. It is a relationship to a particular group of raters, following a particular guideline, at a particular time. The useful follow-up to a vendor is: aligned to whose judgment, and measured how?

The reward model is a proxy

The optimization target is a model's prediction of what a rater would like, not the thing the rater actually cared about. Push hard enough against any proxy and the two come apart, a failure mode named : outputs that score well on the measure and are not what anyone wanted.

Fluent, confident, well-structured answers tend to score well. So do answers that agree with the person asking. Neither correlates reliably with being right, which is one of several reasons a model will produce a citation-shaped string where a citation should be. Section 4 of this module, on language models and hallucination, takes up that failure directly.

Two meanings of "human in the loop"

Keep the phrase in view for the rest of the course, because it names two different arrangements and the difference matters when someone puts it in a control document.

In RLHF it is a training-time construct: many raters, aggregated in advance, compressed into weights you cannot inspect and cannot query about a specific decision. In deployment, means something narrower and more auditable: a named person approving a specific action before it takes effect. The first cannot be reviewed after the fact. The second can, which is why it appears in policies, and Module 12 and Module 13 examine how reliably it holds up once the approvals arrive faster than anyone can read them.

When a vendor says a human is in the loop, it is worth asking which one they mean.

From Deep Learning to Language Models

All three paradigms, reinforcement learning included, can be implemented with (neural networks with many layers that learn hierarchical features automatically). Instead of a human engineer selecting which network traffic features to measure (packet size, port, timing), a deep learning system discovers relevant features directly from the raw data.

This capability is what makes large language models possible. Scale deep learning to massive text datasets (trillions of tokens, billions of parameters) and you get systems that generate human-quality text, analyze logs in natural language, and summarize vulnerability reports. But these capabilities come with a structural reliability problem that every security professional must understand.
