1

The Software Supply Chain and Trust Boundaries

What the Software Supply Chain Is

Modern software relies extensively on third-party components: open-source libraries, frameworks, build tools, CI/CD services, and package registries. The software supply chain encompasses every component, tool, process, and human action involved in developing, building, and distributing software, and each is a potential point of attack. When you declare a dependency on a package, you are not just importing code; you are extending trust to every person and system involved in producing, publishing, and distributing that package.

A critical concept is the . Your project might directly declare 10 dependencies, but those 10 packages each have their own dependencies, which have their own dependencies, and so on. The total dependency tree can easily reach hundreds of packages, each representing a trust relationship you may not even be aware of. A vulnerability or compromise in any transitive dependency affects your application, even though you never explicitly chose to depend on it.

Trust Boundaries

To understand supply chain attacks systematically, think in terms of trust boundaries: points where trust is extended from one entity or system to another with specific assumptions about the other party's behavior. When any of these assumptions is violated, the security impact propagates through all downstream trust relationships.

Trust Boundary Trust Extended Assumption What Happens When Violated
Developer → Registry "The package named X is what it claims to be" Registry enforces identity; packages are what they say Typosquatting, namespace confusion
Developer → Maintainer "The maintainer of package X acts in good faith" Maintainer is who they claim to be, has not been compromised Maintainer takeover, social engineering
Build System → Source "The source code has not been tampered with" Source repository is not compromised CI/CD script modification, source tampering
Consumer → Vendor "The vendor's software is safe to install" Vendor's own supply chain is secure Cascading supply chain compromise

Attackers target whichever boundary is weakest. The most comprehensive study of supply chain attacks to date catalogued 107 attack vectors from 94 real-world incidents with 33 corresponding safeguards. The full taxonomy is in the references, but the four attack vectors below cover the patterns you are most likely to encounter.

2

Attack Vectors in Detail

Package managers resolve dependencies by looking up package names in registries. Organizations that use both internal (private) registries and public registries face a design-level vulnerability: if an attacker publishes a package on the public registry with the same name as an internal package but at a higher version number, the package manager may resolve to the public (malicious) version.

In February 2021, Alex Birsan demonstrated this against Microsoft, Apple, and over 30 other companies: "Dependency Confusion: How I Hacked Into Apple, Microsoft and Dozens of Other Companies". He identified internal package names from publicly available configuration files, then published packages under those names on , , and at artificially high version numbers (e.g., 9.9.9). Build systems automatically pulled his public packages instead of the internal ones, achieving code execution inside corporate environments.

This is not a code vulnerability; it is a design-level vulnerability in how namespace resolution works. The fix requires architectural changes: namespace scoping, registry priority configuration, and dependency pinning.

Attackers register packages with names that are common misspellings of popular packages. A developer who types reqeusts instead of requests, or python-nmap when the legitimate package is python3-nmap, installs a malicious package that may include the legitimate functionality (to avoid detection) plus malicious code running at install time.

The attack surface is vast: dozens of plausible typos exist for every popular package, and automated detection is imperfect since new packages legitimately have similar names.

An attacker gains control of a legitimate, widely used package through social engineering. In the event-stream npm compromise (2018), the original maintainer (~2 million weekly downloads) transferred ownership to "," a contributor who had spent weeks making small, legitimate contributions to build trust. After gaining publish access, Right9ctrl added a dependency (flatmap-stream) containing obfuscated malicious code targeting the cryptocurrency wallet.

The attack exploited a structural problem: open-source maintainers often hand off ownership to whoever offers help, without identity verification or access controls. The malicious dependency went unnoticed for about two and a half months (September to late November 2018), and it was found largely by chance: a developer investigating an unrelated deprecation warning traced it to flatmap-stream.

Rather than compromising source code directly, attackers target the build infrastructure (CI/CD pipelines, build servers, or helper tools) to inject malicious code into artifacts during the build process.

The Codecov breach (2021): Attackers modified Codecov's CI helper script (via leaked Docker credentials) to exfiltrate CI environment variables (AWS keys, deployment tokens, API secrets) from any organization running the compromised script. The modification ran undetected for approximately two months, exposing any of Codecov's customers (the company reported more than 29,000) whose pipelines ran the script, until a customer compared the script's hash with the one Codecov published and found a mismatch.

The 3CX compromise (2023): 3CX, a business communication platform with over 600,000 enterprise customers, distributed trojanized versions of its desktop client through its official update mechanism. Investigation by Mandiant and CrowdStrike revealed a cascading supply chain attack: a 3CX employee had installed a compromised version of Trading Technologies' X_TRADER software, which gave attackers (attributed to the North Korean Lazarus Group) access to 3CX's build environment. This is the first publicly documented case of one supply chain attack being used as the vector for a second supply chain attack.

You explored as a hallucination risk back in Module 3. Here, the focus shifts to why it belongs alongside the other attack vectors in this section.

What makes slopsquatting dangerous from a supply-chain perspective is the predictability of hallucinated package names. When the same prompt is re-run ten times, 43% of fabricated names appear in every single run, and 58% appear more than once. That consistency gives attackers a reliable playbook. Harvest the most commonly hallucinated names, register them on public registries with malicious payloads, and let AI coding assistants do the distribution for free.

Compare this to the other vectors in these tabs. Typosquatting relies on a developer making a typo. Dependency confusion requires knowledge of internal package names. Slopsquatting requires neither. The LLM itself generates the exact package name the attacker has weaponized, and the developer has no obvious reason to question a recommendation from their coding tool. The trust boundary violated is Developer → AI assistant → Registry, a relationship that did not exist before AI-assisted development became widespread.

Defensive Frameworks

How much of supply chain security this section covers

Software supply chain security is a field, not a section. What follows is the working vocabulary we need to reason about dependency risk: the trust boundaries, the main attack vectors, and the frameworks that exist to address them. It is deliberately a survey.

What it leaves out is most of the practice: provenance and attestation in depth, reproducible builds, artifact signing and key management, SBOM generation and consumption at scale, vendor risk assessment, and the operational work of keeping any of it current. Each of those is a subject in its own right. NYU offers a dedicated software supply chain security course, and it is the natural next stop for anyone this section leaves curious. What we want from these pages is the vocabulary, so that when we meet that material it reads as familiar ground rather than a new field.

How the Defensive Frameworks Fit Together

The defensive frameworks are complementary; each addresses a different trust boundary. Here is how they map to attack vectors and what each does operationally.

OpenSSF Scorecard

Automated health check for open-source projects from the . Scores 18+ supply chain practices on a 0-10 scale.

  • Checks: branch protection, CI tests, code review, signed releases, dependency update behavior
  • Use: scorecard --repo=github.com/owner/project before adopting a dependency
  • Boundary: Developer → Registry

Keyless artifact signing that makes publisher identity verifiable without managing long-lived keys.

  • How: developer authenticates via GitHub/Google, receives a short-lived certificate from , signs the artifact, and the event is logged in
  • Detects: unknown identities publishing releases (as Right9ctrl did with event-stream)
  • Boundary: Developer → Maintainer

SLSA

: four levels (L0-L3) of build integrity assurance.

  • How: at L2+, the build service generates authenticated provenance recording source commit, build system, and inputs
  • Detects: build tampering (the Codecov script modification would have failed provenance or shown an unexpected input)
  • Boundary: Build System → Source

SBOM

A machine-readable inventory of every component in your software, in . Does not prevent attacks. Enables the response question: "Are we affected?"

  • Use: when a compromised package is identified, query "Do any of our products include component X at version Y?" instantly instead of investigating for days
  • Boundary: cross-cuts all trust boundaries

How They Combine

Scorecard informs adoption decisions (which dependencies to take). Sigstore verifies publisher identity (who released this artifact). SLSA verifies build integrity (how the artifact was produced). SBOM enables incident response (what is affected when something goes wrong). No single framework covers all four trust boundaries.

Common Misconceptions

  1. "Supply chain attacks only affect open-source software." The 3CX compromise involved two proprietary software vendors. The Codecov breach affected both open-source and proprietary CI/CD pipelines.
  2. "SBOMs solve supply chain security." SBOMs provide inventory, not integrity guarantees, vulnerability remediation, or completeness assurance. An SBOM is an input to a vulnerability management process, not a substitute for one.
  3. "If a package is on the official registry, it must be safe." Most registries do not perform security review of published packages. Malicious packages regularly appear on npm, PyPI, and other registries. Industry reports have documented hundreds of thousands of new malicious packages published per year, and the trend is accelerating.

Detection Timelines

Notice the detection timelines: about two and a half months (event-stream), about two months (Codecov). Supply chain compromises often persist for extended periods because the malicious code arrives through trusted channels. The 3CX case was caught within weeks because endpoint security vendors, CrowdStrike among them, flagged malicious behavior from the signed 3CX desktop app. Detection required active monitoring, not passive trust.

Trust Boundary Analysis

You are reviewing the supply chain security posture of a web application with: 5 direct dependencies in requirements.txt pulling approximately 40 transitive dependencies; built using a GitHub Actions CI pipeline; a third-party monitoring service that injects a JavaScript snippet into production pages; no SBOM generated; no dependency signing verified.

Identify three distinct trust boundaries in this setup. For each:
(1) Name the trust boundary
(2) Name one specific attack vector from this section that could exploit it
(3) Name one defensive mechanism (SBOM, SLSA, Sigstore, Scorecard, or a process control) that would reduce the risk.

Example answer for one boundary: Trust boundary = "Developer → Registry" (for the 40 transitive dependencies). Attack vector = dependency confusion or typosquatting. Defensive mechanism = dependency pinning with hash verification, or OpenSSF Scorecard evaluation of direct dependencies before adoption.

Other boundaries include: "Build System → Source" (GitHub Actions CI pipeline; attack vector: CI/CD script modification as in Codecov; defensive: SLSA provenance generation at L2+); "Consumer → Vendor" (third-party monitoring service injecting JavaScript; attack vector: vendor compromise as in 3CX; defensive: Subresource Integrity (SRI) hashes on the script tag, vendor security assessment, or SBOM inventory of third-party scripts).
