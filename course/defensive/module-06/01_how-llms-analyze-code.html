Driving Question

When an LLM reviews source code for security vulnerabilities, what is it actually doing, and how does that differ from what a dedicated static analysis tool does?

1

The Learning Question

A vulnerability caught during development is a quick fix; the same vulnerability discovered in production can compromise an entire organization. The question is not whether to review code for security. It is how to do it effectively at scale, given that expert human reviewers are scarce, expensive, and subject to fatigue.

AI-assisted code review is increasingly presented as the answer to this scaling problem. But if you do not understand the mechanism behind the tool, you cannot reason about when to trust it, when to doubt it, or how to design a review process that accounts for its blind spots. This section covers that mechanism and compares it against the two established approaches to automated code analysis.

How LLMs, SAST, and CWE Fit Together

How LLMs Approach Code Analysis

When you ask the course model to review a code snippet for vulnerabilities, the model does not compile the code, build a syntax tree, trace variable values through execution paths, or formally verify any property of the program. Instead, it performs against the statistical distributions it learned during training.

The model has been trained on vast quantities of source code, including repositories with known vulnerabilities, commit histories containing security fixes, and security-related documentation. From this data, it has learned correlations: code structures that tend to co-occur with vulnerability labels, and code structures that tend to co-occur with safe labels. When it encounters new code, it estimates the probability that the code resembles patterns it associates with vulnerability.

This is a different kind of operation from what tools do. The LLM is answering the question: "Does this code look like vulnerable code I was trained on?" That is a probabilistic claim based on pattern similarity, not a formal statement about what the code actually does at runtime.

The LLM analysis pipeline can be summarized in three stages.

  1. 1

    Tokenize

    Source code is broken into subword tokens. The model has no concept of "variables" or "functions," only statistical units derived from training-data segmentation. A single identifier like executeQuery may be split into multiple tokens.

  2. 2

    Pattern Match

    The token sequence is compared against statistical distributions learned during training. The model identifies structures that co-occur with vulnerability labels in its training data. This is correlation, not causation. The model does not reason about why a pattern is dangerous.

  3. 3

    Classify & Explain

    Matched patterns are mapped to CWE categories and natural-language explanations are generated. The explanation quality depends on how well the training data associated code patterns with CWE labels. The model can produce plausible-sounding explanations for incorrect classifications.

Where This Mechanism Breaks Down

Because the LLM operates through pattern recognition rather than formal reasoning, it has structural limitations that prompt engineering cannot fix.

The biggest practical limitation is the : the maximum amount of text the model can process in a single pass. Real codebases are far too large to fit in one pass, so the code must be split into chunks. If a vulnerability spans multiple files and the source (where untrusted data enters) and the sink (where dangerous operations occur) land in different chunks, the LLM will never see both endpoints together. It cannot connect the dots across chunks it processes separately.

Semantic Code Analysis Engines

The cross-file limitation of LLMs raises a natural question: what kind of tool can trace data flows across file boundaries? The answer is semantic code analysis engines: tools that build a formal model of the entire codebase before querying it for vulnerability patterns.

These engines work by compiling the source code into an intermediate representation (typically a combination of abstract syntax trees, control-flow graphs, and data-flow graphs) and then running queries against that representation. Unlike pattern matchers that scan for textual patterns, semantic engines understand program structure: they can follow a variable through function calls, conditionals, and file imports to determine whether untrusted data ever reaches a dangerous operation without sanitization.

Several semantic analysis engines are used in industry, each with different strengths. CodeQL (GitHub) compiles code into a relational database you can query with a SQL-like language. Snyk Code, Fortify, and Coverity take different approaches but share the same goal: tracing data flow across function calls and file boundaries with formal rigor.

The common thread is a tradeoff. These tools require more setup (a buildable codebase, query expertise) but in return they produce formal proofs that a taint path exists, rather than probabilistic guesses about code similarity.

Beyond context window constraints, LLMs also lack formal reasoning about program semantics: they cannot determine what values a variable holds at a specific execution point. They produce non-deterministic results, meaning repeated analysis of the same code may yield different findings. And their knowledge is bounded by their training data quality and cutoff date. We will put numbers on these limitations in Section 2, where we measure how well LLM code review actually performs and discover that many of the published accuracy numbers are built on shaky ground.

The CWE Taxonomy

The taxonomy describes weaknesses at different levels of abstraction. Class-level entries, such as CWE-20 (Improper Input Validation), describe broad categories of weakness. Base-level entries, such as CWE-79 (Cross-Site Scripting) or CWE-89 (SQL Injection), describe specific weakness patterns with their own detection and prevention guidance. Variant-level entries describe particular manifestations of a base weakness in a specific language or technology. Entries are also linked by parent and child relationships, but those links do not always run through the broad class you might expect: in MITRE's current research view, CWE-89 sits under CWE-943 and the injection family (CWE-74), not under CWE-20.

The level of abstraction matters for practical classification. When you map a vulnerability finding to a CWE entry, you should select the most specific applicable entry. Mapping a finding to CWE-20 when the weakness is clearly CWE-89 is too broad to be actionable. A developer who receives a finding labeled CWE-20 does not know what to fix. A finding labeled CWE-89 tells them exactly what category of weakness they are dealing with and where to look for remediation guidance.

The 2025 CWE Top 25 Most Dangerous Software Weaknesses ranks weakness types by prevalence and severity. You will see several of them throughout this module, including CWE-79 (Cross-Site Scripting), CWE-89 (SQL Injection), CWE-352 (Cross-Site Request Forgery), and CWE-862 (Missing Authorization).

CWE versus CVE

CWE describes a weakness type (abstract and reusable across products). describes a specific vulnerability instance (concrete, tied to a particular product and version). One CWE can encompass thousands of CVEs. In this module you classify weakness types using CWE.

Three Approaches to Automated Code Analysis

Pattern-based uses declarative rules to match code against known-bad patterns. Fast, deterministic, zero false negatives for covered patterns. Coverage equals the set of rules written. Category exemplified by Semgrep.

Answers: "Does this code match a known-bad pattern?"

Builds a queryable database of the codebase's abstract syntax tree, data-flow graph, and control-flow graph. Enables inter-procedural taint analysis: tracing data flow across function calls, through conditionals, across files. Requires a buildable codebase and query-language expertise. Category exemplified by CodeQL.

Answers: "Does data flow from this untrusted source to this sensitive sink without sanitization?"

Processes code as a token sequence, matching against patterns from training data. Handles novel patterns, multiple languages, and generates natural-language explanations. No formal model of semantics. Non-deterministic. Knowledge frozen at training cutoff.

Answers: "Does this code look like vulnerable code I was trained on?"

The Real Question

Each approach catches things the others miss. No single approach is sufficient. The question is not "which tool is best?" but "how do you combine them?"

Three Tools, One Vulnerability

@app.route('/search')
def search():
    query = request.args.get('q')
    sql = "SELECT * FROM products WHERE name LIKE '%" + query + "%'"
    results = db.engine.execute(sql)
    return render_template('results.html', results=results)

This code takes a user-supplied search query from the URL parameters and concatenates it directly into a SQL statement without sanitization. This is CWE-89: Improper Neutralization of Special Elements used in an SQL Command (SQL Injection).

1

Pattern-Based SAST

Finds it

Mechanism
Flags line 4: execute() receives an argument built by string concatenation with a variable.
Strength
Matches the structural pattern instantly. Fast, deterministic.
Limitation
Does not trace where query came from. No source-to-sink analysis.
2

Semantic-Query SAST

Traces it

Mechanism
Builds a data-flow graph: request.args.get('q') → query → string concat → db.engine.execute().
Strength
Verifies no sanitization between untrusted source and sensitive sink. Formal taint path.
Limitation
Requires a buildable codebase and query-language expertise.
3

LLM Review

Explains it

Mechanism
Identifies CWE-89, generates natural-language explanation with attack example.
Strength
Handles novel patterns, multiple languages, produces readable explanations.
Limitation
Has not formally verified the taint path; recognized a pattern from training data. May miss subtler variants.

Notice the difference. The pattern-based tool found the structural match but did not trace the source. The semantic-query tool traced the full data-flow path from untrusted input to dangerous operation. The LLM generated a useful explanation and correct classification, but without formal verification. All three caught this straightforward case, but they would not all catch more complex variants where the vulnerability spans multiple files or hides behind layers of abstraction.

Common Misconceptions

  1. "Static analysis tools and LLMs do the same thing." Different mechanisms, different false positive and false negative profiles. Research shows that combining them yields 17-60% improvement in F1 (a score that balances precision and recall, covered in detail in Section 2).
  2. "CWE and CVE are the same thing." CWE = weakness type, CVE = specific instance.
  3. "If the LLM identifies a vulnerability, it must be real." LLMs produce both false positives and false negatives.

The comparison above used one straightforward case that all three tools caught. This lab varies the same vulnerability until they stop agreeing, which is where the differences between pattern matching and analysis actually show.

A = CWE-79 (Cross-Site Scripting).

B = CWE-639 (Authorization Bypass Through User-Controlled Key), a base-level entry: the user changes an ID they control to reach another user's record. CWE-862 (Missing Authorization) is defensible but is a class-level entry, and CWE-284 (Improper Access Control) is broader still.

C = CWE-502 (Deserialization of Untrusted Data).

The key skill is selecting the most specific applicable entry rather than defaulting to a broad class-level entry like CWE-20.

Test Your Understanding

Knowledge Check

An LLM reports that a code snippet is "safe" after security review. Which is the best interpretation?

Knowledge Check

When mapping a code weakness to a CWE entry, why is CWE-20 (Improper Input Validation) usually a poor choice?

CWE-20 is a broad, class-level entry. Most weaknesses that involve handling untrusted input have a more specific base-level entry that describes them better (CWE-79, CWE-89, CWE-502, and so on). Mapping to the broad entry when a more specific one applies makes the finding less actionable; a developer told "improper input validation" does not know whether they are dealing with SQL injection, XSS, or something else.
