Metrics for Code Review

Applying the Metrics Framework to Code Review

The confusion matrix framework (true positives, false positives, true negatives, false negatives) applies to code review the same way it applies to log classification or any other detection task. The math is identical. What changes is the interpretation, because the consequences of getting it wrong look very different in a developer's workflow than they do in a SOC.

Four metrics define how you evaluate LLM code-review performance:

  • : Of known vulnerabilities in the answer key, what fraction did the LLM identify? Example: 3/4 = 75%.
  • : Of all findings the LLM reported, what fraction were real vulnerabilities? Example: 3/5 = 60%, so 2 of 5 findings (40%) were spurious. This is not the false positive rate from Module 4, which divides false positives by all safe items; a list of findings does not tell you how much safe code was reviewed, so precision is the measure you can compute here.
  • : 1 minus detection rate. Fraction of known vulnerabilities the LLM missed.
  • : Of correctly detected vulnerabilities, fraction mapped to correct entry. Example: 2/3 = 67%.

Why the Consequences Differ from SOC Triage

The precision-recall tradeoff plays out differently in code review than it does in triage, and the difference matters.

False positives erode developer trust. Developers encounter AI-flagged findings that turn out to be non-issues. If frequent, developers begin ignoring or disabling security tooling. Unlike SOC analysts whose primary job is investigating alerts, developers view security alerts as interruptions. Their tolerance for false positives is lower, and the consequence is tool abandonment.

False negatives create false confidence. When the LLM reports no findings, there is a natural tendency to interpret this as "the code is safe." That converts a tool limitation into a human judgment error, and as you will see below, the overconfidence problem is even worse than you might expect.

When the Measurements Fail

The evidence base evolved in three stages.

  1. 1

    Pre-2024 Benchmarks

    Early vulnerability detection benchmarks reported 90%+ accuracy, creating expectations that AI could reliably find vulnerabilities. These numbers were taken at face value and drove adoption decisions.

  2. 2

    The PrimeVul Re-evaluation (2024)

    Researchers re-evaluated those benchmarks and found that only 25% (BigVul) to 60% (DiverseVul) of the functions labeled "vulnerable" were actually vulnerable, and that many test functions were exact copies of training functions. On a rigorously built benchmark, model performance collapsed, and in the strictest evaluation setting even large models performed close to random guessing. Much of the earlier success came from the data the models were measured against.

  3. 3

    The Overconfidence Study (2023)

    A controlled experiment found that developers using AI code assistants wrote less secure code while believing it was more secure. AI assistance increased both output and false confidence simultaneously.

The Dataset Quality Crisis: PrimeVul

A key finding in AI-assisted vulnerability detection came not from testing a new model, but from testing the tests themselves.

Researchers examined the datasets used to benchmark LLM vulnerability detection, including widely used collections like , CVEfixes, DiverseVul, and the -based CodeXGLUE set, which had been cited across dozens of published studies. They found pervasive quality problems: mislabeled examples (in BigVul, only 25% of the functions labeled vulnerable were actually vulnerable), data leakage (12.7% of BigVul's test functions were exact copies of training functions, which artificially inflates measured performance), and over-broad positive labels.

They then built from the same sources (BigVul, CrossVul, CVEfixes and DiverseVul) with three changes: labels that were checked far more rigorously, duplicate functions removed, and a chronological split so that the test code is newer than the training code. The results were dramatic. A state-of-the-art 7B-parameter model that scored 68.26% on BigVul scored only 3.09% F1 on PrimeVul. Same model, same kind of code. What changed was the quality and separation of the data it was measured on.

What does this mean for you? Much of the published evidence for LLM vulnerability detection capability is built on unreliable measurements. That does not mean LLMs cannot detect any vulnerabilities; they demonstrably can. It means we lack reliable measurements of how well they do it. The training data quality problem is currently one of the strongest binding constraints on performance.

Do not take published benchmark numbers at face value. Ask what dataset the measurement was performed on, how the ground truth was established, and whether data leakage was controlled.

Developer Overconfidence with AI Assistance

A controlled experiment in 2023 found that participants with access to an AI code assistant wrote less secure code than the control group, while being more confident that their code was secure.

Think about what that means. The AI assistant generated plausible-looking code with subtle vulnerabilities. Developers, trusting the AI's output, were less likely to scrutinize it. The result was more vulnerabilities produced with greater confidence. That combination is worse than either problem alone.

Confirmation Bias in AI Code Review

Preprint: not yet peer reviewed

The study described below has not yet undergone peer review. Specific numbers should be treated with caution. The finding is included because the mechanism it describes is important to understand, but treat the magnitudes as preliminary.

Early-stage research is beginning to examine whether LLMs are susceptible to framing effects during code review. The core question: if code is accompanied by comments suggesting it has already been reviewed or sanitized (such as // sanitized input, reviewed by security team), does the model become less likely to flag real vulnerabilities?

Initial findings suggest the answer is yes. While specific magnitudes are still being validated through peer review, the mechanism is worth understanding now: if an attacker can shape the context surrounding vulnerable code, they may be able to reduce AI detection rates systematically. This is an active area of research, and the numbers will sharpen over time, but the underlying risk is concrete enough to inform how we think about AI-assisted review.

Metrics in Practice

  1. 1

    Assemble Ground Truth

    Curate a labeled dataset of code with verified vulnerability status. PrimeVul showed this step is where most benchmarks fail.

  2. 2

    Run Detection

    Apply the tool (LLM, SAST, or combined) to the . Record every finding and every missed vulnerability.

  3. 3

    Compute Metrics

    Calculate precision (what fraction of flagged items are real), recall (what fraction of real vulnerabilities were found), and F1 (harmonic mean of both).

  4. 4

    Interpret with Context

    A high F1 on poorly labeled data is meaningless. Metrics must be interpreted against the ground-truth quality established in step 1.

Step 3: Metrics

CWE Accuracy = 2/3 = 67%. Of the three true positives, two had the correct CWE.

Step 4: Interpretation

Finding 3 (wrong CWE): CWE-20 (improper input validation) is a broad, class-level entry; CWE-502 (deserialization of untrusted data) is the specific, base-level entry for this weakness. A developer told "improper input validation" does not know they are dealing with insecure deserialization. The remediation guidance for CWE-20 is too generic; CWE-502 points directly to deserialization-specific defenses.

Finding 4 (false positive): The developer investigates line 7, finds no hardcoded credentials, wastes time. If this keeps happening, developers start ignoring the tool entirely, eroding trust.

Missed #4 (false negative): The missing authorization vulnerability goes undetected. Attackers could access unauthorized resources while the team believes the code was fully reviewed.

Common Misconceptions

  1. "PrimeVul means LLMs cannot detect vulnerabilities." Overstates the finding. Real capability is somewhere between 3% and 68%; we simply lack reliable measurements to pin it down.
  2. "If the AI sounds confident, it is probably correct." The overconfidence study showed the opposite. Authoritative tone does not correlate with accuracy.
  3. "High false-positive rates are acceptable because you catch more." Counterproductive. Developers disable tooling they do not trust. A tool with 90% recall whose findings are 80% false (20% precision) catches fewer vulnerabilities in practice than a less sensitive tool that developers actually use.

Knowledge Check

A developer says: "The AI reviewed my code and found nothing; it's clean." What is wrong with this reasoning?

LLM false negatives are common and vary by vulnerability type. A clean AI review result means the code did not match learned vulnerability patterns; it does not guarantee absence of vulnerabilities. The model may miss vulnerabilities that require semantic reasoning, span multiple files, or belong to classes outside its training distribution. As the overconfidence study showed, the developer's confidence in the tool may well exceed the tool's actual reliability.
