1

Trust Calibration

The Module's Synthesis

AI is both a useful tool and a source of risk in security contexts. The evidence does not support either blanket trust or blanket distrust. It supports calibrated trust that varies by context.

✓

What AI Code Review Can Do

supported by evidence

Pattern Recognition
Identify code structures that resemble known vulnerability patterns across multiple languages simultaneously.
Natural-Language Explanation
Generate developer-readable explanations of findings, lowering the expertise barrier for triage.
Complement SAST Coverage
Catch novel patterns that rule-based tools miss, improving combined F1 by 17-60% when layered with traditional SAST.
Scale
Review code at speeds and volumes that human reviewers cannot sustain.
✗

What AI Code Review Cannot Do

structural limitations

Formal Verification
Cannot prove the absence of vulnerabilities. A "clean" result means no patterns matched, not that the code is safe.
Cross-Boundary Analysis
Cannot trace data flow across context window boundaries. Large codebases require chunking that breaks inter-procedural analysis.
Novel Vulnerability Classes
Cannot detect vulnerability types not represented in training data. Knowledge is frozen at training cutoff.
Replace Human Judgment
Cannot determine whether a finding is exploitable in a specific deployment context. As Section 2 showed, AI assistance actually increases false confidence.

Trust Calibration Framework

Calibrated trust is a structured process: verify performance against ground truth, layer defenses so each compensates for the others' blind spots, and communicate limitations honestly.

  1. 1

    Verify Ground Truth

    Before trusting any AI code review tool, establish baseline accuracy against a verified dataset. As the PrimeVul study showed, published benchmarks are unreliable. Test against your own codebase with known vulnerabilities.

  2. 2

    Layer Defenses

    Never rely on a single tool. Combine pattern-based SAST, semantic-query SAST, and LLM review so each compensates for the others' blind spots. The NIST SSDF PW practice group requires multiple verification methods.

  3. 3

    Communicate with Calibration

    When reporting AI-assisted findings, state what the tool checked, what it cannot check, and its measured precision (the share of its findings that turned out to be real). The overconfidence problem applies to teams, not just individual developers.

Responsible Communication of Limitations

If you deploy AI code review in an organization, or recommend it to colleagues, communicate clearly what it can and cannot do. The UK NCSC puts it plainly: finding vulnerabilities does not automatically improve security. An organization that increases its detection count without building the process to remediate and learn from findings has not improved its security posture.

When communicating about AI review capabilities to non-technical stakeholders, avoid both extremes: "AI reviews all our code" (implies completeness that does not exist) and "AI code review doesn't work" (ignores genuine utility). Instead: "AI review catches common vulnerability patterns and generates useful explanations, but it misses categories of flaws that require human judgment, its performance varies by vulnerability type, and published accuracy numbers likely overestimate real-world performance."

Reflection Exercise

Think through this position question:
"What should a security team communicate to its developers about the capabilities and limitations of AI-assisted code review?"
Your statement must cite at least two specific findings from this module (e.g., the F1 drop when benchmarks are properly labeled, the developer overconfidence effect, the confirmation bias finding, slopsquatting predictability, the 17-60% F1 improvement from combined approaches). Do not generalize ("AI has limitations"). Try to hold yourself accountable to be specific about what the evidence shows.

A strong response should include specific evidence, e.g.: "Security teams should tell developers that AI code review catches common vulnerability patterns and, when combined with static analysis, improves detection rates by 17-60%. However, when benchmark datasets were rigorously re-labeled, published accuracy (68% F1) dropped to 3%, meaning vendor-reported numbers likely overstate real-world capability. A controlled experiment found that developers with AI assistance wrote less secure code while feeling more confident, so a clean AI review should never be interpreted as proof the code is secure. AI review should be treated as one layer in a multi-layer review process, not a replacement for human expert review of security-critical paths."

Instruction/Completion Pairs for Fine-Tuning

The LLMs you have been evaluating throughout this course are general-purpose models. They were trained on broad internet text, not specifically on your organization's codebase or your preferred vulnerability taxonomy. is the process of taking a pre-trained model and training it further on a narrower, task-specific dataset so that it performs better on that task. One common technique, LoRA (Low-Rank Adaptation), makes this feasible without retraining the entire model.

The key input to fine-tuning is a dataset of : examples of the task you want the model to perform, paired with the correct output for each example. The code-review work from this module provides natural material for building those pairs.

An instruction/completion pair for code review consists of:

Instruction: A prompt describing the code-review task, including the code to review and the expected output format.

Completion: The correct output: the vulnerabilities that should be identified, their CWE mappings, descriptions, and recommended remediations.

Worked Example: SQL Injection

Consider this vulnerable Flask endpoint:

@app.route('/search')
def search():
    query = request.args.get('q')
    sql = "SELECT * FROM products WHERE name LIKE '%" + query + "%'"
    results = db.engine.execute(sql)
    return render_template('results.html', results=results)

From this code, you construct the instruction, a prompt that describes the review task and embeds the code:

The Instruction

Review the following Python/Flask code for security vulnerabilities. For each
vulnerability found, provide: the affected line(s), the CWE identifier, a
description of the weakness, and a recommended remediation. Format as JSON.

@app.route('/search')
def search():
    query = request.args.get('q')
    sql = "SELECT * FROM products WHERE name LIKE '%" + query + "%'"
    results = db.engine.execute(sql)
    return render_template('results.html', results=results)

And the verified completion, the correct output that the fine-tuned model should learn to produce:

The Verified Completion

{
  "findings": [
    {
      "lines": "4-5",
      "cwe_id": "CWE-89",
      "cwe_name": "SQL Injection",
      "description": "User input from request.args.get('q') is concatenated
        directly into a SQL query string on line 4 and passed to
        db.engine.execute() on line 5 without parameterization or
        sanitization. An attacker can inject arbitrary SQL commands
        through the 'q' parameter.",
      "remediation": "Use parameterized queries:
        db.engine.execute('SELECT * FROM products WHERE name LIKE %s',
        ['%' + query + '%']). This separates the SQL structure from
        user data, preventing injection."
    }
  ]
}

The PrimeVul Connection

The quality of your fine-tuning data is bounded by the quality of your labels. If the completion contains an incorrect CWE mapping (e.g., the over-broad CWE-20 instead of CWE-89), a missed vulnerability, or a false positive, you are teaching the model to reproduce that error. The same dataset quality problem that collapsed benchmark scores from 68% to 3% in Section 2 applies here. Every completion must be verified against the answer key before inclusion in the fine-tuning dataset.

Quality Gate

Ask: would you be satisfied if the fine-tuned model produced exactly this output? If the model produced CWE-20 instead of CWE-89, or said "line 3" instead of "lines 4-5," or suggested "input validation" instead of parameterized queries: those are errors in the completion that the fine-tuned model would learn to reproduce.

Common Misconceptions

1. "Fine-tuning on model-generated labels is safe as long as the output looks reasonable." The benchmark quality crisis applies directly: models trained on noisy labels learn noisy boundaries. "Looks reasonable" is not the same as "verified against ground truth."

2. "AI is either useful or dangerous: pick one." It is both. AI code review provides detection capability with measurable but bounded reliability, and introduces new attack surfaces through hallucination-based supply chain risks. That is not a contradiction; it is a tool with specific capabilities and specific failure modes.

What Carries Forward: Data Quality and ML Supply Chains

Why Fine-Tuning Data Quality Matters Now

The instruction/completion pairs from Section 2 matter. When organizations fine-tune models for vulnerability detection, the quality of those pairs directly determines what the model learns. Sloppy CWE mappings, missed findings, or unverified labels in the training set produce a model that confidently reproduces those same errors at scale. The PrimeVul benchmark collapse (68% F1 down to 3%) is a preview of what happens when fine-tuning data inherits the same labeling problems.

Evaluating AI output against verified ground truth, applying structured CWE taxonomies, and catching false confidence, helps us separate useful fine-tuning data from noise.

From Software Supply Chains to ML Supply Chains

The supply-chain vocabulary from Section 4 (dependency confusion, typosquatting, maintainer compromise, build system compromise, SBOM) maps directly to ML-specific supply chains. Model repositories like Hugging Face function analogously to package registries. Poisoned models, malicious plugins for AI frameworks, and compromised training data pipelines are structural equivalents of the software supply chain attacks covered here. The attack patterns are identical; only the supply chain is different. Module 10 takes this up directly: its ML supply chain section works the same trust-boundary vocabulary against model files, weights, and plugins, so the terms you have just learned are the terms it starts from.

Test Your Understanding

Knowledge Check

A company is constructing LoRA fine-tuning data from code-review tasks. They include an instruction/completion pair where the completion contains a CWE mapping that the model originally generated, without verifying it against the answer key. What is the risk?

Open Question

Explain in 2-3 sentences how the software supply chain attack vocabulary from this module (dependency confusion, typosquatting, maintainer compromise) maps to ML-specific supply chains. What is the ML equivalent of typosquatting on a package registry?

In ML supply chains, model repositories (like Hugging Face) function analogously to package registries. The ML equivalent of typosquatting is publishing a malicious model with a name similar to a popular model, for example, "bert-base-uncased-v2" mimicking "bert-base-uncased." The ML equivalent of maintainer compromise is gaining control of a legitimate model's repository to publish a poisoned version. The ML equivalent of build system compromise is tampering with training data pipelines to inject backdoors into models during training. The structural patterns are identical; what flows through the supply chain (packages vs. models vs. training data) differs.
