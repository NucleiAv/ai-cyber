How to get output a security pipeline can consume automatically, how to guarantee that output is structurally valid, and how to decide whether a prompt is ready for production.

1

Why Machine-Usable Output Matters

So far your prompt's output has been for a human to read. Real security automation needs output a machine can read: a correlation rule in a , a ticketing system, or a threat-intelligence platform. That means , typically , with defined fields.

This section covers the difference between asking for JSON (which often breaks) and constraining the model so the output is guaranteed to be valid. It then uses a real standard, , as a realistic target for your output, and ends with the most important caution: structurally valid output is not the same as factually correct output.

2

Two Ways to Get Structured Output

There are two approaches to getting JSON from a model. They look similar from the outside, but the guarantees they provide are fundamentally different.

Approach 1: Requested output (ask for it in the prompt)

In Section 1 you built a structured prompt with a role, a task, and an output contract that said "respond with one word only." That output contract was the simplest version of requested output: you told the model what shape of answer to produce. Now you are doing the same thing, but the shape is more complex. Instead of a single word, you are asking for a JSON object with named fields. The principle is identical. You describe the structure you want inside the prompt text, and the model tries to follow it.

Here is the Section 1 triage prompt evolved into a JSON request. Notice it still has the same pieces (system role, task, delimiter), but the output contract now specifies fields and types instead of a single word:

# System instruction
You are a SOC triage assistant. Classify the SSH log line provided.
Respond with a JSON object containing exactly these fields:
  - "label": one of "benign", "suspicious", "malicious"
  - "source_ip": the IP address from the log line
  - "confidence": one of "low", "medium", "high"
Output only the JSON. No explanation, no markdown fences.

# User message
<<<LOG
Mar 14 02:17:09 web01 sshd[20447]: Failed password for invalid user admin from 203.0.113.45 port 4022 ssh2
LOG>>>

This often works. But "often" is not "always." The model may add a friendly sentence before the JSON, wrap it in code fences, omit a field, or trail off. Any of these breaks an automated parser. You have described what you want, but you have not enforced it.

What you might actually get back:

Sure! Here's the analysis you asked for:
{ "label": "suspicious", "source_ip": "203.0.113.45" }
Let me know if you'd like more detail!

That has prose before and after the JSON, and the confidence field is missing entirely. A strict parser fails on it.

Approach 2: Constrained output (enforce it at the runtime level)

works differently. Instead of describing the schema in the prompt and hoping the model follows it, you pass the schema to the runtime as a separate parameter. The runtime then enforces the structure during token generation, before the model can deviate. This is the genuinely new idea in this section: not just asking for structure (which you have been doing since Section 1), but making it impossible for the model to produce anything else.

Compare the API call below to the one you saw in Section 1. The messages list still uses the same role structure (system, user). What is new is the format parameter: a JSON schema that lives outside the prompt and controls token generation directly.

# Python: constrained output via Ollama
import json

# Define the schema separately from the prompt
triage_schema = {
  "type": "object",
  "properties": {
    "label":      {"type": "string", "enum": ["benign", "suspicious", "malicious"]},
    "source_ip":  {"type": "string"},
    "confidence": {"type": "string", "enum": ["low", "medium", "high"]}
  },
  "required": ["label", "source_ip", "confidence"]
}

# Pass the schema to the runtime via the format parameter
response = client.chat(
  model="your-model-name",
  messages=[
    {"role": "system", "content": "You are a SOC triage assistant. Classify the SSH log line."},
    {"role": "user",   "content": "Classify:\n<<<LOG\nFailed password for invalid user admin from 203.0.113.45...\nLOG>>>"}
  ],
  format=triage_schema   # This is where the constraint is enforced
)

The format parameter tells the runtime to mask any token that would violate the schema during generation. The model literally cannot produce output that breaks the structure. No extra prose, no missing fields, no markdown fences.

What you get back:

{"label": "suspicious", "source_ip": "203.0.113.45", "confidence": "medium"}

Every field is present, the values conform to the allowed options, and there is no surrounding text. This is parseable by any JSON parser without cleanup.

How constrained decoding works under the hood

Recall from Section 2 that the model produces one token at a time by sampling from a . Constrained decoding inserts a step before each sample: the runtime checks the schema for what is structurally legal at the current position, and sets the probability of every illegal token to zero.

  1. 1

    Schema says: object must open with {

    Every token except { is masked to zero probability. The model emits {.

  2. 2

    Schema says: first field name must be "label"

    Only the tokens that form "label": are allowed. The model emits the field name and colon.

  3. 3

    Schema says: value must be one of "benign", "suspicious", "malicious"

    The model chooses from these three options based on the prompt context. This is where it makes its classification decision. It picks "suspicious".

  4. 4

    Schema says: close the object with }

    Only } (or the next required field) is allowed. No prose, no apology, no "Let me know if you'd like more detail."

At every step the schema decides which tokens are legal. The model never has the option to break the structure. But notice step 3: the schema forces the model to pick one of the allowed labels, but it cannot force the model to pick the correct one. The model still makes its own judgment call. That is the gap between syntax and semantics.

It guarantees syntax, not semantics

The schema can force source_ip to be a string, but it cannot force that string to be the correct IP, or even a real one. That means you can get output that is perfectly structured, passes every automated validation check, flows cleanly into your SIEM or threat-intel platform, and is still wrong. cannot tell the difference between a real IP extracted from evidence and one the model invented. Every tool that consumes that JSON will treat it as fact. This is the gap between syntax and semantics, and understanding it is essential before you connect any model output to automation.

3

Valid Does Not Mean Correct

Structured output is what lets a model's analysis flow into automation: an object dropped into a threat-intelligence platform, or a JSON verdict feeding a SIEM rule. That is genuinely useful. But it raises the stakes of the problem from Section 3, because a schema-valid object looks trustworthy and flows downstream without a human reading it.

A perfectly formed object whose field contains a hallucinated IP is worse than malformed output. Malformed output fails loudly and someone investigates. A valid object with a fabricated field fails silently and acts on a fiction. The more machine-usable your output, the more rigorously its contents must be verified.

From triage JSON to a STIX indicator

Using the constrained output from the previous example, you can map the triage verdict to a simplified indicator object. This is the kind of object a threat-intelligence platform actually consumes:

{"type": "indicator", "name": "Suspicious SSH source", "pattern_type": "stix",
 "pattern": "[ipv4-addr:value = '203.0.113.45']", "confidence": 50}

This is a reduced subset of the full STIX standard, containing only the fields needed for a basic entry. Now consider a second run that is also schema-valid:

{"type": "indicator", "name": "Known C2 node", "pattern_type": "stix",
 "pattern": "[ipv4-addr:value = '198.51.100.222']", "confidence": 95}

Why the second object is the real lesson

The second object has a higher confidence score (95) and passes . But the IP 198.51.100.222 was never in the original alert. The model introduced it. The name claims this is a node. A teammate scanning JSON sees a clean "Known C2 node" with high confidence and might push it to a .

Only the verification habit from Section 3 catches this: does this IP actually appear in the source evidence? Is it in any authoritative threat feed? The answer to both questions is no. The object is valid JSON, valid STIX, and completely fabricated. Higher confidence made it more dangerous, not more trustworthy.

How to catch fabricated structured output

The example above is not a hypothetical edge case. Any time a model produces structured output that feeds into automation, fabricated content can slip through. Here is a concrete checklist for catching it:

  1. 1

    Trace every identifier back to the source

    Every IP address, domain, hash, or CVE in the output must appear in the input you provided. If the model produced 198.51.100.222 but you fed it a log containing only 203.0.113.45, the value is fabricated. This is a direct text-matching check; no judgment required.

  2. 2

    Cross-reference against authoritative sources

    If the model labels an IP as "Known C2 node," check it against your , , or . A model's assertion is not evidence. The label is only as good as the source behind it, and the model has no source.

  3. 3

    Treat confidence scores as model opinion, not probability

    A constrained schema that allows "confidence": 95 just means the model chose that number from the allowed range. It does not mean there is a 95 percent chance the assessment is correct. Never use a model-generated confidence score as the sole input to an automated decision.

  4. 4

    Automate what you can

    Steps 1 and 2 can be scripted. A post-processing check that diffs every identifier in the output against the input data, and queries a threat-intel API for any new values, turns a manual habit into a . If an identifier fails both checks, flag the output for human review before it reaches downstream systems.

This is a production problem, not a lab problem

In a classroom exercise, you read the JSON yourself and notice the wrong IP. In a production pipeline processing thousands of alerts per hour, no human reads most of the output. Fabricated data that passes schema validation flows silently into blocklists, case tickets, and automated responses. The more you automate, the more you depend on the verification steps above, and the harder the next question becomes: is this model actually ready to run without a human in the loop?

4

Is It Ready for Production?

The cost of getting it wrong

Suppose your iterated, measured, constrained triage prompt scores 85 percent accuracy on your , with most errors being on novel attack patterns. Your CISO asks: can we deploy this?

There is no universal accuracy threshold. The answer depends on what each type of error costs:

1

False Positive

Lower cost

What happens
The model labels a benign event as suspicious. An analyst spends a few minutes investigating and clears it.
Consequence
Wasted analyst time. Manageable at moderate volume.
2

False Negative

Higher cost

What happens
The model labels a real attack as benign. No analyst ever sees it.
Consequence
An intrusion proceeds undetected. Damage can be severe and irreversible.

An accuracy of 85 percent with false-negative-heavy errors on novel attacks is a real risk, because novel attacks are exactly what you most need to catch. To see why, consider what those numbers look like in a real shift:

What "85% accuracy" looks like in one shift

Imagine your model triages 1,000 alerts during a shift. 85% accuracy means 150 wrong calls. Where those errors land changes everything.

850
Correct classifications
These alerts are routed correctly. The model earns its keep here.
150
Wrong classifications
These are the 15%. What kind of errors are they?

Now break down those 150 errors. Where the errors concentrate matters far more than the total count:

~30
False Positives
Benign events flagged as suspicious.
Impact: Analysts waste time investigating clean events. Annoying, but each one is caught and cleared. No security damage.
~120
False Negatives
Real attacks labeled benign. No analyst ever sees them.
Impact: Intrusions proceed undetected. Any one of these could be a breach. This is the dangerous 15%.
1,000 alerts in one shift
850 correct
120 missed
Correct FP (annoying) FN (dangerous)

The same 85% accuracy with errors concentrated as false positives would mean wasted analyst time but no missed attacks. That is a very different risk profile. The number alone does not tell you whether to deploy. The distribution of errors does.

So the question is not "is 85% good enough?" but rather "what role should the model play, and where does a human fit?" This is the question.

Choosing how much autonomy to give the model

There is no single answer to "should a human review this?" It depends on what happens when the model is wrong. The three deployment models below represent a spectrum from full human control to full autonomy. Most real SOC deployments sit somewhere in the middle.

1

Human Decides

Model advises only

How it works
The model processes every alert and suggests a label, but a human analyst reviews each suggestion before any action is taken.
When to use it
High-stakes decisions where a wrong call causes serious harm: blocking production traffic, escalating to law enforcement, suppressing alerts on critical infrastructure.
Tradeoff
Safest, but slowest. If you have 10,000 alerts per day and one analyst, this does not scale. The model saves reading time but not decision time.
2

Human Spot-Checks

Model acts, human audits

How it works
The model acts on high-confidence verdicts automatically. Low-confidence, novel, or borderline cases are routed to a human queue. A random sample of auto-processed cases is audited regularly.
When to use it
When the volume is too high for full review but the consequences of error are still significant. This is the most common model for SOC triage assistance.
Tradeoff
Balances speed and safety, but depends entirely on where you draw the confidence threshold and how large the audit sample is. Set the threshold wrong and you are back to missing attacks silently.
3

Full Autonomy

No human review

How it works
The model classifies and acts without human review. Alerts labeled benign are suppressed. Alerts labeled malicious trigger automated response.
When to use it
Only when the error rate is extremely low on your specific data, the cost of each error type is well understood, and robust monitoring and rollback are in place.
Tradeoff
Fastest, but most dangerous. Every false negative from the accuracy visual above (those 120 missed attacks) proceeds completely undetected. No human ever sees them.

The key question is not "how accurate is the model?" but "what happens when it is wrong?"

A 95% accurate model making low-stakes suggestions (sorting a reading list) can run with full autonomy. An 85% accurate model making high-stakes decisions (suppressing security alerts) needs human review on every consequential action. Accuracy alone does not determine the right deployment model. The cost of each error type does.

What you should not do is read "85 percent" as "production-ready." Operational data sharpens the stakes: false-positive rates in some SOC environments are reported to approach 99 percent, which is why is attractive, and why an assistant that quietly drops true positives is dangerous.

Three prompting modes this module has not used

Everything so far has been text in, text out, with you supplying the data. Three other modes change what goes into the prompt, and each changes the security picture. This is orientation only; the modules named below do the real work.

ModeWhat changes about the promptWhy it matters for security
Multimodal The prompt carries an image, a screenshot, or a document scan alongside the text. Your instructions and the evidence now arrive through different channels. Everything you learned about the instruction and data boundary applies to pixels too, and text inside an image is data your delimiters do not enclose. A screenshot of a phishing email is evidence; the words in it are not instructions.
Retrieval-augmented A retrieval step fetches documents and pastes them into the prompt before the model sees it. You wrote the instructions; a search index chose the data. The data is selected at run time from a corpus you may not control, so the delimiter matters more, not less. Module 11 covers the retrieval attack surface, including what happens when the corpus itself is poisoned.
Adversarial and jailbreak The prompt is written to defeat the model's rules rather than to use them: role-play framings, many-shot priming, encodings the safety training did not cover, and optimized suffixes. These are the offensive use of the same structure you have been building. You cannot evaluate a guardrail without knowing what is thrown at it. Module 9 covers the technique families and the defenses in depth.

The through-line is the one from Section 1: a model reads one sequence, and any channel that can put tokens into that sequence is a channel an attacker may reach. Adding an image or a retriever adds a channel. It does not add a wall.

Assembling your prompt-engineering playbook

This module has built up a set of practices that work together. Before moving to Module 4, capture them as a reusable playbook in your own notes. A strong playbook records:

  • Your standard prompt structure: the role and rules, the task, the output contract, and a delimiter around untrusted data.
  • Your few-shot rules: how you select examples (including boundary cases), the order you fix, and the single format you keep consistent.
  • Your iteration loop: the held-out test set you use, how you measure accuracy and consistency, the one-variable rule, and where you keep the change log.
  • Your verification checklist: which claims you always cross-check (identifiers, scores, IPs, package names) and the authoritative source you check each against.
  • One technique that did not help on the model you are using, and why, so you do not repeat it.

What commonly gets confused

  • "Asking for JSON in the prompt guarantees JSON." It does not. Only constrained decoding, where the runtime enforces a schema during generation, guarantees valid output.
  • "Machine-parseable means any valid JSON." For sharing with other tools, it means conformance to a specific schema (such as STIX 2.1) that consuming platforms expect.
  • "If the output is valid and confident, it is trustworthy." Structural validity and factual correctness are independent. Higher confidence scores do not indicate higher truth. Verify contents.
  • "85 percent accuracy means production-ready." Readiness depends on the cost of the remaining 15 percent, and especially on which types of errors they are.

Try it yourself: design output for an auto-suppress rule

Your SIEM has a rule that will auto-suppress any alert the model labels benign. Think through: would you use requested or constrained output, and why? What fields should the schema include, and what field would you add specifically because of the auto-suppress risk? What rule would you set for which verdicts may trigger auto-suppression? And what would you verify about the model's benign outputs before trusting auto-suppression at all?

  • Constrained output is required, because a malformed verdict must never reach an auto-suppress rule.
  • The schema should include label, confidence, and a rationale or evidence field. The confidence field is specifically needed because of the auto-suppress risk.
  • Only allow auto-suppression when confidence is high, because auto-suppressing a false benign is a silent false negative, the worst possible error in this context.
  • Before trusting any of this, measure the false-negative rate of benign verdicts on a held-out set, since the suppression rule acts on exactly those outputs.
Knowledge Check

Which approach actually guarantees the model's output is valid JSON conforming to your fields?

What is a grammar in this context? A is a formal set of rules that defines exactly which token sequences are legal output. Think of it as a stricter version of a JSON schema: where a schema says "this field must be a string," a grammar says "at this position, the only legal next characters are {, ", or a digit." Some runtimes (like llama.cpp and Outlines) accept a grammar written in or a similar notation. Others accept a JSON schema and convert it to a grammar internally. The effect is the same: the model cannot produce output that violates the rules.

The exercise: Author a custom grammar (or a richer JSON schema) for a multi-object simplified STIX bundle containing an indicator plus a relationship, and validate conformance against the schema using your runtime. Start with the single-object schema from this section and extend it to require both objects in an array.
