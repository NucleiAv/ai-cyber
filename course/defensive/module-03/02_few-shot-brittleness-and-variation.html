Few-Shot Prompting & Why Outputs Vary

Adding examples to a prompt usually improves it, but two properties of language models make a single good-looking run misleading: prompts are brittle, and generation is stochastic.

When "Looking Better" Is Misleading

In Section 1 you built a structured prompt. The next step toward making that prompt more accurate is showing the model examples of the task done correctly. This technique is called , and it usually helps.

But this section is mostly a warning wrapped around a technique, because two properties of language models will undermine your results if you do not account for them:

1

Brittleness

Prompts are brittle: changes that do not change the meaning of your prompt (the order of your examples, the spacing, the separators) can change the answer significantly.

2

Stochastic Generation

Generation is : running the same prompt twice can produce two different answers.

Because of these two properties, a prompt that appears to perform well on one test may not actually be reliable.

2

Few-Shot Examples and the Three Levers

How few-shot prompting works

A few-shot prompt demonstrates the task by including completed examples. You examples like these to your prompt:

Line: Failed password for invalid user oracle from 203.0.113.9 ... -> malicious
Line: Accepted password for deploy from 198.51.100.7 ...           -> benign

The model infers the pattern ("produce a one-word label in that style") and applies it to the new input. This is in-context learning from Section 1: no training happens, the examples just steer the response.

The catch is that the model's behavior is sensitive to changes that should not matter. Research that systematically varied prompt formatting found that changing only (separators, casing, whitespace) moved accuracy by as much as 76 percentage points on one open model with roughly 13 billion parameters. The order of few-shot examples alone can swing accuracy by tens of points, because certain large language models tend to examples near the start or end of the prompt. (This behavior has been documented in specific large language models; it does not necessarily apply to all model architectures or sizes.) None of these changes alter what you meant. They alter what you got.

Few-shot prompting is powerful, but getting reliable results means controlling three variables: which examples you select (including boundary cases), the order you place them in, and the format you use (kept identical across every example and the live input).

Why the same prompt gives different answers

When the model generates text, at each step it computes a probability for every possible next token and then samples one. If is above 0 (or is below 1), that sample is genuinely random, so two runs can diverge. Set temperature to 0 and the model nearly always takes the most probable token, which makes output approximately deterministic. If you also pass a fixed (a number you choose, such as 42) alongside a higher temperature, the model's random-number generator starts from the same point every time, so you get the same sequence of token choices and therefore the same output. This lets you reproduce a specific run for debugging or auditing without being locked into temperature 0.

To make this concrete: when the triage prompt reaches the point where the model must output its label, it might compute something like 55 percent probability for malicious, 40 percent for suspicious, and 5 percent for benign. At temperature 0, the model always picks malicious (the highest probability). At the default temperature, it usually picks malicious but sometimes draws suspicious, which is exactly what the five-run example below demonstrates. Neither answer is "wrong" in the sense of a malfunction; both are valid draws from the model's probability distribution for this input.

A distribution, not a value

At default settings, your prompt does not produce one answer. It produces a distribution of answers. One run is a single sample from that distribution. Judging a prompt from one run is like judging a coin from one flip. This is the foundation of the iteration methodology in Section 3.

3

Brittleness You Can Reproduce

Why this matters for security

  • Silent degradation. A teammate "cleans up" a deployed triage prompt by re-indenting it and swapping the example order. The meaning is unchanged, but accuracy quietly drops. In a SOC, that shows up as missed detections nobody can explain. Brittleness makes undocumented prompt edits a security risk.
  • False confidence from one good run. You test a prompt once, it nails the case, and you ship it. Because output is stochastic, the next 50 alerts may include confident wrong answers you never saw.
  • Reproducibility for investigations. To reproduce exactly what the model said during an incident, you must have controlled temperature and seed. Otherwise your evidence is not reproducible.

Same meaning, different results

Suppose you have a small labeled set of 10 log lines with known-correct classifications. You write a few-shot triage prompt and create three variants that all mean the same thing. Run each variant against the labeled set in the simulation below. The accuracy numbers illustrate the effect; exact values will depend on the model and the run.

Variant V1

Only change: examples ordered benign to malicious.

Accuracy: 7 of 10.

Variant V2

Only change: the same examples, in reversed order.

Accuracy: 5 of 10.

Variant V3

Only change: the separator switched from -> to a newline plus Label:.

Accuracy: 8 of 10.

Now take the best-scoring variant (V3) and run the simulation five times on one ambiguous line: Failed password for root from 192.0.2.51 port 33001 ssh2. The five runs returned: malicious, malicious, suspicious, malicious, suspicious.

What each result tells you

  • V1 versus V2 changed only example order and lost two correct answers. If you judged "V2 looks cleaner" by eye, you might ship the worse prompt. The lesson is not that benign-first is always better (that may not hold on your data). The lesson is that example order is a variable you need to test, not assume.
  • V3 changed only the separator and format, and scored the highest of the three. Same meaning, different result. That is textbook brittleness, and it is why you should fix one format and keep it identical across every example.
  • The five runs on the ambiguous line disagree: three returned malicious and two returned suspicious. Neither malicious nor suspicious is the single "correct" answer from the model's perspective. The prompt produces a distribution of answers. The honest report for this input is "60 percent malicious, 40 percent suspicious across five runs at default temperature." That disagreement is itself useful information: it signals that the log line is genuinely ambiguous.
4

Why Single-Run Testing Fails

Now that you have seen brittleness and stochastic generation in action, here are the misconceptions that most commonly trip people up when working with few-shot prompts.

Common misconceptions

  • "More examples are always better." Beyond a few well-chosen examples, gains flatten and can reverse. Order and format effects start to dominate, and very long example lists run into the effect. Curate carefully rather than piling on more examples.
  • "If two prompts mean the same thing, they behave the same." Brittleness says otherwise. Meaning-preserving changes can change results.
  • "It was wrong once, so the prompt is broken," or the opposite, "it was right once, so the prompt is good." Both of these judge a distribution from a single sample.

Chain-of-thought is largely a large-model behavior

reasoning gains were demonstrated on very large models (roughly 60 billion parameters and up). Small models, those with a few billion parameters, often do not benefit. Adding "think step by step" may produce longer output with no accuracy improvement, and it costs tokens and time. Test it on the model you are using, and treat a as a useful finding, not a failure. A well-known technique can simply not apply to every model.

Tradeoffs to keep in mind

  • Lowering temperature to 0 improves repeatability but reduces useful diversity. Sometimes you want varied samples, for example to measure how often the model agrees with itself (as you will do in Section 3). There is no single correct temperature setting.
  • Format robustness is an active research area. Techniques exist to average over many formats, but no current method makes a small model fully format-insensitive. Brittleness is a property to manage, not a bug you can fix.

Try it yourself: evaluate a colleague's conclusion

Two triage prompts, P1 and P2, contain identical instructions and identical four examples; only the example order differs. P1 scored 8 of 10 on a colleague's test, P2 scored 6 of 10. Your colleague concludes "P1 is the better prompt, ship it." In three or four sentences, state what additional evidence you would require before agreeing, which two procedures from this section you would run to get it, and a specific temperature and seed choice you would use and why.

  • The 8-versus-6 gap could be order-sensitivity noise on a tiny 10-item set.
  • Run each prompt multiple times to estimate variance, and test on a larger or re-labeled set, ideally trying additional orderings too.
  • Use temperature 0 plus a fixed seed for a repeatable head-to-head, while separately running at default temperature to observe variability. Only then can you say "P1 is more reliable" with any confidence.
Knowledge Check

A prompt outputs benign for an alert on Monday and suspicious for the same alert on Tuesday, with no change to the prompt. What is the best explanation?

Take a fixed task and increase the number of few-shot examples from 2 to 8 to 16. Chart accuracy at each level and note where adding more examples stops helping or starts hurting. That is the lost-in-the-middle effect in action.
