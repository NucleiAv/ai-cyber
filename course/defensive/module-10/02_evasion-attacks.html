The Optimization Behind an Adversarial Example

In the previous section, the attack targeted the training data before the model was ever trained. Evasion works differently: it takes the trained model as a given and instead looks for an input the model will misclassify. Say a malware classifier correctly flags a file. An asks: what is the smallest change to this file that makes the classifier call it benign, while the file stays fully functional as malware? The model never changes. Only the input does.

The result of that search is called an . To build one, the attacker looks for the smallest that pushes an input across the model's decision boundary, while the input still works the way it originally worked. In plain terms: change the input as little as possible, in the direction that most reduces the model's confidence in the correct label, without breaking whatever the input needs to keep doing.

When the attacker can see the model's internals, they can compute exactly which direction reduces the correct-label confidence fastest and adjust the input accordingly. This is the white-box case. The perturbation is often imperceptible to a human, maybe a few pixel changes too small to notice, or a handful of altered bytes in a file. To us the input looks the same. To the model it belongs to a different class.

This is where cybersecurity examples are different from image examples. Perturbing a photo only has to keep the photo recognizable. Perturbing malware has to keep the malware functional, a much tighter constraint. An attacker cannot scramble arbitrary bytes in an executable, because most changes would corrupt the program. Instead, the perturbation has to stay in regions that do not affect execution, such as padding or unused code caves, where bytes can be changed freely. After the perturbation, the file still runs, still does its malicious work, but now a byte-based classifier calls it benign.

The animation makes the search look like one smooth slide across the boundary, but do not let that fool you. Working out which features to modify, in which direction, and by how much is a serious optimization problem in its own right, and much of the craft of evasion lives inside it. The entire task can be written as a single compact objective with three constraints. Expand the panel below to unpack that objective piece by piece.

What follows is a recipe an attacker may work from when they tweak a malicious file so a detector waves it through while the file keeps doing everything it did before. Written as one line of math, the whole attack looks like this:

Attacker’s objective minimize ‖δ‖2 subject to
classifier(x + δ) = benign behavior(x + δ) = behavior(x) δ touches editable regions only

The setup

x

The original, malicious file or data, exactly as the attacker starts with it.

δ (delta)

The modification, the “noise” the attacker adds to the file.

x + δ

The newly modified, adversarial file the detector will actually see.

The core optimization goal

minimize ‖δ‖2 The attacker wants to minimize the L2 norm (the ) of the modification. In plain terms: keep the change as small, subtle, and efficient as possible. Massive, messy changes are more likely to break the file or trip other security alarms along the way.

A closer look: what ‖δ‖2 actually means

That one symbol carries the whole idea of “how big is the change,” so it is worth unpacking. The notation ‖δ‖2 is the L2 norm, also called the Euclidean norm or Euclidean length. It measures the total magnitude, the straight-line length, of a vector.

The mathematical formula

If δ is a vector of individual changes, δ = [δ1, δ2, …, δn], the L2 norm squares each component, adds them up, and takes the square root:

‖δ‖2 = √δ12 + δ22 + … + δn2

This is the Pythagorean theorem (a2 + b2 = c2), scaled up to work in any number of dimensions.

Geometric interpretation

Picture δ as an arrow pointing from the original file x to the modified file x + δ. The L2 norm is the exact straight-line distance between those two points. A small ‖δ‖2 means the modified file sits very close to where the original file lived.

Why attackers choose the L2 norm

  • Spreading out the changes. Because it squares each component before summing, the L2 norm heavily penalizes any single large change. Minimizing it pushes the algorithm toward many tiny, near-imperceptible tweaks spread across the file rather than one or two obvious edits.
  • Blending into the crowd. Keeping the Euclidean distance minimal leaves the altered file statistically almost identical to the original, which makes the modification very hard for standard anomaly-detection systems to spot.

The constraints: the rules of the attack

classifier(x + δ) = benignThe evasion goal

The primary objective. When the security model scans the modified file, it must call it safe, “benign,” instead of malicious. Everything else in the recipe exists in service of this line.

behavior(x + δ) = behavior(x)Functionality preservation

The modified file must behave exactly like the original. If the malware encrypted files or stole passwords before, it must still do exactly that afterward. A modification that breaks the payload makes the attack a failure, no matter what the classifier says.

δ touches editable regions onlyStructural constraints

In real file formats, such as Windows executables or Linux binaries, you cannot inject random bytes anywhere without crashing the program. The attacker confines δ to editable regions, unused header space, padding, or slack space, so the file stays structurally valid and runnable.

Putting it together: find the smallest, most precise modification δ that flips the security model’s verdict from malicious to benign, without altering what the malware actually does and without breaking its file structure. Every evasion technique in this section, from padding edits to surrogate-model transfer, is a different way of solving this one optimization problem.

Why Model Access Is Often Unnecessary

A fair question at this point: how useful is any of this if the attacker cannot see inside the target model? In practice, attackers rarely have the target's weights. But they often do not need them, because of a property called . An adversarial example crafted against one model frequently fools another model trained for the same task, even when the two models use different architectures and different training data.

That said, if black-box attacks work well enough, why do security researchers (and nation-state attackers) treat obtaining the model's weights as a priority target? Because having the weights changes the problem from trial and error to exact math. A black-box attacker is guessing which changes might shift the classifier's output, submitting inputs and watching what comes back. A white-box attacker can compute the gradient directly: they know precisely which bytes to change, in which direction, and by how much, to cross the decision boundary with the smallest possible perturbation. The result is more reliable evasion, achieved faster, with fewer modifications to the file. That is why model theft and weight exfiltration are treated as serious security events, and why the distinction between white-box and black-box access shapes how much damage an attacker can do.

The attacker has the target model's internals. They compute the direction that most reduces the model's confidence in the correct label and adjust the input accordingly, arriving at a minimal, precise perturbation. Most published evasion results are white-box because full access makes the math exact.

The attacker has no access to the target's weights or architecture. Instead, they train or obtain a , craft the perturbation against that surrogate, and submit the result to the real target. Because adversarial examples transfer between models often enough to be useful, black-box evasion is practical. This is what makes evasion an operational concern rather than just a lab demonstration.

Why this matters for a security team

Every detector has an , a threshold chosen to balance false positives () against false negatives (). Evasion gives an attacker the ability to produce on demand. The detector is not broken and its threshold is not wrong. The attacker is just producing inputs that are specifically designed to fall on the safe side of the line. This is why a team that trusts a detector's benchmark score without testing how it behaves under adversarial inputs is measuring the wrong thing: the benchmark reports accuracy on ordinary inputs, but evasion uses inputs the benchmark never contained.

Evading a Malware Classifier

Consider a classifier that reads a file as a sequence of raw bytes and predicts malicious or benign. It performs well on a standard test set. Now suppose an attacker has a file the classifier correctly flags as malicious, and the attacker wants to deliver that file without tripping the detector. Think about what the attacker can and cannot do.

  • They cannot retrain or alter the classifier. It is deployed and out of reach. That rules out poisoning and forces an inference-time approach.
  • They cannot rewrite the malicious logic. The file has to keep working. That is the functionality-preserving constraint, tighter than the constraint on an image attack.
  • They confine the perturbation to regions that do not affect execution. Bytes are appended or edited in areas the program never runs, chosen to push the classifier's score below its malicious threshold. Because the attacker lacks the model's internals, they craft the perturbation against a surrogate and rely on transferability to get it to work on the real target.

The result, in detector terms: a file that is genuinely malicious and genuinely functional now gets classified as benign, a false negative. on the ordinary test set is unchanged, which is exactly why the benchmark gave no warning.

Lab results and production are different claims

Most published evasion results are white-box attacks on benchmark datasets under controlled conditions. Evading a production detector in a black-box setting, while keeping a real payload functional, is harder and less certain than a benchmark demonstration suggests. The ongoing back and forth between attackers and defenders is real, and so is the gap between laboratory results and production outcomes.

Why evasion is hard to shut down

One defense is to train a model on adversarial examples so it learns to resist them, a technique called . It helps, but the gains tend to be narrow: a model hardened against one kind of perturbation often remains vulnerable to a different kind, and robustness measured in a lab does not always hold up against an attacker who can adapt. Whether adversarial-robustness research has meaningfully improved real-world model security is still an open question. For a security team, the safer assumption is that a determined attacker will eventually find an evasive input, which means evasion resistance is one layer of defense, not a guarantee by itself. That reasoning leads to the same conclusion as the operating-point discussion above: measure a detector against adversarial inputs, not just clean ones, and do not treat a benchmark score as the final word on how it will perform.

Two things folks often trip up on

The first is assuming that an attacker needs the model's weights to build an adversarial example. However, transferability removes that requirement in many cases! The second is confusing evasion with . Jailbreaking bypasses a model's safety alignment to make it produce prohibited content. Evasion makes a classifier assign the wrong label to an input. They target different things and use different mechanisms.

  • Goal: the smallest change to the input that flips the model's verdict.
