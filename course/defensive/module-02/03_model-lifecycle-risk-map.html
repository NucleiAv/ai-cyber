1

From Behavior Stack to Risk Classification

Section 1 showed how every LLM response begins as probabilistic token selection. Section 2 introduced the behavior stack, the layered sources (pretraining, alignment, fine tuning, system prompts, retrieval, decoding, filters) that shape what the model produces.

This section collapses those layers into three that serve as a practical classification tool. Each stage groups related behavior stack layers, carries a distinct security profile, and calls for a distinct category of controls.

1

Pre training

What is in the data

Risk profile
Memorized PII and credentials, embedded biases, unknown data provenance
Who controls it
The model developer. You cannot change what was trained; you choose which model to use.
Key question
"What might this model have memorized, and what biases might it carry?"
2

Fine tuning

What adaptation does

Risk profile
Alignment compromise, memorization amplification, data extraction from fine tuning sets
Who controls it
The deploying organization. You choose what data goes in and how to test what comes out.
Key question
"If we fine tune on internal data, what are we putting at risk?"
3

Inference

What happens during use

Risk profile
Prompt injection, data exposure across network boundaries, system prompt leakage, fabrication and output variability (covered in Section 5), excessive agency
Who controls it
Your team and end users. The broadest attack surface because it is exposed to external input.
Key question
"What risks exist every time someone interacts with this model?"

Three stages, three owners. The lifecycle framework is useful because each stage maps to a different responsible party. The model developer owns pre training decisions. Your organization owns fine tuning decisions. The operational environment (your team, your users, your deployment configuration) owns inference. When a risk appears, knowing the stage tells you who can actually fix it and what category of control to reach for.

2

Matching Risks to Controls

The lifecycle classification is useful because it determines the category of control that can actually address a risk. Applying the wrong category is a common and costly mistake.

Pre training controls

Operate at the model selection level: reviewing model cards, requiring data provenance documentation, choosing models with documented curation practices.

Fine tuning controls

Operate at the data handling level: sanitizing training data before fine tuning, restricting access to fine tuned models, testing for memorization and alignment degradation.

Inference controls

Operate at the operational level: input validation, output filtering, access controls, monitoring, prompt hardening, secure deployment configuration, source verification and grounding (covered in Section 5), structured output review, and reproducibility settings (fixed seeds, low temperature).

Control Mismatch Errors

Prompt filtering (an inference stage control) cannot fix a memorization problem (a pre training risk). Data sanitization (a fine tuning control) cannot prevent prompt injection (an inference risk). When a control does not seem to work, the first question is whether it targets the correct lifecycle stage.

A security team discovers that their LLM based assistant sometimes outputs fragments of credit card numbers. Which lifecycle stage is the most likely origin of this risk?

Mapping the OWASP LLM Top 10

The is the industry recognized classification system for LLM security risks. OWASP updates this list periodically: entry numbers shift, categories are added or removed, and descriptions evolve. Rather than memorize a snapshot, the goal here is to see how the lifecycle framework organizes these recurring risk categories. The ten entries below represent the risk themes most relevant to cybersecurity practitioners, grouped by the lifecycle stage where each originates. You will work with each category in depth in Modules 9 through 11.

Pre training and Fine tuning Stage Risks

These risks involve data that entered the model before anyone interacted with it. Controls focus on model selection and data handling.

Sensitive Information Disclosure

Model reveals memorized sensitive data from pre training or fine tuning corpora, including PII, credentials, and proprietary content.

Supply Chain Vulnerabilities

Compromised model weights, poisoned datasets, or tampered plugins enter the pipeline before the model is deployed.

Data and Model Poisoning

An adversary manipulates training data to corrupt model behavior, embedding backdoors or biased outputs that persist through deployment.

Misinformation

Fabricated output presented as fact. Section 5 examines the types of hallucination and an operational detection workflow. The risk originates in pre training (statistical patterns, not verified knowledge) and surfaces at inference.

Inference Stage Risks

These risks emerge when users and systems interact with the deployed model. Controls focus on operational security: input validation, output filtering, access controls, and deployment configuration.

Prompt Injection

Adversarial input overrides the model's instructions, causing it to perform unintended actions or reveal restricted information.

System Prompt Leakage

Hidden instructions that define the model's role and constraints are exposed through crafted queries.

Improper Output Handling

Downstream systems trust model output without validation, allowing generated content to trigger unintended code execution or data modification.

Excessive Agency

The model is granted permissions beyond what the task requires, enabling it to take actions with consequences the user did not intend.

Vector and Embedding Weaknesses

The retrieval pipeline returns poisoned or unauthorized content, allowing an attacker to influence model output through injected documents.

Unbounded Consumption

Unconstrained model usage leads to resource exhaustion, denial of service, or runaway costs from unthrottled API access.

A Living List

OWASP updates the LLM Top 10 as the threat landscape evolves. Entry numbers, names, and descriptions change between editions. The risk themes above have appeared consistently across editions because they reflect structural properties of how LLMs are built and deployed. When you return to this topic in Modules 9 through 11, always check owasp.org for the current version.

Model Cards as a Practitioner Tool

A is the primary source of provenance information when evaluating whether to deploy a model. It documents what was done at each lifecycle stage and what the developers consider the model's boundaries. For a security practitioner, it is the starting point for assessing pre training and fine tuning risks before the model ever reaches inference.

When evaluating a model card, two complementary questions structure the review:

✓

What It Reveals

Documented information

Training data
Sources, curation practices, and filtering applied to the pre training corpus
Limitations
Known failure modes, domains where the model underperforms, and documented biases
Intended use
Approved use cases and explicitly out of scope applications
Safety testing
Alignment procedures, red teaming results, and evaluation methodology
?

What to Question

Critical evaluation

Specificity
Is the training data description precise, or does it say only "diverse public data"?
Honesty
Are limitations documented in concrete terms, or are they vague disclaimers?
Adversarial coverage
Does safety testing cover adversarial extraction, jailbreaks, and prompt injection?
Reproducibility
Can benchmark results be independently verified? What is the knowledge cutoff date?

Vagueness is a signal. When a model card describes its training data as "a diverse corpus of publicly available text" with no further detail, you cannot assess memorization risk, bias profile, or whether the training set included credentials, PII, or malicious content. Treat insufficient documentation as a risk factor, not a neutral gap.

Explore on your own: Spend time looking up the model cards for popular models you currently use or plan to use. Compare what each card reveals and what it omits. Pay attention to how training data, limitations, and safety testing are described across different providers. The differences tell you a great deal about each organization's transparency and your ability to assess risk.

Check Your Understanding

Knowledge Check

A model card describes its training data as "a diverse corpus of publicly available text" but provides no further detail about sources, curation, or filtering. From a security perspective, what is the main concern with this level of disclosure?

Scenario

For each scenario below, identify the lifecycle stage where the risk originates, then name the category of control (model selection, data handling, or operational) that addresses it:

(a) An LLM reproduces a verbatim API key from its training data.
(b) A user crafts a prompt that causes the model to ignore its safety instructions.
(c) An organization fine tunes a model on internal HR documents, and the model later reveals employee salary data.

(a) Pre training → Model selection controls. The API key was in the training corpus and was memorized during pre training. Mitigation focuses on choosing models with documented data curation and filtering practices.

(b) Inference → Operational controls. Prompt injection is an inference stage attack. Mitigations include input validation, output filtering, prompt hardening, and system prompt design. These are the controls your team applies at deployment.

(c) Fine tuning → Data handling controls. The HR data was memorized during fine tuning, amplified by the small dataset. Mitigations include sanitizing data before fine tuning (removing PII and sensitive identifiers) and testing fine tuned models for memorization before deployment.
