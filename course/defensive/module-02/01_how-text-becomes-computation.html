How Text Becomes Computation

How your prompts become tokens, how tokens become numerical vectors, how transformer layers transform those vectors through attention to produce predictions, and why security data pays a token tax that general text does not.

Learning Objectives

By the end of this section, you will be able to:

From Text to Tokens

An LLM never sees your text. It cannot process characters, words, or sentences directly. Before anything else happens, a converts your input into a sequence of . These are subword chunks that the model treats as its fundamental units of input.

This is the first stage of how text becomes computation: your prompt is split into a sequence of numerical IDs, and from this point forward, the model operates entirely on those numbers. Understanding this process is essential because it determines how much of your security data actually fits in a single prompt, and what gets lost when it does not.

How Tokenization Works

Tokenizers are built during model training using algorithms like . The algorithm scans the training corpus and identifies which character sequences appear most frequently. Those frequent sequences earn their own entry in the tokenizer's . Common English words like "the," "security," and "network" typically become single tokens. Rare or domain specific text (hexadecimal strings, Base64 payloads, log syntax) gets split into many small fragments because those patterns were uncommon in the training data.

  1. 1

    You type a prompt

    Your input is plain text: a question, a log entry, a block of code.

    Analyze this log: 192.168.1.105 port 443 SYN
  2. 2

    The tokenizer splits it into subword chunks

    Each chunk maps to an ID in the vocabulary. Common phrases stay intact; technical syntax fragments.

    ["Analyze", " this", " log", ":", " 192", ".", "168", ".", "1", ".", "105", " port", " 443", " SYN"]
  3. 3

    The model receives a sequence of numerical IDs

    Each token is replaced by an integer ID from the tokenizer's vocabulary. The word "Analyze" might map to ID 38875, the space+word " this" to 1596, and so on. These IDs are not meaningful on their own. They are lookup keys that the model uses to begin computation. What happens next, from embedding lookup through prediction, is covered in the subsection below.

    [38875, 1596, 3251, 235292, 23109, 235265, 235274, ...]

Key insight: The word "Analyze" becomes one token. The IP address 192.168.1.105 becomes five or more tokens. One logical unit of security data consumes the same token budget as several English words. This asymmetry is the foundation of every capacity calculation you will do with LLMs in security operations.

Modern tokenizers vary in vocabulary size and training method. Larger vocabularies can represent more patterns as single tokens, but no vocabulary is equally efficient across all domains. Typical sizes range from roughly 32,000 entries in older models to over 250,000 in newer ones (for example, GPT-4 uses ~100,000 entries, Llama 3 uses 128,000, and some Google models exceed 256,000). These vocabularies are built from massive training corpora dominated by natural language text using algorithms like BPE or SentencePiece. The vocabulary is always optimized for what appeared frequently in training. Security specific syntax, including hexadecimal strings, Base64 payloads, log formats, and protocol flags, was a tiny fraction of that data, so it rarely earned dedicated vocabulary entries. The consequence: security text is systematically more expensive to process than general English, regardless of which model family you use.

From IDs to Vectors to Predictions

Tokenization converts your prompt into a list of integer IDs. But a list of integers is not something a neural network can operate on directly. The model needs dense numerical representations it can transform through learned mathematical operations. The journey from token IDs to a generated response follows a fixed pipeline that every transformer based LLM shares.

Continuing with the same example prompt:

Analyze this log: 192.168.1.105 port 443 SYN
  1. 1

    Embedding lookup

    Each token ID is used as a lookup key into an embedding table: a large matrix learned during training. The row corresponding to each ID is an embedding, a vector of floating point numbers (typically thousands of dimensions) that captures statistical patterns the token was associated with during training. The embedding for "Analyze" captures different patterns than the embedding for "SYN." At this stage, each embedding reflects only the token itself, with no awareness of surrounding context. These vectors are the model's actual input, not the text and not the IDs.

    Explore how embedding vectors can place related items near each other in a projected space. Rotate, zoom, filter groups, and click points to inspect how different concepts shape the neighborhood.

  2. 2

    Positional encoding

    Embedding vectors alone carry no information about order, so the model needs positional information to know that "192" appears before "168" and that "SYN" comes at the end. To build the foundation first, we begin with the method introduced with the original Transformer in 2017, shown in the demo below. In that method, a fixed sinusoidal position vector is added to each token's embedding, so the same token at a different position produces a different vector. Understanding this approach makes the modern one easier to follow. Most modern models instead use Rotary Position Embedding (RoPE), which leaves the embeddings unchanged and applies position inside the attention computation of every transformer layer (step 3). RoPE rotates the vectors that attention uses to compare tokens (the Query and Key vectors described in Part 3) so that the resulting attention scores reflect the relative distance between tokens. The purpose is the same in both approaches: without positional information, the model would treat the input as an unordered bag of tokens.

  3. 3

    Transformer layers process the vectors

    The sequence of position aware embedding vectors passes through dozens of transformer layers (a large model may have 80 or more). Each layer applies two operations in sequence. First, the attention mechanism lets each token position exchange information with other positions. In global attention layers, every token can interact with every other token; in local or sliding window layers, each token interacts only with nearby neighbors. 

    A causal mask ensures that during generation, each token can only attend to tokens that came before it, never to future tokens that have not been generated yet. Second, a feed forward network transforms each token's representation independently, applying learned patterns to reshape the information. After many layers of attention and feed forward processing, each vector has been updated: "SYN" now carries contextual information about the port number and IP address that preceded it, not just its own isolated embedding.

  4. 4

    Projection to logits

    After the final transformer layer, the model takes the vector at the last token position and projects it into a set of logits: one raw score for every entry in the vocabulary. If the vocabulary has 128,000 entries, this step produces 128,000 scores. A high logit for a token like " This" means the model's learned weights make that token a strong candidate to come next. A low logit for a token like " banana" means the model considers it unlikely in this context.

  5. 5

    Probabilities and token selection

    The logits are converted into probabilities using a function called softmax, which normalizes the scores so they sum to 1. The model then selects the next token using a decoding strategy. Common strategies include: greedy decoding, which always picks the highest probability token; temperature sampling, which flattens or sharpens the distribution to control randomness; top k sampling, which restricts the choice to the k most likely tokens; and top p (nucleus) sampling, which includes tokens until their cumulative probability reaches a threshold p. More on these later!

    In practice, these controls are often combined (for example, temperature with top p). This process is autoregressive: the selected token is appended to the context, and the entire pipeline repeats from step 1 to generate the next token. Each prediction is conditioned on everything that came before it, including the model's own previous outputs.

  6. 6

    Decoding back to text

    Once the model emits a stop signal or reaches a length limit, the full sequence of generated token IDs is converted back into readable text by the tokenizer. This decoding step is the reverse of tokenization: IDs become subword chunks, and chunks are reassembled into the response you see. The entire journey, from your typed prompt to the model's answer, was a chain of matrix multiplications over numerical vectors. The model may develop internal representations that correlate with meaningful patterns, but the mechanism is mathematical transformation, not human like comprehension.

Text does not become understanding

It is tempting to describe the pipeline above as the model "reading" your prompt and "deciding" what to say. That framing is misleading. What actually happens is: text becomes numerical vectors, and the model performs learned matrix operations over those vectors to predict the statistically most likely next token. The output often looks like comprehension because the patterns learned during training are powerful, but the mechanism is mathematical transformation, not reasoning. Every time the model produces an insightful analysis of your firewall logs, it is executing the same fixed sequence of vector multiplications and probability calculations described above.

The process above is called autoregressive generation: the model predicts one token at a time, and each prediction becomes part of the input for the next. This has a practical consequence for security work. If the model makes a mistake early in its response, for example misidentifying a source IP, every subsequent token is generated conditioned on that error. The model does not go back and revise. It builds forward from whatever it has already produced, which means early errors can compound. This is one reason why breaking complex security analyses into smaller, verifiable steps tends to produce better results than asking for a single long analysis in one pass.

The Token Tax on Security Data

The practical consequence of tokenization is what we call the token tax: the hidden cost of processing security data through a system optimized for natural language. Different data types consume dramatically different amounts of your token budget.

IPv4 Address

192.168.1.105

~5 to 7 tokens

Splits on dots and number groups. One logical unit becomes five or more fragments.

SHA-256 Hash

e3b0c44298fc...7852b855

~20 to 25 tokens

Hexadecimal characters rarely form coherent units in the tokenizer's vocabulary.

Firewall Log Entry

Full UFW line with MACs, IPs, ports, flags

~55 to 75 tokens

Multiple expensive elements compound within a single entry.

Hexadecimal data is the most expensive

A single SHA-256 hash consumes as many tokens as a full paragraph of English text. When you paste a list of indicators of compromise into an LLM, each hash, IP, and encoded payload is consuming far more of your context budget than you would estimate by character count alone.

Tokenization varies by model. Different model families use different tokenizers with different vocabularies. The token counts above are representative but the exact count for a given input will differ across models. Always test with the tokenizer of the model you are actually using.

How Attention Shapes the Output

Part 1 traced the pipeline: text becomes tokens, tokens become embeddings, and transformer layers transform those embeddings into predictions. This part takes a closer look at step 3 of that pipeline. Attention is not a separate stage that runs after the pipeline; it is the first of the two operations inside every transformer layer, so it runs once per layer, dozens of times over, before any logits are produced. The mechanism at the heart of each transformer layer is attention, and understanding how it works is essential for predicting when an LLM will handle your security data well and when it will not.

The central mechanism is called . When the model processes your input, it does not treat all tokens equally. In every attention layer, each token position computes a relevance score against the other positions it is allowed to see. The causal mask described in step 3 limits each position to itself and the tokens that came before it. In a full (global) attention layer, that means every earlier token in the input; in architectures that use local or sliding window attention, some layers restrict this comparison further to nearby tokens only (see the accordion in this section for details). In either case, tokens that score high contribute more to the updated vector at that position, and tokens that score low contribute less. Attention never selects the next token directly. It refines each position's vector, and only the vector at the final position, after the last layer, is projected into logits in step 4.

A useful way to think about this is a three part process known as Query Key Value (QKV):

Q: Query

"What am I looking for?"

Each token position produces a Query describing what information it needs from the tokens it can see. When the model predicts the next token, the Query at the final position is the one whose result ultimately feeds that prediction. Think of it as a search request broadcast to the earlier tokens.

K: Key

"What do I contain?"

Each input token advertises what kind of information it offers. The model compares every Key against the Query to compute a relevance score for each token.

V: Value

"Here is my information."

Each input token carries content that gets combined into the updated vector of the position that issued the Query. Tokens with high relevance scores contribute more of their Value; low scoring tokens contribute less.

The model compares the Query against every Key to compute relevance scores, then uses those scores to take a weighted combination of all the Values. The critical insight is that the model does not read your input word by word like a human reader. While processing your prompt, it computes attention for all positions in parallel, and each position can draw directly on any earlier token, however far back, through this relevance scoring mechanism. The response itself is still generated autoregressively, one token at a time, as described in step 5; the parallelism applies to how the input is processed, not to how the output is produced. This is why the structure and placement of data within your prompt can meaningfully affect the quality of the output.

Each attention layer also runs several of these QKV computations side by side, known as attention heads. Each head learns its own Query, Key, and Value projections, so different heads can track different kinds of relationships; one head might link a port number to the protocol flag that follows it, while another tracks sentence structure. The outputs of all heads are combined before the layer's feed forward network processes each position.

Attention is not understanding

Attention is a learned statistical operation over vectors. It can develop internal representations that support remarkably useful behavior, including patterns that correlate with syntactic structure, entity relationships, and domain specific conventions. However, these representations are not equivalent to human comprehension, awareness, intent, or judgment. When we say the model "pays attention to" certain tokens, we mean it assigns them higher relevance weights through matrix operations, not that it understands why those tokens matter.

Processing long inputs efficiently is one of the central engineering challenges in LLM design. Different model families combine several techniques to balance computational cost, memory usage, and attention quality. The techniques fall into two groups: attention patterns (which tokens can see which) and infrastructure optimizations (making the math faster and lighter on memory).

Attention patterns

Full (global) attention lets every token attend to every other token. This captures the richest relationships but scales with input length, making it expensive for long contexts.

Sliding window (local) attention restricts each token to a fixed neighborhood (e.g., 4,096 nearby tokens). This is efficient for local patterns like syntax and sentence structure, but cannot form on its own.

Local/global hybrid architectures alternate local and global layers within the same model. Local layers handle nearby context efficiently; periodic global layers provide full context visibility. This is the pattern most current long context models use.

Infrastructure optimizations

Improved positional encodings: techniques like and YaRN scaling allow models to handle sequences longer than those seen during training without retraining the model from scratch.

KV cache optimizations: during autoregressive generation, the model stores Key and Value vectors from all previous tokens in a so it does not recompute them at each step. In practice, most current long context models combine several of these techniques. None fully eliminates the attention degradation effects discussed in Section 5 of this Module, but each generation of models narrows the gap.
