Where Model Behavior Comes From

An LLM's behavior is not determined by a single factor. It emerges from layered causes: training data, post training alignment, system instructions, user context, retrieval, tools, and decoding settings. Each layer introduces distinct capabilities and distinct security risks.

Model Behavior Comes from a Stack, Not One Source

Section 1 covered the mechanics of how text enters the model and how the model processes it. This section addresses a deeper question: where does the model's observable behavior come from?

A common simplification is that "the model's behavior comes from its training data." Training data is foundational, but it is not the whole story. What an LLM actually does when it produces output is shaped by multiple layers, each applied at a different stage of the model's development or use. Think of these layers as a . Lower layers establish broad capabilities, and upper layers shape, constrain, and direct those capabilities toward specific outputs.

The Behavior Stack

From deepest (hardest to change) to shallowest (easiest to change at runtime):

  1. Pretraining data and model weights: the statistical patterns learned from a massive corpus. Determines what the model can do.
  2. Post training alignment: instruction tuning, preference tuning (RLHF, DPO), and safety training. Shapes how the model responds: helpfulness, refusal behavior, style.
  3. Fine tuning on specialized data: further training on domain specific datasets. Specializes capabilities but can amplify memorization and weaken safety behaviors.
  4. System/developer instructions: hidden instructions that define the model's role, constraints, and persona for a deployment.
  5. User prompt and conversation context: the immediate input that steers generation. Module 3 covers prompt engineering in depth.
  6. Retrieval and tools: external documents fetched at inference time (RAG), tool calls, API access. Grounds output in current information.
  7. Decoding and sampling settings: temperature, top p, frequency penalties. Controls randomness and repetition in output.
  8. Deployment safety layers: output classifiers, content filters, rate limiters applied by the provider or deployer after generation.

Each layer can override, constrain, or amplify the effects of the layers below it. A model pretrained on billions of web pages (layer 1) may have learned how to produce harmful content, but preference tuning (layer 2) trains it to refuse such requests. A system instruction (layer 4) can further restrict the topics it will address. A deployment filter (layer 8) can block outputs that slip past all other layers.

Why This Matters for Security

Different security risks originate at different layers of the stack, and the appropriate mitigation depends on correctly identifying the layer. A memorization risk lives in the weights (layer 1). A jailbreak exploits the alignment layer (layer 2). A prompt injection targets the system/user prompt boundary (layers 4 and 5). Misdiagnosing the layer leads to misapplied controls.

The rest of this section examines each major layer group (pretraining, post training, and inference time factors) with a focus on the security risks each introduces.

Pretraining and Parametric Memory

During pretraining, the model processes a massive corpus (web pages, books, code repositories, academic papers, forum posts) and adjusts its to become better at predicting the next token in a sequence. After processing billions of examples, the model develops internal representations that capture statistical regularities in language, facts, reasoning patterns, and code structure.

The result is . To understand how this differs from a conventional knowledge store, consider what you cannot do with parametric memory:

  • You cannot ask the model where it learned a given fact.
  • You cannot selectively update a single piece of information without retraining.
  • You cannot verify whether a recall is factual or confabulated, because the model generates the most statistically likely continuation regardless of truth value.

Uneven Coverage Across Domains

Parametric memory is not uniformly reliable. The model's statistical coverage reflects the composition of its training corpus: topics that appeared frequently and consistently produce strong internal representations, while topics that were rare, specialized, or poorly represented produce weaker ones. For security practitioners, this creates a systematic reliability gap.

Common web frameworks, popular programming languages, and widely discussed vulnerabilities are densely represented in training data. Niche industrial control system protocols, proprietary security tools, organization specific configurations, and specialized compliance frameworks may have minimal representation. The less training data available for a domain, the more the model fills gaps with statistically plausible but factually unreliable completions. It does not signal this shift: the same confident tone accompanies both well grounded and poorly grounded output.

Sparse Signal Means Higher Fabrication Risk

When you ask the model about a topic where its training signal is sparse, contradictory, or absent, it does not stop and say "I don't know." It continues predicting the next most probable token, constructing plausible sounding answers from whatever statistical fragments are available. The result can be entirely fabricated while appearing entirely authoritative. Section 5 examines the types of fabrication that result and the strategies for detecting them; the point here is that uneven parametric coverage is the source of that risk.

Knowledge Cutoffs and Parametric Limits

Every model has a . For security practitioners, this creates an operational gap: the model has no parametric information about vulnerabilities, threat actors, or developments disclosed after that date.

The critical danger: the model will not reliably indicate when it lacks knowledge. If you ask about a CVE disclosed after the cutoff, the model does not say "I have no information about that." Instead, it generates a plausible sounding description by assembling statistical patterns from the thousands of CVE descriptions it saw during training. The fabricated output may include:

  • A realistic CVE identifier that follows the correct format (CVE-2025-XXXXX) but refers to no real vulnerability.
  • A plausible CVSS score with a severity rating that matches the described attack vector.
  • Fabricated affected software versions and configuration details.
  • A coherent exploit narrative describing an attack path that never existed.
  • Remediation steps that sound authoritative but address a nonexistent problem.

All of this is presented with the same surface confidence as factual answers. This is a structural consequence of next token prediction: the model produces what is statistically probable given the prompt, not what is verified. The same pattern applies to any post cutoff content: new threat campaigns, recently published patches, vendor advisories, and regulatory changes are all outside the model's parametric memory.

A related risk applies even within the model's training window: asking for highly specific details (exact version numbers, precise configuration parameters, specific command syntax, named sources with page numbers) increases the chance of fabrication. The model's statistical patterns capture general relationships more reliably than exact values. When pressed for specifics it lacks, it generates plausible looking details rather than qualifying its uncertainty.

Parametric Recall Cannot Be Trusted for Recency or Precision

For any recency sensitive claim (recent CVEs, current threat intelligence, active campaigns, newly disclosed vulnerabilities) or any claim requiring exact specifics (precise version numbers, configuration values, command syntax), parametric memory alone is insufficient. Reliable answers require grounding in current authoritative sources, whether through retrieval augmented generation, tool calls to live databases, or manual verification. Always check a model's documentation for its cutoff date before relying on it for time sensitive security tasks. Section 5 covers how to detect and verify unreliable outputs in operational workflows.

Post Training, Fine Tuning, and Alignment

A pretrained model is a powerful but undirected pattern completion engine. It can continue any text in a statistically plausible way, but it does not reliably follow instructions, refuse harmful requests, or produce helpful structured answers. These behaviors are introduced through , which transforms the raw pattern completion engine into something that behaves like an assistant.

Instruction Tuning and Supervised Fine Tuning

teaches the model to follow user requests: answering questions, following formatting requirements, producing structured outputs. Without this step, a pretrained model responds to "Summarize this log" by generating text that looks like a continuation of a web page, not a direct answer to the instruction.

Preference Tuning and Safety Alignment

methods such as RLHF and DPO are the primary mechanism that teaches models to refuse dangerous requests, avoid generating certain content categories, and adopt a helpful conversational tone. This is what turns a raw autocomplete engine into a system that declines to provide instructions for creating malware.

What Post Training Does and Does Not Do

Post training shapes which behaviors are expressed; it does not erase knowledge from the model's weights. A safety aligned model still has the parametric patterns for producing harmful content; alignment training teaches it to decline rather than comply. This is why alignment can be bypassed through adversarial techniques (jailbreaks) and why it can be weakened through further fine tuning.

Domain Fine Tuning: Specialization and Its Risks

Organizations often fine tune a base or aligned model on domain specific data (incident reports, internal documentation, proprietary code) to create a specialized assistant. Fine tuning reshapes behavior toward the target domain, but it introduces two well documented risks:

  • Memorization amplification: Fine tuning datasets are small relative to the pretraining corpus. Each example has disproportionate influence on the model, making fine tuning data significantly more extractable than pretraining data.
  • Safety alignment degradation: Research demonstrates that safety behaviors can be weakened with as few as a handful of adversarially crafted fine tuning examples. Even benign fine tuning on domain data can inadvertently reduce the model's refusal rate for harmful queries.

Fine Tuning Security Implication

If your organization fine tunes a model on internal data, that data becomes embedded in the model's weights and potentially extractable. If the fine tuned model is then exposed to users (internal or external), sensitive training content (credentials, PII, proprietary logic) may be recoverable through targeted prompting or extraction attacks.

Inference Time Behavior: Context, Retrieval, Tools, and Decoding

Everything discussed so far (pretraining, post training, fine tuning) is baked into the model's weights before a user ever sends a prompt. But a significant portion of observable behavior is determined at , the moment the model actually generates a response.

System Instructions and User Prompts

Most deployed LLM applications include a . The user's prompt then provides the specific task or question. Together, the system prompt, conversation history, and user input form the context window: the complete text the model conditions on when generating its response.

Prompt engineering (the craft of structuring these inputs to elicit desired behavior) is covered in Module 3. For this section, the key insight is structural: the same model with the same weights can exhibit dramatically different behavior depending on what appears in its context window. This is why prompt injection is an attack surface; it manipulates behavior by manipulating context.

Retrieval Augmented Generation and Tool Use

addresses the knowledge cutoff and uneven coverage problems by injecting retrieved documents into the context at query time. Tool use and function calling extend this further, allowing the model to invoke external APIs (querying databases, running code, or accessing live systems) and incorporate the results into its response.

These mechanisms are critical for cybersecurity applications: a RAG enabled system can retrieve current CVE data, while a tool enabled system can query the NVD API directly. When the model's context contains authoritative source material, the statistically probable next tokens tend to align with the supplied data rather than with whatever fragments the model's parametric memory happens to contain. This is why retrieval is the single most effective way to reduce fabrication risk for recency sensitive or domain specific queries: it shifts the model from generating from memory to generating from evidence.

However, retrieval and tools also introduce new attack surfaces, including poisoned retrieval sources, manipulated tool outputs, and indirect prompt injection through retrieved content. The presence of retrieval does not eliminate the need for verification; it changes the verification target from "is the model's memory accurate?" to "is the retrieved content accurate and unmanipulated?" Section 5 covers the operational verification strategies that apply in both cases.

Decoding and Sampling Settings

The final layer of behavior control is how the model selects tokens from its predicted probability distribution. As Section 1 described, the model's last computational step produces a set of logits (one raw score per vocabulary entry), which are converted into probabilities via softmax. The model then samples from this distribution, and the sampling process is governed by parameters that determine how much randomness enters the selection.

scales the logit values before they enter softmax. A temperature near zero amplifies differences between logits, making the model almost always select the highest probability token (approaching greedy decoding). A high temperature compresses differences, giving many tokens a comparable chance of selection and producing more varied but less predictable output.

and further constrain which portion of the distribution the model may sample from. Top k limits selection to a fixed number of candidates; top p limits it to the smallest set of tokens whose cumulative probability exceeds a threshold. In practice, these parameters are often combined, and the effective sampling pool is the intersection of all active constraints.

The security implication is direct: decoding settings are a source of output variability. The same prompt submitted twice with a nonzero temperature can produce materially different responses, because the model samples different tokens from the same probability distribution on each run. For security critical applications (log analysis, policy enforcement, alert classification) lower temperatures reduce variability and improve reproducibility. Section 5 examines when variability matters operationally and how to design for consistency.

Model Behavior vs. LLM System Behavior

It is useful to distinguish between model behavior (what the neural network itself produces given weights + context) and system behavior (what the end user observes after system prompts, retrieval, tools, filters, and deployment controls are applied). A security assessment must consider the entire system, not just the model in isolation. A model might generate harmful output that a deployment filter catches: the model behavior is unsafe, but the system behavior is safe. Conversely, a model might be safe but a poisoned retrieval source might cause harmful system behavior.

Memorization, Contamination, and Evaluation Skepticism

Two risks rooted in the pretraining and fine tuning layers deserve focused attention because they are well documented, difficult to detect, and directly relevant to security decision making: and .

The Memorization Evidence Chain

LLMs do not merely learn general patterns from training data. Under certain conditions they memorize and reproduce verbatim sequences, including PII, credentials, proprietary code, and other sensitive content. This is not theoretical. A series of peer reviewed studies establishes an escalating evidence chain. The studies used specific models available at the time of publication, but the underlying mechanism (memorization as a structural property of next token prediction on large corpora) applies broadly.

1

Verbatim extraction from pretrained models (Carlini et al., USENIX Security 2021)

Extracted hundreds of verbatim sequences from a production language model, including real names, phone numbers, email addresses, and 128 bit UUIDs. First large scale demonstration that next token prediction training leads to memorization of training data.

2

Extraction survives safety alignment (Nasr, Carlini et al., ICLR 2025)

A divergence attack against a production safety aligned model recovered over 10,000 verbatim training examples for approximately $200 in API costs. Demonstrated that preference tuning and safety alignment do not prevent training data extraction. They suppress it under normal use but do not remove memorized content from the weights.

3

PII leakage is widespread (PII Scope, 2024)

Found that 16.9% of model generations contained memorized PII in targeted testing scenarios. Demonstrated that PII memorization is not limited to adversarial extraction; it occurs in normal use.

4

Fine tuning amplifies memorization

A model fine tuned on the Enron email dataset yielded 256 unique pieces of PII from just 1,800 generations. Fine tuning on a specific dataset makes that data more extractable, not less, because fine tuning examples have disproportionate influence on the model's behavior.

Security Implication

Any data that enters a model's training pipeline (pretraining or fine tuning) may later be reproducible. If your organization sends proprietary data to a cloud LLM provider whose terms allow training on user inputs, that data may become extractable by other users. If your organization fine tunes a model on internal data, that internal data becomes embedded in the model's weights and potentially extractable by anyone with access to the fine tuned model.

Benchmark Contamination and Evaluation Skepticism

When benchmark or evaluation data appears in the model's training corpus, the model has effectively "seen the test answers" during training. Its published benchmark scores then overstate its actual capability on novel, real world inputs.

This matters for security practitioners because model selection decisions are often based on benchmark comparisons. If a model scores highly on a contaminated benchmark, deploying it for security tasks based on that score creates a gap between expected and actual performance, potentially a dangerous gap for tasks like threat classification or vulnerability triage.

The Practitioner's Rule

Never select a model for security operations based solely on published benchmark scores. Evaluate the model on your own data, with your own test cases, measuring metrics relevant to your operational context. Dynamic benchmarks (where test questions change regularly) and private evaluations (held out from public datasets) are more reliable than static public benchmarks, but the most trustworthy assessment is always your own.

Check Your Understanding

Scenario

A cybersecurity vendor deploys an LLM based threat intelligence assistant. The system uses RAG to retrieve recent threat reports, a system prompt that restricts the model to cybersecurity topics, and a low temperature setting for consistency. During testing, the team observes three problems: (A) The model sometimes fabricates threat actor names that don't exist in any retrieved document. (B) The model occasionally provides generic advice that contradicts the specific guidance in retrieved reports. (C) The model refuses to discuss certain legitimate offensive security techniques. For each problem, identify which layer of the behavior stack is most likely responsible, and what mitigation would address that layer.

(A) Fabricated threat actor names: This is a parametric memory / pretraining issue (layer 1). The model generates plausible sounding names from statistical patterns in its weights when the retrieved context does not provide a definitive answer. Mitigation: Improve retrieval quality so the model has grounding for its claims; add instructions to cite sources and decline when evidence is insufficient; consider output verification against known threat actor databases.

(B) Generic advice contradicting retrieved reports: This is likely a context/retrieval integration issue (layers 5 and 6). The model may be relying on parametric patterns when retrieved content should take precedence, or the retrieval is injecting irrelevant documents that dilute the signal. Mitigation: Improve retrieval relevance and ranking; adjust system prompt to instruct the model to prioritize retrieved content over general knowledge; test with varied retrieval scenarios.

(C) Refusing legitimate offensive security topics: This is a post training alignment issue (layer 2). Preference tuning trained the model to refuse content that resembles harmful instructions, and its safety boundaries are overly broad for this security professional context. Mitigation: Adjust system prompt to clarify the model's authorized scope for security professionals; if the system prompt is insufficient, consider a domain fine tuned model with appropriately calibrated safety boundaries; add deployment layer overrides for verified professional users.
