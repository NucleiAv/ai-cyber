Cloud API Deployment

In a cloud API deployment, every prompt your organization sends crosses a network boundary to a third party server. The vendor's infrastructure processes the input, generates the response, and returns it. Three security considerations follow directly from that architecture:

1

Data Exposure

Every prompt, including any sensitive data it contains, travels to and is processed on infrastructure you do not control.

Confidentiality
2

Vendor Data Retention

Policies vary by provider. Some retain prompts for model improvement unless you opt out. Some offer enterprise agreements with no retention guarantees. You must verify.

Governance
3

Compliance Risk

Sending regulated data (PII, PHI, financial records) to a third party API may violate data residency requirements, sector specific regulations, or organizational policy.

Regulatory

Cloud APIs also offer significant advantages: access to the most capable models, managed infrastructure, service level agreements, and continuous model updates. The security question is not whether cloud is inherently bad. It is: what data am I sending, what does the provider do with it, and does that align with my risk tolerance?

Case Study: Samsung Data Leak (2023)

Samsung engineers used a cloud based LLM for routine work tasks. Within 20 days, three separate data exposure incidents occurred: proprietary source code was pasted into prompts, semiconductor equipment measurement data was shared for analysis, and a meeting transcript was submitted for summarization. Each prompt transmitted proprietary data across the network boundary to the LLM provider's servers.

Samsung subsequently banned employee use of external AI tools. The incident illustrates a systemic risk category: any data submitted to a cloud LLM during inference may enter the provider's data pipeline. This applies to any cloud API deployment where prompts contain sensitive content.

Local Deployment: Data Residency Is Not Security

In a local deployment, the model runs on infrastructure your organization owns and controls. Data never leaves your network boundary. This eliminates the cloud data exposure risk, but it introduces a different set of risks that are easy to underestimate.

The core lesson: "local" means data stays within your boundary. It does not mean the deployment is secure. Local deployment shifts responsibility for security entirely to your organization. If you misconfigure the deployment, you own the consequences.

Insecure Defaults in Local Inference Tools

Local inference tools often ship with default configurations optimized for convenience, not security. Three common issues create risk:

No Authentication

Some tools bind their API to all network interfaces by default, meaning any device on the network can access the model without credentials.

No Access Logging

Usage is not audited by default, making it impossible to detect misuse or unauthorized access after the fact.

Model File Vulnerabilities

Model weight files are a potential attack surface. Maliciously crafted model files can exploit parsing vulnerabilities to access memory contents.

Example: Ollama Exposed Instances

Ollama, a widely used open source local inference tool, binds its API to all network interfaces by default. In 2025, security researchers discovered thousands of Ollama instances exposed to the public internet without authentication. This is the same class of misconfiguration risk that affects any networked service with permissive defaults, from databases to container registries. Always audit the network exposure of any local inference tool before deployment.

Hybrid Models and the Evaluation Checklist

Most organizations will not choose purely cloud or purely local. Hybrid approaches route different tasks to different deployment models based on data sensitivity: tasks involving non sensitive data go to a cloud API for maximum capability, while tasks involving regulated or proprietary data use a local model.

Regardless of the deployment model, evaluate every option against the same structured checklist:

Evaluation Factor Cloud API Local
Network exposure All prompts cross the network boundary Data stays within boundary, but the API itself may be exposed
Authentication API key or OAuth managed by vendor Often no authentication by default; you must add it
Data residency Data processed in vendor's jurisdiction Data stays in your jurisdiction
Data retention Varies by vendor and agreement tier Under your control
Model file integrity Vendor managed You must verify provenance and integrity of downloaded weights
Access logging Typically available via vendor dashboard Must be configured by your team
Capability Access to largest, most capable models Constrained by local hardware

This checklist is tool agnostic. It applies whether you are evaluating a specific cloud provider, a specific local inference tool, or a managed on premises solution. The names and versions change; the evaluation criteria do not.

Quantization as a Security Variable

is essential for running models on consumer hardware. It makes local deployment practical. But it is not purely a performance optimization; it has security implications that matter for operational use.

Mild quantization (16 bit to 8 bit) generally produces minimal quality degradation. More aggressive quantization introduces effects that matter for security operations:

Safety Alignment Degradation

Research shows aggressive quantization can weaken guardrails that prevent the model from generating harmful content.

Increased Bias

Quantized models show disproportionate quality degradation on non English text and underrepresented topics.

Reduced Truthfulness

Studies report decreasing truthfulness scores at lower quantization levels, which directly affects reliability in security operations.

Testing Obligation

If you deploy an aggressively quantized model for security operations, its behavior may differ from the full precision version in ways that affect safety and reliability. Always test the specific quantized variant you intend to deploy against your specific tasks. Do not assume that evaluation results from the full precision model transfer to the quantized version.

Deployment Decision Scenario

Apply the evaluation checklist to a realistic deployment decision. Work through the scenario below, then reflect on what shaped your reasoning.

Decide: Deploy the Clinical LLM

Scenario

You are the security lead at a mid size healthcare company. The IT team wants to deploy an LLM to help clinicians summarize patient notes and flag potential drug interactions. Patient data includes protected health information (PHI) subject to HIPAA. Your team has 16 GB RAM workstations and a budget for one cloud API subscription. What deployment model do you recommend?

Risk: PHI crosses the network boundary. You have access to the most capable models, but every patient note crosses the network boundary to a third party server. This creates HIPAA compliance risk regardless of the vendor's assurances. Even with a Business Associate Agreement (BAA), you are transmitting PHI to infrastructure you do not control.

Is there a way to get cloud capability for some tasks while keeping PHI local?

Cloud with BAA: legally defensible, technically risky. A BAA provides contractual protection, but it does not eliminate the technical risk: PHI still leaves your network. If the vendor experiences a breach, or if data retention policies change, your patients' data is exposed. Many healthcare organizations take this route, but a security lead should document the residual risk explicitly.

Consider what you would document in your risk register.

PHI stays within your boundary. Good for compliance. But 16 GB workstations limit you to smaller, quantized models. You must also ensure the inference tool's API is not exposed on the hospital network, add authentication, and verify model file integrity.

An aggressively quantized model may have degraded safety alignment. For clinical use, have you tested the quantized variant against your drug interaction tasks?

Most compliance friendly option. You keep PHI within your boundary, but you accept reduced model capability and take full responsibility for securing the deployment. Your hardening checklist: restrict API to localhost, add authentication if network access is needed, enable logging, verify model file integrity, and test the quantized model's accuracy on your clinical tasks.

Good. You accepted the tradeoff and defined your controls.

Route tasks by data sensitivity. Non PHI tasks (general medical knowledge queries, documentation formatting, policy lookups) go to the cloud API for maximum capability. Tasks involving actual patient data (note summarization, drug interaction checks) run on the local model, keeping PHI within your boundary.

This requires clear data classification policies and technical enforcement. The risk of a clinician accidentally pasting PHI into the cloud routed interface must be addressed through workflow design, not just policy.

Key takeaway. There is no universally correct answer. The right deployment model depends on regulatory requirements, risk tolerance, hardware constraints, and the sensitivity of the data involved. What matters is that you evaluated each option against the same checklist (network exposure, authentication, data residency, retention, model integrity, logging, and capability) and made a documented, justified decision.

Auditability and Reproducibility Controls

Section 5 covers reproducibility settings: fixed seeds, low temperature, constrained sampling: as inference time controls for reducing output variability. But the ability to reproduce a past inference decision depends on more than sampling parameters. It requires capturing the full context that produced the output. That makes reproducibility a deployment governance requirement: the logging infrastructure, retention policies, and audit fields must be designed into the deployment architecture before the model serves its first request.

Without these controls, incident response becomes guesswork. If a model produces a harmful or incorrect output, your team needs to answer: What prompt was sent? Which model version processed it? What retrieval documents were injected? What sampling settings were active? If any of these are missing, you cannot reproduce the failure, attribute it to a root cause, or verify that a fix actually resolves it.

Required Audit Fields

Every inference request in a security relevant deployment should log the following fields. Together, they form the minimum information needed to reconstruct any model interaction after the fact.

1. Prompt Text or Template Version

The exact input sent to the model, or a versioned template ID if prompts are generated programmatically. Without this, you cannot reproduce what the model saw.

2. System Instruction Version

The system prompt or instruction set active at the time of the request. System prompts change over time; the version must be pinned to the log entry.

3. Model Name and Version

The specific model identifier (e.g., gpt-4-0613, claude-3-sonnet-20240229). Cloud providers update models silently; the version string is the only anchor.

4. Deployment Mode

Cloud API, local, or hybrid, and which routing path was taken for this specific request. In hybrid deployments, you need to know which model handled which query.

5. Sampling Parameters

Temperature, top p, top k, and any other decoding settings active for this request. As Section 5 explains, these directly determine output variability.

6. Random Seed

If the API supports deterministic mode, the seed value used. Without it, identical inputs can produce different outputs and the interaction is not reproducible.

7. Retrieval Corpus Version and Document IDs

If retrieval augmented generation (RAG) was used, which corpus version was active and which specific documents were retrieved and injected into the prompt.

8. Tool Versions and Outputs

If the model called external tools (APIs, databases, code interpreters), which versions were active and what they returned. Tool outputs are part of the model's effective input.

9. Timestamp

UTC timestamp for the request. Essential for correlating model behavior with external events, model updates, or corpus changes.

10. User or Session Identifier

A pseudonymized identifier linking the request to a user or session, enabling pattern analysis across interactions without exposing PII.

11. Final Model Output

The complete response returned to the user, including any content that was subsequently filtered. You need both the raw output and the post filter version.

12. Human Reviewer Decision

If a human reviewed the output before it reached the end user, what was their decision (approved, edited, rejected) and who made it. This closes the accountability loop.

Why this belongs in deployment architecture. These fields cannot be added retroactively. If the logging infrastructure is not part of the deployment design, the data is simply not captured. After an incident, there is no way to go back and reconstruct what the model saw, what settings were active, or what the full output was. Auditability is a deployment decision, not an inference time afterthought.
