Why Models Fabricate and Why Outputs Vary

When LLMs produce output for security tasks, two reliability risks demand practitioner attention: the model may fabricate plausible but unsupported claims (hallucination), and it may produce different outputs from the same prompt across runs (variability). This section teaches you to classify fabrication types, identify the conditions that raise risk, apply a verification workflow, and design for reproducibility.

From Probabilistic Generation to Output Reliability

Section 1 showed that LLMs generate output by predicting and sampling tokens from a probability distribution over the vocabulary. Section 2 showed that the model's observable behavior is shaped by a stack of sources: pretraining, alignment, fine tuning, system prompts, user context, retrieval, tools, and decoding settings. Section 2 also identified specific conditions under which those sources produce unreliable output, including uneven parametric coverage across domains, knowledge cutoffs that leave post cutoff queries ungrounded, and decoding settings that introduce randomness.

This section studies what security practitioners must do when those mechanisms produce plausible but unreliable outputs. The question is no longer how does the model generate? or where does behavior come from? The question is: when should you trust what comes out, and what should you do when you cannot?

2

Two Failure Modes Students Must Separate

LLM outputs can fail in two distinct ways. Both trace to the probabilistic generation mechanism, but they are different problems that require different responses. Confusing them leads to misapplied controls.

Fabrication (Hallucination)

An output presented as factual but not grounded in reality or in the evidence supplied to the model. The model invents facts, citations, identifiers, or reasoning chains that do not exist.

This is an accuracy and grounding problem. The response sounds correct but is not. The mitigation is verification: checking claims against authoritative sources.

Output Variability

Different outputs from the same or similar prompt across runs, caused by sampling randomness, decoding settings, backend infrastructure changes, retrieval corpus updates, model version changes, or conversation history differences.

This is a reproducibility and control problem. Two runs may both be plausible but disagree. The mitigation is controlling decoding settings, stabilizing inputs, and logging everything.

Related but Not Identical

A fabricated output may be perfectly consistent across runs (the model confidently produces the same wrong answer every time at low temperature). A variable output may contain no fabrication (two different but accurate summaries of the same log data). Treating variability as proof of hallucination, or treating consistency as proof of accuracy, are both diagnostic errors. The sections that follow address each failure mode on its own terms.

3

Types of Hallucination in Security Contexts

Not all hallucinations are alike. Recognizing the type helps you target your verification strategy. The four categories below cover the patterns most relevant to security work.

Factual Fabrication

The model invents facts that do not exist. In a security context, this might be a CVE identifier that follows the correct format (CVE‑2024‑XXXXX) but refers to no real vulnerability, a claimed default port number for a service that uses a different port, or a fabricated statistic about breach frequency. The output looks correct because it follows the structural conventions of real data.

Source Fabrication

The model cites a source that does not exist or attributes a real finding to the wrong source. It might reference a NIST Special Publication number that was never issued, attribute a technique to a MITRE ATT&CK group that never used it, or cite an RFC with a correct looking number that does not correspond to the claimed topic. The citation format is impeccable; the citation itself is fiction.

Entity Conflation

The model merges attributes of two or more distinct entities into a single description. It might blend the tactics of two different APT groups into one profile, combine the vulnerability details of two similarly named CVEs into a single description, or merge the capabilities of two security tools that share a similar name. Each individual fact may be true of something, but the composite is wrong.

Logical Confabulation

The model constructs a chain of reasoning where individual premises may be true but the logical connections between them are invented. It might argue that because a vulnerability affects a library and a target application uses that library, the application is therefore exploitable through a specific attack path, when in reality the application's implementation does not expose the vulnerable code path. The reasoning structure looks sound but does not hold.

4

When Hallucination Risk Rises

Hallucination is always possible, but certain conditions make it substantially more likely. Recognizing these conditions lets you calibrate your verification effort: spend more scrutiny where the risk is highest.

Requests for Exact Specifics

Asking for precise version numbers, exact command syntax, specific configuration parameters, named sources with page numbers, or exact statistics increases fabrication risk. The model's statistical patterns capture general relationships more reliably than exact values. When pressed for specifics it lacks, it generates plausible looking details rather than qualifying its uncertainty.

Sparse or Specialized Domains

As Section 2 explained, parametric coverage is uneven. Niche protocols, proprietary tools, organization specific configurations, and specialized compliance frameworks may have minimal representation in training data. The less training data available for a domain, the more the model fills gaps with statistically plausible but factually unreliable completions.

Post Cutoff Events

Section 2 detailed how every model has a knowledge cutoff. Any CVE, threat campaign, patch, or advisory published after that date exists outside the model's parametric memory. Without retrieval or tool access, the model will construct fabricated responses from related patterns it saw during training rather than admitting ignorance.

Ambiguous or Underspecified Prompts

When a prompt is vague, the model infers missing context from statistical patterns. If you ask "Is this server vulnerable?" without specifying the server, software version, configuration, or threat model, the model fills every gap with its best statistical guess. Each inferred detail is an opportunity for fabrication. Precise, well scoped prompts constrain the model's generation space and reduce the room for invented content.

Long Inputs and Buried Evidence

Section 1 documented the lost in the middle effect: the model attends less effectively to information positioned far from the beginning and end of long inputs. When critical evidence is buried in the middle of a large prompt, the model may overlook it and generate output based on patterns from better attended regions or from parametric memory rather than from the supplied data. This is a distinct mechanism from hallucination, but the result can look the same: the output contradicts or ignores evidence that was present in the input.

Confidence does not correlate with accuracy. A hallucinated response looks identical to an accurate one in tone, structure, and apparent certainty. The model does not signal when it shifts from well grounded patterns to fabrication. There is no built in confidence score you can inspect. You cannot use the model's own language ("I'm confident that...") as evidence that a claim is correct.

5

Detection and Mitigation Workflow

Because the model itself cannot reliably flag its own hallucinations, detection and mitigation must be built into your workflow rather than delegated to the model. The following workflow applies to any security task where LLM output informs a decision.

Step 1: Identify Which Claims Require Verification

Not every token in a response carries the same risk. Focus verification effort on the output categories most prone to fabrication:

  • Exact identifiers: CVE numbers, MITRE ATT&CK technique IDs, NIST publication numbers, RFC numbers.
  • Exact values: version numbers, port numbers, configuration parameters, command syntax.
  • Citations and attributions: vendor advisory titles, research paper references, threat actor attributions.
  • Exploitability and impact claims: statements about whether a vulnerability is exploitable in a specific configuration.
  • Temporal claims: statements about when events occurred, especially near or after the model's knowledge cutoff.

Step 2: Separate Summary from Evidence

When the model summarizes data you supplied (log entries, configuration files, documents), its output is constrained by what you provided. When the model makes claims that go beyond the supplied data, drawing on parametric memory or inference, fabrication risk increases. Train yourself to notice the boundary: is this claim derived from data in the prompt, or is the model adding information from its own weights?

Step 3: Verify Against Authoritative Sources

Apply source specific verification to high risk claims:

  • Check every CVE identifier against the NVD (National Vulnerability Database).
  • Verify MITRE ATT&CK technique IDs, group attributions, and software entries against the MITRE ATT&CK website.
  • Confirm NIST publication numbers and their content against the NIST publications catalog.
  • Validate vendor advisories against the vendor's own security portal.
  • Sandbox or review any recommended commands, scripts, or configuration changes before executing them in production.

Step 4: Use Source Grounding to Reduce Fabrication

As Section 2 explained, retrieval augmented generation shifts the model from generating from parametric memory to generating from supplied evidence. When factual accuracy matters, supply the source material directly: paste the actual CVE record, provide the real configuration file, include the specific log entries. The model is far less likely to fabricate when the statistically probable next tokens align with authoritative data in the context.

However, retrieval does not eliminate the need for verification. It changes the verification target: instead of asking "did the model invent this?" you ask "is the retrieved source accurate and unmanipulated?" Poisoned retrieval sources can cause the model to produce grounded but wrong output.

Step 5: Prompt for Explicit Uncertainty

Instruct the model to qualify its confidence and flag gaps. Prompts like "If you are uncertain about any detail, say so explicitly" or "Distinguish between claims you can support with specific evidence and claims that are your best estimate" shift the model's output distribution toward tokens that express uncertainty rather than tokens that assert false confidence. This technique reduces but does not eliminate the problem. A model instructed to flag uncertainty will still sometimes hallucinate without flagging. Treat it as a useful layer in a defense in depth strategy, not a standalone solution.

Step 6: Cross Validate with Multiple Queries

Run the same query multiple times and compare outputs. If the model produces materially different answers to the same question across runs, that inconsistency signals that the model's statistical confidence in the underlying content is low. Consistent answers do not guarantee accuracy, but inconsistent answers reliably indicate higher hallucination risk. For critical decisions, run the query three to five times, extract the key claims from each response, and flag any claim that appears in fewer than all responses for manual verification.

Step 7: Escalate High Impact Outputs

For any output that will directly inform an operational decision (incident classification, vulnerability remediation, compliance determination, threat attribution), route the LLM output through human review before action. The model accelerates your workflow by generating drafts, surfacing candidates, and organizing data. The human review step ensures that acceleration does not introduce fabricated content into decisions that affect security posture.

Layer these strategies. No single technique eliminates hallucination. The most robust approach combines source grounding, explicit uncertainty prompting, cross validation, authoritative verification, and human review. Each layer catches failures that other layers miss.

6

Why the Same Prompt Produces Different Outputs

Section 2 defined output variability as a reproducibility problem distinct from fabrication. Multiple sources can cause the same prompt to produce different outputs across runs. Understanding these sources is essential for designing security workflows that require consistency.

Sampling and Decoding Settings

As Sections 1 and 2 explained, temperature, top p, and top k control how much randomness enters token selection. Any nonzero temperature allows the model to select different tokens from the same probability distribution on different runs. At temperature 0 (greedy decoding), the model should select the highest probability token every time, but even this does not guarantee perfect reproducibility in practice.

Infrastructure Nondeterminism

GPU floating point arithmetic is not perfectly deterministic across different hardware. Request batching can change computation order. KV cache state and context caching differences between API calls can produce slightly different internal representations. These effects are small but sufficient to change token selection at decision boundaries, even at temperature 0.

Provider Side Model Updates

Cloud API providers periodically update model weights, system prompts, safety filters, and infrastructure. A prompt that produced one output last week may produce a different output this week because the model behind the API endpoint changed. Unless you pin a specific model version, your workflow is subject to unannounced changes.

Retrieval, Tools, and Context Changes

In RAG enabled systems, the retrieved documents may change between runs as the retrieval corpus is updated. Tool calls may return different results over time. Conversation history accumulates across turns, changing the context the model conditions on. Any change in the model's input changes the probability distribution it generates from.

Designing for Reproducibility in Security Operations

Output variability is not inherently a problem. The question is whether the task requires consistency. The guidance below matches reproducibility strategy to task type.

Low Variability: Extraction, Classification, Compliance, Triage

Use temperature 0.0 through 0.2. Constrain output to structured formats (severity labels, JSON schemas, fixed categories). Use fixed prompt templates rather than ad hoc instructions. Stabilize retrieval sources so the same query returns the same documents. Pin model versions when the API allows it. Accept that outputs will be less creative and may be more repetitive.

Controlled Variability: Brainstorming, Red Teaming, Training

Use temperature 0.5 through 0.8 for tasks that benefit from diversity: brainstorming attack vectors, generating phishing simulation variants, red team scenario planning, hypothesis generation, or training exercises. Higher variability increases the chance of hallucination, so pair these settings with stronger verification. Never use high variability outputs as authoritative without review.

Even with optimal settings, perfect reproducibility is not guaranteed. Infrastructure nondeterminism, provider side model updates, and retrieval corpus changes can introduce variation that no sampling parameter controls. Your reproducibility strategy must account for this: when exact reproduction is impossible, your logs should at least let you reconstruct the conditions under which the output was generated. Check Your Understanding

Scenario

Your SOC team has integrated an LLM into its alert triage pipeline. The model reads each incoming alert and classifies it as critical, high, medium, or low severity. During a Friday evening shift, an analyst notices that the same alert (identical source IP, identical signature, identical payload) was classified as "high" at 6:12 PM but "critical" at 6:47 PM when it fired again. The analyst also discovers that the model's explanation for the "critical" classification references a threat intelligence report from a vendor that the SOC does not subscribe to, and the cited report title returns no results on any search engine.

For this scenario, identify: (1) which parts of the output might be hallucinated, (2) what must be verified and against which sources, (3) what decoding and reproducibility settings should be used for this task, and (4) what evidence should be logged for each classification.

(1) Likely hallucination: The cited threat intelligence report is source fabrication. The model generated a plausible sounding citation because the statistical patterns of security text include references to vendor reports, but the specific report it produced is fiction. The "critical" severity rating itself may or may not be fabricated, but it was generated alongside fabricated justification, which undermines confidence in the classification.

(2) Verification requirements: Every cited source must be checked against the SOC's subscribed intelligence feeds. The severity classification should be cross referenced against the alert signature's known risk level in the SOC's own detection rules. Any vendor advisory or threat report referenced in the explanation must be verified against the vendor's published portal. Commands or remediation steps must be reviewed before execution.

(3) Recommended settings: Alert triage classification requires consistency. Set temperature to 0.0 (or as close as the API allows). Constrain output to a structured schema: a severity label from a fixed set plus a reasoning field that must cite only sources present in the supplied context. Use a fixed prompt template. Ground the model via RAG by supplying relevant threat intelligence with each alert rather than relying on parametric memory.

(4) Logging requirements: Record the exact prompt (including any retrieved context), the model's response, the severity label, the timestamp, and the sampling parameters used. If an incident response decision was informed by the classification, the post incident review needs to be able to reconstruct what the model saw and produced.
